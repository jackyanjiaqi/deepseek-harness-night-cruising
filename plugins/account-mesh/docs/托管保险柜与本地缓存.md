# 托管保险柜与本地缓存

> 状态：P1 已实现（rc.15）· 2026-11-27  
> 基线：`dsh-account-mesh@0.1.0-rc.13`。远端 JLC 压缩块传输已验收（`1e7537c`：`sessions/export/prepare` + `mesh-bin` 分块 + 本地解码）。  
> 需求来源：`docs/daily/20261126/托管保险柜和本地缓存策略.md`。  
> 取代：`docs/daily/20261126/底部栏插件面板与保险柜设计.md` 中“关闭 DSH 后保险柜清空”的生命周期（该文第 2/4/6 节）；其“不提供查看/下载入口、面板只报聚合状态”的面板约束继续有效。  
> 关联：`DETAIL.md`、`JSONL会话数据压缩.md`。

## 0. 结论

把“每次打开远端会话都要跨网重传整份档案”改成“**档案只传一次，之后每次只换一把小钥匙**”：

1. 远端 B 的档案第一次到本机 A 后，A 随机生成内容密钥 `DEK` 加密落盘，`DEK` 用 B 派生、按次发放的开柜密钥 `K_g` 包在容器头里；明文不落盘，`K_g` 用完即弃；
2. 再次打开同一会话时，A 通过已认证的 mesh 通道向 B 申请**这一代、这一个容器**的开柜票据；B 校验后只回一把包在链路密钥里的 `K_g`，并同时给出下一代 `K_{g+1}`；
3. A 解密 → 只把 32 B 的 `DEK` 重新包到 `K_{g+1}`（重写约 120 B 的头）→ 提交 → 丢弃钥匙。旧的 `g` 从此失效，网线上只有不到 1 KB 的票据，档案本体一个字节都不重传，也不重写；
4. B 永远不接收 A 的密文、不代 A 解密、不返回明文，只对**自己创建过的托管项**按自己的策略发钥匙；
5. 任何一步失败（B 离线、撤销、篡改、代次回放、旧版本）都退回完整 JLC 拉取，不伪造“已是最新”。

一句话概括安全目标：**把 A 当成可能完全被对方控制的对手来写 B 的代码；B 最坏只会交出一把它自己托管给这台设备的会话钥匙，交不出别的会话、明文服务或根密钥。**

## 1. 现状与差距

| 能力 | rc.13 现状 | 本设计目标 | 差距 |
| --- | --- | --- | --- |
| 档案传输 | JLC 压缩块，`prepare` + `mesh-bin` | 不变 | 已验收 |
| 落盘 | 进程内随机密钥 AES-256-GCM，`vault/*.ncv` | 跨重启可用的 `NCV2` 容器 | 密钥是进程级的，重启即失效 |
| 进程内二次打开 | 命中保险柜，跳过块传输，但仍整份 decode | 命中后连 native decode 也尽量跳过（投影 sidecar） | 需要新增投影缓存 |
| 跨重启二次打开 | 重新拉全量 | 一个 RTT 换钥匙，秒开 | 本次核心 |
| 一致性 | 无远端指纹校验 | 开柜回包带 `fresh`，陈旧时标注并后台刷新 | 需要新增指纹 |
| 钥匙生命周期 | 进程内存，退出即丢 | B 派生、按代发放、两阶段提交、可撤销 | 需要新协议 |
| 面板 | 聚合状态 + 清空 | 增加“托管中/仅本次进程”模式说明 | UI 小改 |

## 2. 角色与术语

| 术语 | 含义 |
| --- | --- |
| A（观看方） | 用户当前操作的 DSH 实例，保存密文、发起开柜 |
| B（托管方） | 拥有会话原文的远端 DSH 实例，派生并保管根密钥 |
| 托管项 / 容器 | 一份 JLC archive 的密文对（`.hdr` + `.dat`），按 `(peer, session, priority)` 定位，文件名是逻辑键的 SHA-256 |
| 内容密钥 `DEK` | A 首次托管时随机生成的 32 B，只用来加密 `.dat`；以 `wrap_g` 形式存在容器头里，没有 `K_g` 取不出 |
| 开柜密钥 `K_g` | 第 `g` 代开柜密钥，由 B 的根密钥派生；A 只在一次开柜期间持有，用来解包/重新包住 `DEK` |
| 代（generation） | 开柜密钥的版本。每开一次柜前进一代，旧的 `K_g` 立即失效 |
| 开柜票据 | B 对一次开柜的授权回包：包好的 `K_g`、包好的 `K_{g+1}`、签名、新鲜度 |
| 托管账本 | B 侧记录 `depositId`、对端设备、B 自己的会话 id、内容哈希、代次、撤销状态的文件；只在 B 侧，A 的容器里没有会话 id |
| 提交（commit） | A 把容器头的包裹从 `K_g` 换成 `K_{g+1}` 并原子落盘后，通知 B 确认新代次；提交前的旧代仍可重发一次，提交后旧代死亡 |
| 撤销 | B 主动让某个托管项或某台设备的全部托管项永久不可开 |

`K_g` 与明文 `DEK` 只存在于进程内存与链路密文里；默认配置下磁盘上没有 A 可直接使用的钥匙（可选的离线通行证是显式例外，见 15.2）。这是与“把钥匙存 cookie 目录”不同的默认取舍。

## 3. 威胁模型

| 编号 | 威胁 | 本设计的处理 |
| --- | --- | --- |
| T1 | 拿到 A 的磁盘：直接读保险柜文件 | 只有 `.dat` 密文与包着的 `DEK`；没有 `K_g` 取不出 `DEK`。A 的索引只有哈希与随机 `depositId`，没有标题、路径 |
| T2 | 同账号的另一台设备 C 冒充 A 申请钥匙 | 托管项绑定创建时的 `peerDeviceId`；C 的设备身份不匹配即拒绝。C 即使拿到 A 的密文文件也解不开 |
| T3 | A 伪造/篡改容器，把 B 当解密神谕 | `vault/open` 不接受密文；B 只按账本派生钥匙，返回的钥匙绑定 `archiveSha`；本地 GCM 失败即丢弃 |
| T4 | A 驱使 B（包括 B 的 agent）去“变相解密” | 没有代解密接口；钥匙只能在 B 的本地策略下发放；批准动作不在 mesh RPC / 工具 / MCP 面上，只能由 B 的用户在 B 的界面点（严格模式） |
| T5 | 重放旧票据、回滚到旧代、跳过代次 | 账本维护 `confirmedGen` / `issuedGen` 窗口；`gen` 只允许当前未提交代或下一已发放代，其余拒绝；票据带随机 challenge 与有效期 |
| T6 | 撤销后仍用缓存 | `revoked` 是账本硬状态；A 收到 `revoked` 立即删除本地容器并回退完整拉取 |
| T7 | 陈旧数据被当成最新展示 | 开柜回包带 B 侧文件指纹；`fresh=false` 时 UI 标注“本地缓存”，并后台拉取替换 |
| T8 | 钥匙/明文进日志、进工具返回值、进 UI | 日志只记 `depositId`、代次、字节数；工具只返回投影消息；面板只有聚合数字 |

**非目标（诚实边界）**：

- 同一个 OS 用户下的恶意程序读取 A/B 的进程内存、ptrace、调试 Host，或直接改插件代码；
- B 本身被攻陷；
- A 已经把明文显示在屏幕上之后被截屏/复制（这已经不是缓存层能解决的问题）；
- JS 运行时/GC 可能在内存里保留密钥或明文的副本；本设计只承诺“不主动写盘、不进日志、不进工具返回值”，不承诺抗内存取证；
- 文件大小、访问时间等元数据侧信道（能看出“某会话大概多大、最近开过”）；
- 公网中间人（当前 mesh 只在 LAN/Tailscale，链路由 DTLS + Ed25519 双向认证保护）。

## 4. 设计原则

1. **B 只发钥匙，不代解密。** 任何接口都不接受“密文 + 请解开”这种形态，从结构上消灭神谕。
2. **钥匙不落 A 的盘（默认）。** A 保存的是用 `DEK` 加密的档案，以及用 `K_g` 包住的 `DEK`；`K_g` 不落盘，`DEK` 没有 `K_g` 取不出来。
3. **一容器一 DEK、一代一开柜钥。** `K_g` 只对一个 `depositId + archiveSha + 对端设备 + 代次` 有效，不能横向解开别的会话。
4. **授权可撤销、可审计、不可重放、不可转移。** 票据单次、短效、绑定链路与设备；B 能看见谁在什么时候开了哪个托管项。
5. **失败即回退。** 任何校验失败都退到完整 JLC 拉取；绝不把旧数据标成新数据，绝不把失败标成成功。
6. **明文只在内存和屏幕。** 解密、投影、换钥都在 `transfer` 管线内完成；不写明文临时文件、不进 `workspace`、不进日志。

## 5. 密钥体系

### 5.1 四层密钥

| 层 | 生成方 | 存放 | 用途 |
| --- | --- | --- | --- |
| 根密钥 `root_B` | B 首次启用托管时随机 32 B | B：`vault/root.key`，0600，永不出机 | 派生每个托管项每一代的开柜密钥 |
| 开柜密钥 `K_g` | B 按需派生 | 只在 B 内存与 A 本次开柜内存 | 包裹/解包 `DEK`；它才是每次开柜要换的“钥匙” |
| 内容密钥 `DEK` | A 首次托管时随机 32 B | 只以 `wrap_g` 存在容器头；没有 `K_g` 取不出，A 也不单独保存明文 `DEK` | AES-256-GCM 加密 `.dat` 里的 archive 与 sidecar |
| 链路密钥 `linkKey` | A、B 每条 WebRTC 链路各自生成 X25519 临时密钥对，握手时交换 | 只在链路内存 | 包装 `K_g`，让票据不能跨链路/跨设备重放 |

派生：

```text
K_g = HKDF-SHA256(
        ikm  = root_B,
        salt = depositId,
        info = "dsh-mesh/vault/v2/K|" + peerDeviceId + "|" + archiveSha + "|" + g,
        len  = 32)

DEK = random 32 B（A 生成，B 不知道）

wrap_g = AES-256-GCM(K_g, nonce=random12, plaintext=DEK,
                     aad = "dsh-mesh/vault/v2/hdr|" + depositId + "|" + g
                           + "|" + archiveSha + "|" + peerDigest + "|" + sessionDigest)

box(K_g) = AES-256-GCM(linkKey, nonce=random12, plaintext=K_g,
                       aad = "dsh-mesh/vault/v2/wrap|" + depositId + "|" + g
                             + "|" + archiveSha + "|" + A.deviceId)

linkKey = HKDF-SHA256(
        ikm  = X25519(ephA, ephB),
        salt = helloNonce,
        info = "dsh-mesh/vault/v2/link|" + deviceIdA + "|" + deviceIdB,
        len  = 32)

sig = Ed25519_B("dsh-mesh/vault/v2/ack|" + depositId + "|" + g + "|" + archiveSha
                + "|" + challenge + "|" + expiresAt)
```

要点：

- `depositId` 是 B 创建托管项时生成的 16 B 随机值，不是会话 id；它只出现在账本、容器头、A 的索引和票据里，不泄露标题/路径。
- **B 不知道 `DEK`，也不保存 `K_g`。** 账本只存元数据，`K_g` 在每次开柜时由根密钥重新派生。B 重启后仍能放行；账本泄露不会泄露内容（没有 `DEK`），根密钥泄露才会。
- 根密钥丢失/重置 = 所有 A 侧容器永久不可读。B 提供“重置根密钥”，必须二次确认，效果等于让所有托管项作废，A 下次打开时回退完整拉取。根密钥被重置时账本必须整体作废，否则会发出一把解不开的旧钥匙；A 端表现为认证失败并回退。
- 链路密钥是纵深防御：DTLS 本身已加密，但包装后票据与具体链路实例绑定，录下旧链路的回包也无法在另一条链路或另一台设备上使用。
- **换钥只重写容器头**（约 120 B），`.dat` 不变。所以 20 MB 和 500 MB 的会话，换钥成本一样，不会因为“每开一次柜把整份档案重加密一遍”而把秒开拖成慢开。

### 5.2 为什么 A 不保管一把“长期开柜钥匙”

如果 A 把 `K_g` 存在本地钥匙串，磁盘被拿走就等于明文缓存；如果 B 在每次拉取时直接把长期密钥给 A，B 就再也收不回权限。本设计让 `K_g` 只在一次开柜的内存里存在，`DEK` 虽然留在 A 的容器头里，但被 `K_g` 包着：A 的静态数据始终是“没有 B 放行就打不开”的状态。代价是 B 必须在线才能开柜——但浏览远端会话本来就需要 B 在线，所以不损失主路径体验。

**诚实说明**：`DEK` 在多次开柜之间是固定的（否则每次都要重写整份 `.dat`）。如果攻击者在某次开柜时同时拿到了 `K_g` 和当时的容器头副本，他就拿到了 `DEK`，此后即使容器头换到 `K_{g+1}`，他仍能解开未变化的 `.dat`。但能在那个时刻读到 `K_g` 的攻击者，通常也能读到 A 内存里的明文/投影；而“只拿到磁盘、没有 `K_g`”的攻击者拿不到任何东西。若要求“旧钥匙连旧副本也解不开未来数据”，需要每次开柜全量重加密 `.dat`，代价是 O(档案大小) 的读写；默认不做，见 15.3。

## 6. 容器格式与磁盘布局

### 6.1 两个文件：`.hdr` 与 `.dat`

容器由一个可轮换的小头和一份不可变的大数据组成，换钥只动小头：

```text
<sha256>.hdr（约 120 B，每次开柜原子替换）
offset  size  field
0       4     "NCV2"
4       1     version = 2
5       4     gen（u32 BE）
9       1     priority（0=dialog，1=none）
10      16    depositId
26      32    archiveSha256
58      4     wrapBox 长度（固定 60）
62      ...   wrapBox = nonce(12) | tag(16) | cipher(DEK, 32 B)

<sha256>.dat（不可变，只在首次托管/刷新时写）
offset  size  field
0       4     "NCV2D"
4       1     version = 2
5       4     archiveBox 长度
9       ...   archiveBox = nonce(12) | tag(16) | cipher(archive)
...     4     projectionBox 长度（0 表示没有 sidecar）
...     ...   projectionBox = nonce(12) | tag(16) | cipher(gzip(JSON))
```

- `DEK` 固定，所以 `.dat` 只写一次；`K_g` 每代变化，只体现在 `.hdr` 的 `wrapBox` 里。20 MB 与 500 MB 的换钥成本都是“重写约 120 B + fsync”。
- 三个 box 各自独立 nonce、独立 AAD：
  - `wrap_g`：`"dsh-mesh/vault/v2/hdr|" + depositId + "|" + gen + "|" + archiveSha + "|" + peerDigest + "|" + sessionDigest`；
  - archive：`"dsh-mesh/vault/v2/data|archive|" + depositId + "|" + archiveSha + "|" + peerDigest + "|" + sessionDigest`；
  - projection：同上，域改为 `projection` 并带 `"|proj1"` 版本。
- `gen` 只在头的 AAD 里，不在档案的 AAD 里；所以换代不必重写 `.dat`，但改代次会让 `wrapBox` 解不开。改 `depositId`/`archiveSha` 会让 `.dat` 与本机对不上。
- `.hdr` 不加密，但它的字段被 `wrapBox` 的 AAD 认证；伪造 gen/depositId 会解包失败。头里只有随机 `depositId`、哈希、代次，没有标题、路径、明文。
- 一个托管项的 `.dat` 同时装 archive 与“投影 sidecar”（面板直接渲染的 items 的 gzip JSON）。sidecar 与 archive 在同一份 `.dat` 里一次写入，避免“档案换了、投影没换”的错配。
- 文件名：`SHA256("jlc\0" + peerDeviceId + "\0" + sessionId + "\0" + priority)`，与 rc.13 的 `safeKey` 一致，磁盘上看不到会话名；`.hdr`/`.dat` 共用前缀。
- 投影 sidecar 带格式版本与解码时的 `archiveSha`；版本不符或哈希不符就丢掉 sidecar，回退 native decode。
- 交换两个容器的 `.hdr`/`.dat`、或把旧 `.hdr` 配新 `.dat` 都会在 AAD/`archiveSha` 校验处失败，不会解出错内容。
- 首次托管或刷新时先写 `.dat` 再写 `.hdr`；如果恰好在两次 rename 之间崩溃，旧头配新数据（或反之）会在启动校验时整对删除，按需重拉。换钥只写 `.hdr`，不存在这个窗口。

### 6.2 A 侧布局

```text
$DSH_HOME/account-mesh/vault/
  index.json          0600  仅哈希键 → {depositId, gen, hdrBytes, datBytes, archiveSha, lastUsedAt}
  <sha256>.hdr        0600  可轮换头（gen + wrapBox）
  <sha256>.dat        0600  不可变数据（archive + sidecar）
  tmp/                0700  写临时文件，启动时清空
```

`index.json` 只用于启动 GC、LRU 与聚合计数，不含任何明文标识；打开会话时 A 直接用逻辑键重算文件名，**不依赖索引**。索引丢了就从 `.hdr` 重建（丢失 `lastUsedAt`，用文件 mtime 代替），无法认领的容器按老化清理即可，不影响已知会话的开柜。启动时：`.dat` 有而 `.hdr` 无视为孤儿删除；`.hdr` 的 `archiveSha` 与 `.dat` 不符时整对删除。

### 6.3 B 侧布局

```text
$DSH_HOME/account-mesh/vault/
  root.key            0600  32 B 根密钥
  ledger.json         0600  托管账本
  releases.json       0600  最近 N 次开柜审计（环形）
```

账本条目：

```json
{
  "depositId": "b64u-16B",
  "peer": "device-id-of-A",
  "sessionId": "session-...",
  "priority": "dialog",
  "archiveSha": "sha256(archive)",
  "size": 12345678,
  "fingerprint": { "bytes": 12345678, "mtimeMs": 1764000000000 },
  "confirmedGen": 3,
  "issuedGen": 3,
  "createdAt": 1764000000000,
  "lastUsedAt": 1764000300000,
  "revoked": false,
  "superseded": false
}
```

账本里的 `sessionId` 是 B 自己的会话标识，只用于 `stat`/查询会话是否还在；A 的 `.hdr`/`.dat` 里没有它，A 只认随机 `depositId`。同一 `(peer, sessionId, priority)` 的新 `prepare` 会创建新 `depositId`，旧条目标记 `superseded` 并在下一次清理时删除；`superseded` 条目与 `revoked` 一样拒绝开柜。A 用新容器原子替换旧文件。

## 7. 协议

### 7.1 首次拉取 = 托管（A 主动 `mesh_session_fetch`）

```text
A                                                B
|-- sessions/export/prepare -------------------->|
|<-- manifest + header + vault{depositId, gen=0, |
|     archiveSha, box(K_0), fingerprint} --------|
|-- sessions/export/block × N ------------------->|
|<-- mesh-bin 二进制块 ---------------------------|
|  组装 archive，校验 archiveSha                    |
|  生成 DEK；把 archive + sidecar 加密成 .dat        |
|  用 K_0 把 DEK 包进 .hdr；原子 rename             |
|  清零 K_0 / DEK                                   |
|  （gen 仍为 0，B 的 confirmedGen = 0）            |
```

- `vault` 字段只在 A 在 hello 里声明 `caps: ["vault2"]`、且 B 的 `vaultRelease != "deny"` 时返回；B 也只在 A 声明 `caps` 时创建账本条目。旧 A 完全无感。
- 首次托管不需要 `commit`：B 创建条目时 `confirmedGen = issuedGen = 0`，A 落盘成功即视为第 0 代当前态；落盘失败则 A 丢弃容器，B 的条目按 `vaultMaxAgeDays` 老化。
- `K_0` 用链路密钥包好；A 只用它把 `DEK` 包进 `.hdr`，随后清零。下次打开走 7.2，B 重新发放 `K_0` 并要求 A 立即换到 `K_1`。

### 7.2 热开柜（A 再次打开同一会话）

```text
A                                                B
| 读容器头：depositId, gen, archiveSha, priority   |
|-- vault/open {depositId, gen, challenge,        |
|               archiveSha, priority} -------------->|
|                                                | 1 链路已认证、B 信任 A
|                                                | 2 账本存在该 depositId 且 peer=A
|                                                | 3 gen ∈ {confirmedGen, issuedGen}
|                                                | 4 archiveSha/priority 与账本一致
|                                                | 5 未撤销、未过期
|                                                | 6 策略：auto 直接发；confirm 等 B 用户
|                                                | 7 派生 K_gen、K_{gen+1}，issuedGen=gen+1
|<-- open-ack {gen, fresh, fingerprint,          |
|      box(K_gen), next{gen+1, box(K_{gen+1})},   |
|      expiresAt, sig} --------------------------|
| 验签；解 box；用 K_gen 解包 DEK                |
| 用 DEK 解 sidecar（优先）或 archive（缺 sidecar） |
| 校验 AAD、sidecar 版本；解了 archive 才校验其 sha |
| 用 K_{gen+1} 重新包住 DEK → 重写 .hdr → fsync →  |
| rename                                          |
|-- vault/commit {depositId, gen: gen+1} -------->|
|                                                | confirmedGen = gen+1
| 清零 K_gen / K_{gen+1} / DEK，投影进内存 L0       |
```

- 正常路径网络字节 = 一次 `open` + 一次 `commit`，约 1 KB 量级；档案不重传。
- A 先解密，**把 `DEK` 重新包到 `K_{gen+1}` 并原子替换 `.hdr` 后**才 `commit`。提交失败（链路断）不影响本地已更新的头：下次 `open` 带 `gen+1`，B 的 `issuedGen` 已是 `gen+1`，允许重发并继续推进。
- 渲染优先用 sidecar：它有自己的 GCM tag，且 AAD 绑定 `archiveSha`；只有 sidecar 缺失/版本不符、或轨迹视图需要原始事件时才解 archive 并校验其 sha。两条路径都不会把未认证的字节渲染出来。
- 开柜回包带 `fresh`。`fresh=false` 时 A 仍然解密并展示（用户看的是自己本来就有权看的缓存），但打上“本地缓存 · 远端已更新”标记，并后台发起完整拉取替换；`fresh=null`（B 无法 stat 文件）按“未知”处理，live 会话默认后台刷新。
- 换钥只是把 32 B 的 `DEK` 用新 `K_{gen+1}` 重新包一遍、重写约 120 B 的 `.hdr`；无论档案多大都是同一成本。它换来的是上一代 `K_g` 在提交后立即失效（对当前磁盘而言）。

### 7.3 两阶段提交与崩溃恢复

B 的账本对每个托管项维护：

- `confirmedGen`：A 已确认落盘的最高代；
- `issuedGen`：B 已发放钥匙的最高代（通常 `confirmedGen` 或 `confirmedGen + 1`）。

允许的开柜代次只有 `{confirmedGen, issuedGen}`。其余一律 `gen-mismatch`。

| 崩溃点 | 磁盘状态 | 下次开柜 | 结果 |
| --- | --- | --- | --- |
| B 发完 open-ack，A 没收到 | A：`g`；B：`issued=g+1` | A 带 `g` | `g == confirmed`，B 重发 `K_g` 与 `K_{g+1}`，正常 |
| A 解密后、重写 `.hdr` 前崩 | A：`g`；B：`issued=g+1` | A 带 `g` | 同上 |
| A 重写 `.hdr` 并 rename 后、commit 前崩 | A：`g+1`；B：`confirmed=g` | A 带 `g+1` | `g+1 == issued`，B 重发 `K_{g+1}` 与 `K_{g+2}`，正常 |
| A 已 commit，但容器随后丢失 | A：无；B：`confirmed=g+1` | 无容器 | 走完整拉取，生成新 `depositId` |
| A 伪造 `g+2` | — | `g+2 > issued` | 拒绝，A 回退完整拉取 |

提交前旧代仍可重发一次，是为了崩溃恢复；提交后 `gen < confirmedGen` 的票据一律拒绝，录制的旧票据无法重放。`vault/commit` 同样校验 `depositId` 属于发起设备、`gen <= issuedGen`，不会替别的设备或更远的代次推进账本。

### 7.4 轮换与失效

- 每开一次柜前进一代；`K_g` 在 `commit` 后从 B 的可发放集合中消失（`gen < confirmedGen` 拒绝）。
- 重写 `.hdr` 失败（磁盘满、只读、掉电）时 A 不提交，保留旧头与旧代；下次可重试，不会出现“头是新代、B 认为是旧代”的错位。
- 需要强制全量轮换时，B 直接撤销该托管项（`revoked`），A 的旧代全部拒绝，回退完整拉取生成新 `depositId`。
- 根密钥重置使所有派生结果变化，所有托管项等同撤销。
- `.dat` 不变意味着旧 `K_g` 对**新的 `.hdr`** 无效，但“旧 `K_g` + 旧 `.hdr` 副本”仍能取出 `DEK`；这是 5.2 说明的取舍，默认不接受 O(档案大小) 的全量重加密。

### 7.5 撤销

| 触发 | 行为 |
| --- | --- |
| B 面板“撤销该设备托管” | 该 `peer` 的全部条目 `revoked=true`；A 下次开柜收到 `revoked`，删除本地容器并回退 |
| `mesh_peer_forget` / 公钥重绑 | 自动撤销该设备全部托管项 |
| B 删除会话 / 清空工作区 | B 在下次 `open` 发现会话已不存在时返回 `revoked` 并撤销；A 删除本地容器 |
| B 停止插件 / 卸载 | 根密钥与账本随 `$DSH_HOME` 保留；重新安装后仍可放行（如果账本还在），否则 A 回退 |
| A 面板“清空保险柜” | 只删 A 本地密文、索引与该会话的 L0/L2 投影，不通知 B；B 条目按老化清理 |

撤销是 B 的单方动作；A 不能撤销 B 侧的条目，只能清空自己的本地副本。

A 只在收到**确定性拒绝**（`revoked` / `unknown` / `peer-mismatch` / 容器认证失败）时删除本地容器回退完整拉取；链路断开、B 离线、用户取消等**暂时性失败**保留容器与投影，下次再试，避免一次网络抖动就丢掉缓存。

### 7.6 陈旧检测

B 用账本里的 `sessionId` 找到会话文件，在 `prepare` 与 `open` 时取 `{bytes, mtimeMs}` 指纹：

- 与账本记录一致 → `fresh: true`；
- 不一致 → `fresh: false`，`fingerprint` 返回新值，但**仍发放当前容器的钥匙**（A 有权看旧内容），由 A 决定是否后台刷新；
- B 没有可 stat 的落盘文件（纯 live/内存会话）→ `fresh: null`，A 对 live 会话默认后台刷新。

任何情况下都不会把 `fresh=false` 的容器标成最新；UI 文案与 `mesh_session_fetch` 返回值都如实标注。

### 7.7 严格模式（“验证码”式审批）

`vaultRelease: "confirm"` 时：

1. A 的 `vault/open` 到达 B，B 校验完账本后**挂起**该 RPC（不设应用层超时），在 B 的本地界面生成一条审批项：设备名、B 自己的会话标题、`depositId` 后 6 位、代次、请求时间；
2. B 的用户点“允许本次 / 本会话今日允许 / 始终允许此设备 / 拒绝”；
3. 只有 `POST /account-mesh/api/vault/pending`（B 的本地 `webServer` 路由，受现有浏览器信任围栏保护）能完成审批；mesh RPC、agent 工具、MCP 都没有审批入口；
4. 审批文案全部由 B 用自己的账本与会话标题渲染，**不渲染 A 传来的任何字符串**，防止 A 伪造“系统提示”做钓鱼；
5. A 的界面显示“等待对端确认”，用户可以取消，或点“改为完整拉取”；A 无法代替 B 点确认；
6. B 的待审批队列按 `depositId` 去重，同一托管项的重复请求只占一条（显示次数），避免 A 刷屏把真正的请求淹没；“本会话今日允许 / 始终允许此设备”是 B 本地保存的放行策略，不是发给 A 的钥匙。

默认 `auto`：B 对自己创建、发给已信任同账号设备的托管项自动放行，保持秒开；共享账号或演示机建议 `confirm`。

不要求 B 把验证码念给 A 输入——那会把安全建立在人肉搬运上。这里的“短信验证码”就是票据本身：单次、短效、绑定这次请求和这台设备，只是投递渠道换成了已认证的 mesh 通道。

## 8. 为什么 B 不会被 A 驱使去“变相解密”

这是需求里点名的问题。核心做法不是“给 B 加一个判断”，而是**让“代解密”这个接口根本不存在**。

| A 的尝试 | B 的实际反应 |
| --- | --- |
| 发一段密文让 B 解开 | 没有这种 op。`vault/open` 的入参只有 `depositId/gen/challenge/archiveSha/priority`，没有密文字段 |
| 伪造一个 `depositId` | B 只认自己账本里的条目；不存在 → `unknown`，不区分“不存在”和“无权” |
| 用别的设备身份申请 A 的托管项 | 账本绑定创建时的 `peerDeviceId`；身份不符 → `peer-mismatch` |
| 跳过代次、回放旧票据 | 只接受 `{confirmedGen, issuedGen}`；旧代、超前代一律拒绝；challenge 每次随机 |
| 篡改本地容器，希望 B 返回能解开的钥匙 | B 按账本派生，钥匙绑定 `archiveSha`；本地 AAD/GCM 先失败，A 直接丢弃 |
| 让 B 的 agent 批准 | 审批只在 B 的本地 UI 路由；工具/MCP/mesh 白名单里没有审批 op |
| 用 A 的字符串伪造审批界面 | 审批界面只渲染 B 本地账本与标题，不渲染 A 的入参 |
| 反复申请钥匙 | 每次开柜换一代，提交后旧代死亡；B 的 `releases.json` 记录谁在何时开了哪个 `depositId`，用户可查、可撤销 |
| 撤销后继续用缓存 | `revoked` 是硬状态；A 收到即删容器 |

**最坏情况分析**：假设 A 的插件被完全改写、A 的用户是恶意的——

- A 能拿到的极限 = B 主动托管给“这台设备”的那些会话的内容，而这些会话 A 本来就能通过 `mesh_session_read` / `mesh_session_fetch` 读到；
- A 拿不到 B 没有托管的会话、拿不到 B 的根密钥、拿不到“把任意密文变成明文”的服务、拿不到别的设备的托管项；
- A 能让 B 做的事只有“为已托管项发一把一次性钥匙”，且 B 可以随时撤销、可以改成人工确认。

因此 B 的“操作者”不会被 A 按在键盘上替他解密：B 只在自己定义的策略下，对已经决定共享给这台设备的缓存发钥匙；审批权、撤销权、根密钥都在 B 侧。

还要区分“A 的插件开柜”和“A 的 DSH/agent 拿到钥匙”：`K_g` 只进入 account-mesh 的 transfer 管线，`mesh_session_fetch` / `mesh_session_read` 只拿到投影后的 items；没有任何工具、路由或返回值把 `K_g`、`DEK` 或 `.hdr`/`.dat` 路径交给模型。插件内部能开柜，不等于 DSH 核心或 agent 持有钥匙——这正是需求里“不等同于本地 dsh 拿到钥匙打开本地文件”的落点。

## 9. 本地缓存分层与秒开

| 层 | 内容 | 生命周期 | 命中效果 |
| --- | --- | --- | --- |
| L0 | `transfer.cache`：已解码的 `items` / `dialogItems` | 进程内存，LRU 256 MiB | 同一进程内重开：不读盘、不解码、不联网 |
| L1 | `NCV2`（`.hdr` + `.dat`，archive + 投影 sidecar） | 跨重启，`vaultMaxBytes` LRU | 冷启动重开：一次开柜 RTT + 解 sidecar；sidecar 命中时连 archive 都不解 |
| L2 | 远端元数据（树、`sessions/index`、分页） | 进程内存 LRU（现有 `routes.js` 页缓存） | 列表与分页不重复拉取；不进 L1，避免把“浏览元数据”也变成持久化负担 |

打开会话的优先级：

```text
选择会话
  → L0 命中（当前进程内已解码、且刚校验过新鲜度）？直接渲染
  → L1 有容器？vault/open → 解包 DEK → 解 sidecar 渲染（sidecar 失效才解 archive）
                    → 后台按 fresh 决定是否刷新
  → 都没有？走现有 sessions/events 分页（立即出内容），同时按需触发 JLC 完整拉取并托管
```

- “JLC 拉取完整会话”不再只是一个按钮：当 JLC 可用且用户打开一个尚未托管的会话时，Host 可以自动发起一次拉取（后台、可取消），完成后写入 L1；首屏仍由分页保证。这样“托管”是使用过程的副产物，而不是要用户记得点按钮。
- 投影 sidecar 让冷启动的“解码”也省掉；它和 archive 用同一个 `DEK`，写在同一个 `.dat` 里，换钥只重写 `.hdr`。sidecar 命中时只解它（几 MB），20 MB/500 MB 的 archive 都不碰；只有轨迹视图需要原始事件、或 sidecar 版本/哈希不符时才解 archive 并重建。
- 性能预算（20 MB archive，带 sidecar，LAN，Apple silicon）：

| 阶段 | 预算 |
| --- | --- |
| `open` + `commit` 网络 | ≤ 2 KB，≤ 1 RTT |
| 用 `K_g` 解包 `DEK` | < 1 ms |
| sidecar 解密 + gzip 解压 | ≤ 20 ms |
| 换钥（重写 `.hdr` + fsync） | ≤ 5 ms |
| 冷启动首屏合计（sidecar 命中） | ≤ 300 ms |
| sidecar 失效时额外解 archive | ≤ 40 ms |

- 同一 `(peer, session, priority)` 的并发开柜在 A 侧合并为一次（single-flight），避免两个请求各换一代、互相覆盖 `.hdr`。
- 容量：`archive + sidecar` 计入 `vaultMaxBytes`，按 `lastUsedAt` LRU；写满时淘汰最久未用项。淘汰不是请求门控，不影响任何在途模型调用。

## 10. 落盘位置、生命周期与迁移

### 10.1 位置的取舍

需求笔记写的是“目标本地机器上工作空间内托管”。本设计把“工作空间”解释为 **DSH 的私有数据空间** `$DSH_HOME/account-mesh/vault/`，不放进用户项目 cwd：

| 放进项目工作区的问题 | 私有数据目录的好处 |
| --- | --- |
| 会被 `git add`、网盘同步、Time Machine 备份带走密文 | 不进入版本库与常规同步面 |
| DSH 的 workspace 索引与 agent 文件读取会看到它 | 面板不提供读取入口，agent 也没有路径 |
| 用户手动浏览/复制，违背“不会让用户轻易拿到” | 目录 0700、文件 0600、随机文件名 |

`vaultDir` 可以显式指到别处（例如加密外置盘）；文档与 UI 会标注“不要指向 git 仓库或同步目录”。即使容器被复制到另一台设备，开柜仍绑定原设备身份，复制品打不开——这既是限制也是防泄露。

### 10.2 生命周期变化（相对 rc.13）

| 事件 | rc.13 | 本设计 |
| --- | --- | --- |
| 正常关闭 DSH | 删除全部 `.ncv` | **保留** `.hdr`/`.dat` 与索引；清零内存钥匙 |
| 进程启动 | 删除全部 `.ncv` | 只清 `tmp/`、孤儿/损坏的 `.hdr`/`.dat`、旧版 `.ncv`；按 `vaultMaxAgeDays` 老化 |
| 崩溃 | 残留密文下次删除 | 残留密文继续可用；按两阶段提交恢复代次 |
| 清空保险柜 | 删全部 | 删 `.hdr` + `.dat` + `index.json`；B 侧条目保留到老化/撤销 |
| 升级 | — | `.ncv`（v1）直接删除（旧密钥本来已丢失，重拉即可） |

这是行为变化，设置页文案必须改：从“关闭 DSH 后清除”改为“**跨重启保留密文；没有远端放行无法打开；可随时清空**”。`vaultMode: "session"` 保留 rc.13 的进程级行为给需要的人。

### 10.3 启动顺序

1. `mkdir vault/`（0700），清 `tmp/`；
2. 载入/生成 `root.key`（B 角色，两者都可能有）；
3. 读账本与索引；账本损坏就改名保留并重建（不会丢 A 的密文，只是需要重新拉取才能建新条目）；
4. 校验索引与磁盘文件，删孤儿与坏头；
5. 按 `vaultMaxAgeDays` 删除长期未用项；
6. 注册 `exit` 时只做同步索引落盘，不再删密文。

## 11. 配置

```yaml
- id: account-mesh
  config:
    vaultMode: hosted          # hosted：跨重启托管；session：rc.13 的进程级行为
    vaultEnabled: true
    vaultMaxBytes: 268435456   # 容器 + sidecar 上限，LRU
    vaultMaxAgeDays: 30        # 长期未开柜的老化；不是请求门控
    vaultRelease: auto         # B 侧策略：auto | confirm | deny
    vaultReleaseTtlMs: 600000  # 票据有效期（密码学授权窗口，不是操作超时）
    vaultPassTtlMs: 0          # 离线通行证，0=关闭；见第 15 节
    vaultDir: ''               # 默认 $DSH_HOME/account-mesh/vault
```

与仓库“不设应用层超时 / 不做用量门控”的一致性：

- `vaultReleaseTtlMs` 是**票据的有效期**（类似短信验证码 5 分钟内有效），过期只意味着这次授权作废、需要重新申请；它不中止在途模型请求，也不是“等太久就失败”的请求超时；
- `vaultMaxBytes` / `vaultMaxAgeDays` 是缓存容量与保留期，只影响本地淘汰，不累计用量、不因“缓存太大”暂停任何请求；
- `vault/open` 的 RPC 本身没有 deadline；等待对端确认、等待用户取消都由用户或真实错误结束。

## 12. 接口

### 12.1 mesh RPC（新增白名单）

| op | 方向 | 入参 | 返回 |
| --- | --- | --- | --- |
| `vault/status` | A→B | — | `{enabled, mode, release, entries, bytes}`，聚合，不含 `depositId` 列表 |
| `vault/open` | A→B | `{depositId, gen, challenge, archiveSha, priority}` | 见 7.2；`revoked/unknown/peer-mismatch/gen-mismatch/denied/disabled` 用统一错误 |
| `vault/commit` | A→B | `{depositId, gen}` | `{ok, gen}` |

说明：

- 对会话与工作区仍然只读：不写会话、不改远端文件；新增的 vault op 只改 B 自己的托管账本/审计，不改会话内容。`vault/open` 不接收密文、不返回明文。
- `sessions/export/prepare` 的返回增加可选 `vault` 字段；旧对端忽略、旧 A 不声明 `caps` 就不带。
- `hello` / `hello-ack` 增加 `caps: ["vault2"]` 与 X25519 公钥 `xpk`；**原有 `sig` 的签名载荷一字不改**，另加 `xsig`（同一 Ed25519 密钥对 `HELLO_CTX|nonce|deviceId|xpk` 的签名）。旧版本忽略多出来的字段、仍能验证原有 `sig`，不会因为升级把老对端踢下线；新版本只在 `caps` 含 `vault2` 时启用托管。
- `vault/open` 在 B 未启用托管时返回 `disabled`；A 收到 `disabled` 不删容器，只是本次回退分页/拉取。
- 审批、撤销、重置根密钥**不在** RPC 白名单内。

## 15. 取舍与开放问题

1. **默认 `auto` 还是 `confirm`**：`auto` 保住秒开，语义上等于“同账号已信任设备可读的会话，也允许开缓存”；`confirm` 更稳，但每次都要 B 的用户在场。建议个人自用默认 `auto`，共享/演示机默认 `confirm`。
2. **离线通行证（默认关闭）**：`vaultPassTtlMs > 0` 时，B 签发一张 `{depositId, gen, expiresAt, passBox}` 的通行证，其中 `passBox` 是把 `K_g` 用 **A 的持久设备公钥**（不是链路临时密钥）包好的结果；A 存在 `vault/passes/`（0600，设备绑定），TTL 内 B 离线也能开。它让“B 掉线时仍可看缓存”成立，但等价于在 A 的盘上放了一把有时限的钥匙——只比“cookie 目录”强一点。默认 0，不推荐在共享账号开启。
3. **为什么不每次全量重加密 `.dat`**：全量重加密能让“旧钥匙 + 旧头副本”也解不开未来数据，但每次开柜都要 O(档案大小) 的读写，500 MB 会话会从秒开变成秒级到十秒级，且显著增加 SSD 写入。默认用“固定 `DEK` + 轮换 `K_g`”，把换钥成本压到约 120 B；如果用户明确要求更高等级，可以后续加 `vaultRekey: "full"` 的可选模式，而不是做成默认。
4. **为什么不做成“一个大容器”**：单文件要处理并发写、局部更新、损坏放大，且一个坏块毁全部；按 `(peer, session, priority)` 一对 `.hdr`/`.dat` 可以用 rename 原子替换，坏一个只回退一个会话。
5. **为什么不让 B 在发送前就加密**：那会改动已验收的 JLC 块协议与 manifest；A 侧落盘前加密不改变“B 持有 `K_g`、A 才能取 `DEK`”的安全性质，改动面最小。等 P3 若要把“密文过线”也纳入，再评估。
6. **A 是否缓存 `sessions/index` / 分页到 L1**：默认不做。元数据小、变化快，放内存 L2 足够；持久化会放大“陈旧列表”的风险。
7. **`priority` 是否合并**：当前按 `(peer, session, priority)` 分开存，语义最保守；若确认 JLC 的 `priority` 只影响块顺序、不影响档案内容，可合并成一份省空间，需 native 侧确认后再改。
8. **工作区路径**：如果确实需要“容器跟着项目/移动硬盘走”，用 `vaultDir` 显式指定，并在 UI 警告 git/同步风险；不建议做成默认。

## 17. 向后兼容：通用对象容器（未来电台 / 小游戏）

托管保险柜不能把“JLC 会话 archive”写死在协议和文件格式里。未来电台的音频分片、小游戏的素材包/状态快照，都应当是同一种**托管对象**，只是 `kind` 不同。

### 17.1 逻辑对象

```text
objectKey = (peerDeviceId, kind, objectId, variant)
```

| kind | objectId | variant | 典型成员 |
| --- | --- | --- | --- |
| `session` | 远端 session id | `dialog` / `none` | `archive`, `projection` |
| `radio` | 电台/频道 id | `segment:<n>` | `audio-opus`, `playlist`, `metadata` |
| `game` | 游戏/房间 id | `asset-pack` / `state` | `asset-index`, `blob`, `snapshot` |
| 未来 | 由插件定义 | 由插件定义 | 由插件定义 |

- `kind`、`objectId`、`variant` 只用于**本地索引和 B 的账本**；A 的 `.hdr`/`.dat` 里只存哈希、随机 `depositId`、内容哈希与成员类型，不存标题/路径/原始 id。
- 一个对象可以由多个成员组成；成员各自独立 GCM nonce/tag，但共享同一 `DEK`（同一对象换钥只动 `.hdr`）。
- 成员表放在 `.dat` 开头：`count` + `{typeLen,type,boxLen,box}`。未知成员类型可以原样保留、跳过解密，不因未来新增类型破坏旧读端。
- 内容类型带版本：`session/archive@1`、`session/projection@1`、`radio/audio-opus@1`、`game/state@1`。读取端遇到不认识的 `kind/type` 只跳过该成员，不把对象标成损坏。
- 电台/小游戏可能产生大量小分片：默认每个 `objectKey` 一个容器；分片可独立 `depositId`，由业务侧索引组合。不要把所有分片塞进一个无限增长的单文件，否则换钥/淘汰/并发写都会退化。
- 如确实需要 `.asar` 式单文件虚拟文件系统，应作为**上层打包**：一个容器内多个成员 + 索引成员；底层仍是 NCV2 对象，不改变换钥和授权模型。

### 17.2 协议泛化

`vault/open` / `vault/commit` 只认：

```text
depositId, gen, challenge, contentHash, kind, objectIdHash, variant
```

B 的账本按 `depositId` 记录 `peer、kind、objectId、variant、contentHash、confirmedGen、issuedGen、revoked、superseded`。B 不因为 `kind` 不同而接受“密文解密”请求；仍然只按账本派生钥匙。

A 的本地索引同样按 `hash(peer|kind|objectId|variant)` 定位；索引里只保留哈希、`depositId`、代次、路径和字节数。

### 17.3 权限与保留

- 每个 `kind` 可以有自己的 host root 子目录（如 `<root>/session/...`、`<root>/radio/...`、`<root>/game/...`），但根仍由本机用户选择。
- B 的保留策略可按 `kind` 覆盖：例如电台分片 24 小时、会话 30 天、游戏素材 7 天；默认沿用 `vaultRetentionDays`。
- 本机删除内容时按 `peer` 或 `peer+kind` 删除；删除是路径重设的前置条件。
- 远端撤销时按 `depositId`/`peer` 撤销；A 下一次打开收到 `revoked` 后删除对应本地容器，其他 `kind` 不受影响。

### 17.4 当前实现边界

- 当前 rc.14 的宿主数据结构已经保留 `kind/objectId/variant` 字段的扩展位；首个实现只注册 `session`，`radio`/`game` 的成员类型和根目录分流在后续插件中接入。
- `.dat` 成员表现在是 `archive + projection` 两项；新增成员不需要改 `.hdr` 换钥逻辑，只需在写入时增加成员并保持旧成员类型可跳过。
- 单文件 `.asar` 虚拟文件系统不做默认；优先保证按对象淘汰、原子换钥和故障隔离。

### 18.2 与设计稿的刻意差异

- 没有实现 X25519 链路包裹：票据只通过现有 DTLS + Ed25519 双向认证的 RPC 通道传输；不在磁盘/日志留下钥匙。额外链路包裹留作 hardening。
- `vaultRelease: confirm` 暂未接本地审批 UI；当前返回 `confirmation-required`，调用方回退完整拉取。目录选择的倒计时审批已经实现。
- 默认 `deletion` 不自动发生：过期只影响开柜，容器保留；只有远端 `revoked` 或本机用户删除才清。
- `.dat` 仍是 `archive + projection` 两个成员，但格式用成员表边界预留；未来 radio/game 加成员不需要改 `.hdr` 换钥。
- 没有强制单文件 `.asar` 虚拟文件系统；按对象 `.hdr/.dat` 更容易原子换钥、淘汰和隔离损坏。
