# 面向对象/字符结构的二进制扁平传输压缩方案

下面给出一个完整、可落地的方案，覆盖你提出的所有要点，并补齐了 JSON 数组、长字符串、转义序列、布尔/负数、数字键映射等遗漏部分。整体设计目标是：**结构扁平化 + 语义化下标 + 混合编码（霍夫曼 + 直读字面量）**。

---

## 一、总体设计原则

1. **不用 JSON 文本传输**，改用二进制字节流。
2. **对象压缩为扁平数组**：`[键表, 值表, 类型标记表(可选)]`，下标即语义。
3. **霍夫曼编码只作用于"键"和"短字符串值"**，且需满足"高频短码、低频直读"。
4. **数字、布尔、负数、超长数字 ID 走直读通道**，不参与霍夫曼编码空间。
5. **长字符串/转义序列走独立字面量通道**，避免污染编码表。
6. **数组（JSON array）单独用类型标记**，不嵌套，用"长度前缀 + 元素流"扁平展开。

---

## 二、数据模型：语义化扁平数组

一个对象 `{k1:v1, k2:v2, ...}` 序列化为：

```
[ 键表, 值表, 类型表 ]
```

- **位置 0 — 键表**：`[k1, k2, ...]`，元素为字符串或整数（整数键需经映射表，见第六节）。
- **位置 1 — 值表**：`[v1, v2, ...]`，与键表一一对应。
- **位置 2 — 类型表（可选）**：每个值一个类型标记，用于区分 `string / number / bool / null / array / object-ref / literal`。若值表元素自带类型前缀字节，可省略此表。

> 你举的例子 `{a:1,...,e:5}` → `[[a,b,c,d,e],[1,2,3,4,5]]`，就是省略了类型表（全为标量）的最简形态。

**类型标记字节**（1 字节）：

| 码 | 含义 |
|---|---|
| 0x00 | null |
| 0x01 | false |
| 0x02 | true |
| 0x03 | 小整数（-1..-128 或 0..127，1 字节补码） |
| 0x04 | 中整数（2/4/8 字节，后跟长度） |
| 0x05 | 大数字字面量（如 ID，见第五节） |
| 0x06 | 霍夫曼编码字符串 |
| 0x07 | 字面量字符串（长串/转义串） |
| 0x08 | 数组（后跟长度 + 扁平元素流） |
| 0x09 | 嵌套对象（递归为子扁平数组） |

---

## 三、键的霍夫曼编码机

### 3.1 建表流程

1. **收集**：一轮数据中所有出现的键字符串，统计频次。
2. **过滤**：只对"出现 ≥ 2 次"或"频次 × 长度"超过阈值的键建码；**只出现一次的长键不建码**，走直读（见 3.3）。
3. **构建霍夫曼树**，生成码字（前缀码，无歧义）。
4. **码表随包传输**：`[码字数, (键字节长度, 键字节, 码位长, 码位), ...]`，用变长整数编码。

### 3.2 键的三种表示形态

传输时键位置是一个"联合体"，首字节为**键标记**：

| 标记 | 形态 | 说明 |
|---|---|---|
| 0x10 | 霍夫曼码 | 后跟码位（按位打包），解码时查表 |
| 0x11 | 直读字符串 | 后跟变长长度 + UTF-8 字节（低频长键，如 `peer-at`） |
| 0x12 | 数字键映射 | 后跟映射表索引（见第六节） |

你给的 `[1,32,'peer-at',91]` 形态即：`1` 和 `32` 是霍夫曼码字（十进制示意），`'peer-at'` 是直读，`91` 是另一码字——**混合出现在同一位置槽中**，由键标记字节区分。

### 3.3 位打包

霍夫曼码字按 **MSB-first** 连续写入一个比特流，与直读/数字标记之间用字节对齐边界隔开（每个槽先写标记字节，再写内容），保证可解码。

---

## 四、值的编码通道

值表每个元素 = **1 字节类型标记 + 载荷**：

- **布尔/null**：仅标记字节，无载荷（`0x00/0x01/0x02`）。你强调的 `1 0 -1` 作为布尔/负数表示，落在 `0x01/0x00/0x03`，**不进入霍夫曼码空间**。
- **小整数**：标记 `0x03` + 1 字节补码（覆盖 -128..127）。
- **中整数**：标记 `0x04` + 长度字节(2/4/8) + 大端补码。
- **大数字字面量**：标记 `0x05` + 变长长度 + ASCII 数字串（如 `8902349230841`）。**规则**：位数 > 15 或绝对值 > 2^53 的数字一律走此通道，判定为"合法数字形态、不可能是霍夫曼码"，直读。
- **霍夫曼字符串**：标记 `0x06` + 码位流（短、高频值）。
- **字面量字符串**：标记 `0x07` + 变长长度 + UTF-8 字节（长串/含转义，见第七节）。
- **数组**：标记 `0x08` + 元素个数(变长) + 各元素"类型标记+载荷"顺序流（**扁平展开，不嵌套括号**）。
- **嵌套对象**：标记 `0x09` + 子扁平数组（键表/值表/类型表三段），递归但每层仍是扁平三段式。

---

## 五、数字与霍夫曼编码空间的隔离规则（关键）

为防止"数字被误读为霍夫曼码"，定义**直读数字白名单**：

1. 布尔/负数哨兵：`0, 1, -1` 固定映射为 null/true/false 或小整数，**永不参与霍夫曼**。
2. 位数 ≥ 16 的整数（如 ID `8902349230841`）→ 大数字字面量通道。
3. 绝对值 > 2^53 的浮点/整数 → 字面量通道。
4. 其余数字一律带 `0x03/0x04` 类型标记，**标记字节本身就在霍夫曼码空间之外**，解码器先读标记再分流，从根本上避免歧义。

> 核心思想：**类型标记字节是"逃逸前缀"**，霍夫曼码流只出现在 `0x06/0x10` 标记之后，二者物理隔离。

---

## 六、数字键的映射表

若对象键是数字（如 `{1:"x", 2:"y"}`），**必须经映射表**，因为裸数字可能与霍夫曼码字冲突：

- 包级维护 `数字键映射表`：`[ (数字, 短ID), ... ]`，短ID 为 1 字节序号。
- 键槽写 `0x12 + 短ID`，解码时反查回原数字。
- 映射表本身用变长整数编码，随包头发送。

---

## 七、长字符串与转义序列处理

- **长度阈值**：UTF-8 字节数 > 64 或含 `\uXXXX`/`\n`/`\"` 等转义 → 走 `0x07` 字面量通道，**原样存 UTF-8，不做 JSON 转义**（二进制流无需转义）。
- **短串且高频** → `0x06` 霍夫曼。
- 字面量通道可选用**可选轻量压缩**（如 LZ4 块）标记 `0x07 0x01` 表示已压缩，`0x07 0x00` 表示裸存，兼顾长文本。

---

## 八、JSON 数组的扁平化

JSON 数组 `[a, b, c]` 序列化为：

```
0x08 | 元素数(变长) | elem1(标记+载荷) | elem2 | elem3
```

- 元素若是对象 → 该元素内是 `0x09 + 子三段式`，**不产生嵌套括号**，只是逻辑递归、物理连续。
- 元素若是数组 → 再次 `0x08`，但整体仍是"长度前缀 + 顺序流"，可流式解析，栈深度 = 逻辑嵌套深度，内存扁平。

---

## 九、完整包结构（二进制帧）

```
[魔数 2B][版本 1B]
[数字键映射表长度 + 表]
[霍夫曼码表长度 + 表]
[顶层类型标记 1B]
[顶层载荷：扁平三段式或数组流]
[CRC32 4B]
```

所有长度用**变长整数（LEB128 风格）**，减少小值开销。

---

## 十、编解码流程

**编码**：
1. 遍历对象树，收集键/短串频次 → 建霍夫曼表（过滤低频长键）。
2. 扁平化：对象→三段式，数组→长度流，长串/大数字→字面量通道。
3. 每个槽写"标记字节 + 载荷"，霍夫曼码位打包。
4. 写映射表、码表、CRC，输出字节流。

**解码**：
1. 读魔数/版本/表。
2. 读顶层标记分流。
3. 对每个槽：先读标记 → 按标记查霍夫曼表 / 直读 / 数字映射 / 递归数组。
4. 重建对象/数组，校验 CRC。

---

## 十一、与纯 JSON 的对比（你关心的收益）

| 项 | JSON | 本方案 |
|---|---|---|
| 键重复 | 每处全写 `"peer-at"` | 高频键 1 个短码字 |
| 结构符号 | `{ } [ ] : , "` 大量 | 仅标记字节 + 长度前缀 |
| 数字 | 文本每位 1 字节 | 小整数 2 字节，大数按需 |
| 转义 | `\"` `\uXXXX` 膨胀 | 二进制裸存，零转义 |
| 数组 | 嵌套括号 | 长度前缀扁平流 |

典型对象体积可降 **50%–80%**（取决于键重复度与字符串长度）。

---

## 十二、边界与扩展

- **只出现一次的键**：按你要求不建码，`0x11` 直读，避免码表膨胀。
- **空对象/空数组**：键表长度 0 / 元素数 0，仅标记字节。
- **浮点**：`0x04` 后跟 4/8 字节 IEEE754，标记区分 int/float（可用 `0x04` 子码）。
- **版本协商**：版本字节允许后续加入字典压缩、列式编码等扩展而不破坏旧解码器。

以上即完整方案：**扁平语义数组 + 类型标记逃逸 + 霍夫曼仅覆盖高频键/短串 + 数字/布尔/长串/数组各自独立通道 + 二进制无转义帧**，可直接作为编解码器规范实现。

# 关于 dsh 记录会话使用的 jsonl格式

DSH（DeepSeek Harness）的会话日志虽然名义上是 JSONL 格式，但**实际落盘时默认是经过 Zstandard 压缩的，并非可直接阅读的纯文本**。它采用“逻辑上是 JSONL、物理上是多帧 zstd 拼接”的设计，目的是在保留事件级可追溯性的同时，大幅降低流式增量事件带来的存储开销。

### 存储位置与物理形态

会话文件路径通常为 `<home>/sessions/<project-dir>/<session-dir>/session.jsonl.zstd`，其中 `home` 默认为 `$DSH_HOME` 或 `~/.dsh`。

物理编码是**多个独立 Zstandard 帧的拼接**：第一帧只包含 header 行，之后每个持久追加批次对应一帧。因此，直接用文本编辑器打开 `.zstd` 文件是看不到内容的，必须先解压才能得到逐行的 JSONL。如果配置为 `compression: none`，则文件变为纯文本的 `session.jsonl`，可直接按行读取。

### 逻辑行结构

解压后，每一行是一个 JSON 事件记录。第一行是**不可变的会话头**（`type: "session"`），包含会话 id、cwd、创建时间、agent 预设等元信息。后续每一行是一条存储记录，可以是原样的 `SessionEvent` JSON，也可以是经过打包的 chunk 行。

常见的核心事件类型包括：

*   **`session`**：会话头，仅首行出现。
*   **`request/header`**：记录本次请求的模型路由信息（provider、model）。
*   **`assistant/message`**：助手消息，其 `data.usage` 字段包含 token 用量统计。
*   **`tool/call`**：工具调用记录。
*   **`user/message`**：用户消息。

此外还有 `step/start`、`step/end`、`turn/start`、`turn/end`、`approval/*` 等事件，用于支撑完整的会话重建。

### 关键优化：打包分片行

DSH 日志中会产生大量 `assistant/chunk` 增量事件（流式输出的 token 碎片）。如果每个碎片都单独存一行 JSON，重复的封装字段开销可能比载荷本身还大。因此默认启用 `packChunks`：将**至少 3 个连续、同属一个块的 chunk 事件**合并为一行打包记录（如 `text-chunks`、`reasoning-chunks`、`tool-call-chunks`）。这一优化在真实编程会话中实测可使逻辑日志**体积缩小约 60%**。读取时该过程是无损的，解码后会精确重建每个原始事件的 `seq` 和 `time`，且读取端对打包、非打包及混合布局完全透明。

### 与你先前压缩方案的关系

你之前设计的方案是面向“对象/字符结构”的通用二进制扁平化压缩，而 DSH 的 JSONL 是**事件日志**形态：每行是一个独立的事件对象，行与行之间是追加关系而非键值对应关系。两者场景不同——你的方案更适合结构化数据的紧凑序列化，而 DSH 的选择优先保证了事件流的可逐条回放、崩溃恢复和增量写入能力，压缩主要依赖 zstd 帧和 chunk 打包，而非对事件 JSON 本身做字段级的霍夫曼编码。如果你的目标是将 DSH 的 JSONL 事件流进一步压缩，可以考虑对解压后的 JSON 行应用你方案中的“键表+值表”扁平化，但需注意保留 `seq` 连续性和 `sourceEventSeqs` 等引用字段的语义完整性。

## 一、为什么字段名层面是最佳靶场

JSONL 的本质是**每行一个结构高度同构的 JSON 对象**。事件日志尤其如此：几百上千行里反复出现同一批键：

```
"type" "seq" "time" "data" "session_id" "role" "content" "tool" "usage" ...
```

这恰好命中你方案的两个核心假设：

1. **键高度重复** → 霍夫曼建表收益极大。一个 `"session_id"`（12 字符含引号）在 JSON 里每行占 12+ 字节，压成 1 个短码字，几千行就是几万字节的节省。
2. **键表可下沉为"包级共享表"** → 你原设计是每个对象带 `[键表,值表]`。对 JSONL，更优的做法是**整个文件共用一张键表**（因为所有行同构），每行只需传"值表 + 键表索引序列"。这把键表的重复开销摊到零。

这比普通对象压缩收益更高，因为普通对象是一次性的，JSONL 是同构多行，键表摊销效应极强。

---

## 二、值层面的机会与陷阱

### 机会
- **`type` 字段**：枚举值（`assistant/message`、`tool/call`、`step/start`…）→ 完美霍夫曼，几十个固定值。
- **`role`、`model`、`provider`**：低基数枚举 → 霍夫曼。
- **`seq`、`time`**：单调递增 → 用**差分编码 + 变长整数**（你方案里的 LEB128）比霍夫曼更好，因为霍夫曼对单调数列无意义，差分后才接近小整数分布。
- **`usage` 里的 token 数**：小整数 → 直读通道。

### 陷阱（必须处理）
1. **`content`、`reasoning` 这类长文本**：这是日志体积的大头，但**几乎不重复**，霍夫曼完全无效。必须走你的 `0x07 字面量通道`，甚至叠加 zstd/LZ4。**不要试图对自由文本建霍夫曼**——码表会爆炸且无收益。
2. **`tool` 参数、嵌套 `data`**：结构不规则，基数高。适合走"嵌套对象递归扁平三段式"，但键表不宜全局共享，应**按事件类型分桶建表**（`assistant/message` 一套表、`tool/call` 一套表）。
3. **`session_id`、`cwd`、时间戳字符串**：长且每行重复同值 → 用**字典/引用表**（首行定义，后续行只传索引），比霍夫曼更省。这其实是你"数字键映射表"思想的推广：**任何高重复长值都该做值字典，而非霍夫曼**。

---

## 三、JSONL 特有的关键约束：行独立性

这是你方案面对 JSONL 时**最重要的一条**，普通对象压缩不会遇到：

> **JSONL 的每一行在语义上是独立、可单独解析的事件。** 流式写入、崩溃恢复、按行 `tail`、按 `seq` 跳转回放，都依赖"任意一行可脱离上下文解析"。

如果你的压缩把**跨行共享的键表/码表放在文件头**，那么：
- 单行不再自包含 → 破坏 `tail` 和断点恢复。
- 文件头损坏 → 整个文件不可解。
- 无法追加写（新事件可能引入新键，要回改头部表）。

**解决思路（推荐）：分块自包含（chunked frames）**

把 JSONL 切成固定大小的**块**（如每 256 行或每 64KB 逻辑数据一块），每块**自带键表 + 霍夫曼码表 + 值字典**：

```
[块头: 键表, 码表, 值字典]
[行1: 键索引序列 + 值流]
[行2: ...]
...
[块尾: CRC]
```

这样：
- 块内摊薄表开销（256 行共享一张表，摊销极佳）；
- 块间独立，坏一块不影响其他块，可 `tail` 最后一块、可并行解压；
- 追加写只需开新块，不回改旧块。

这正好对应 DSH 用"多帧 zstd 拼接"的动机——**你是在用"多块自包含的霍夫曼扁平数组"做同一件事，但粒度更细、字段级收益更高**。

---

## 四、和 zstd 的关系：不是二选一，是分层

DSH 现在用 zstd 帧 + chunk 打包，本质是**通用字节级压缩**。你的方案是**结构级压缩**。两者正交，正确做法是叠加：

```
JSONL 行
  → 你的方案（键表+霍夫曼+差分+值字典+扁平数组）  ← 结构冗余消除
  → zstd（每块或整文件）                          ← 残余字节冗余消除
```

实测经验：结构级压缩先做掉 40–60% 的"字段名+结构符+枚举"冗余后，zstd 再压剩下的文本，**总压缩率通常优于单用 zstd**，因为 zstd 对"重复键名字符串"的字典匹配不如显式键表干净（zstd 有 window 限制，跨大文件的长距离重复匹配不到）。

反过来，如果只做你的方案不做 zstd，长文本（`content`）部分会留下大量冗余。所以**两者都要**。

---

## 五、还要注意的坑

1. **`seq` 连续性与引用字段**：`sourceEventSeqs`、`parentId` 这类跨行引用，压缩时必须保持数值语义不变（别把 seq 也霍夫曼了，用差分+变长整数）。解压后必须能精确重建原始 `seq/time`。
2. **chunk 打包兼容**：DSH 的 `text-chunks` 打包行本身就是"数组形态"，正好可套用你方案的 `0x08 数组流`。解包逻辑要在解码后执行。
3. **未知字段/版本演进**：新事件类型可能带来新键。块内键表要允许"本块新增键"，用 `0x11 直读`兜底，不强制进码表——这正好用上你"低频长键不建码、直读"的规则。
4. **浮点与科学计数法数字**：JSON 里 `1e10`、`0.5` 要归一化后再判断走小整数还是字面量，别被文本形态骗了。
5. **Unicode 转义**：JSONL 里 `\uXXXX` 解压后若还原成原始 UTF-8，体积可能变化；建议**编码前先做一次 JSON 解析再重新序列化到你的二进制**，避免转义残留。

## 六、一句话总结

**JSONL 是你这套霍夫曼数组压缩的"理想输入"——同构多行让键表摊销到极致、枚举值霍夫曼收益高、差分编码天然适配 seq/time；但必须按"块级自包含"改造以保住行独立性，值层面要区分"枚举/数字走结构压缩、长文本走字面量+zstd"，且与 zstd 分层叠加而非替代。** 直接对整文件建全局霍夫曼表是不可行的（破坏追加与恢复），这是 JSONL 与普通单对象压缩最大的不同。

## 一、核心约束：进度码必须"可独立定位"

接收端要产生进度事件，前提是**它在收到进度码时还没解完整个流**。所以进度码不能埋在霍夫曼比特流里（那要先解前半段才能读它），也不能放在"长度前缀之后"（长度未知时读不到）。可行的做法是**旁路进度通道（sideband）**：

```
[帧头: 总长/块数/进度槽数量]
[进度槽表: 固定偏移数组]      ← 接收端先读这个
[数据体: 块1][块2][块3]...
```

进度码不混进数据体，而是**数据体按块切分，每块开头一个固定 4 字节进度码**。接收端可以按"块边界"跳读，不必解块内容就能拿到进度。

---

## 二、两种落地形态

### 形态 A：块内前缀（推荐，最简单）

每块固定结构：

```
[块进度码 4B][块长度 4B][块数据...]
```

- 块数据是任意压缩产物（你的霍夫曼扁平数组或 zstd 帧）。
- 接收端循环：读 4B 进度码 → 发进度事件 → 读 4B 长度 → 读块数据 → 解块。
- **进度码与块数据物理分离**，解码器无需理解块内编码就能读进度。
- 你原方案的"数组固定位置"对应为：**块索引 = 数组下标，进度码 = 该下标处的固定字段**，语义清晰。

进度码内容建议打包成一个 32 位整数：

```
高 8 位: 块序号（0..255，超过则用扩展块头）
低 24 位: 已完成百分比 × 1000，或已处理字节数（取模）
```

### 形态 B：帧头进度槽表（适合"固定位置数组"字面诉求）

如果坚持"数组固定位置"：

```
[槽数量 N][槽0偏移 4B][槽1偏移 4B]...[进度码区: N×4B][数据体]
```

接收端先读槽表，知道每个进度码的字节偏移，可**随机跳读任意进度**，甚至支持"只关心第 k 个进度"的场景。代价是发送端要预先知道所有块偏移（流式发送时需两遍或缓冲）。

## 三、和霍夫曼/变长的冲突及解法

| 冲突 | 解法 |
|---|---|
| 霍夫曼比特流不可随机定位 | 进度码永远在**块边界字节对齐处**，块内才用比特流 |
| 变长整数长度未知 | 块头用**固定 4B 长度**，块内才用 LEB128 |
| 流式发送时总长未知 | 帧头写"块数上限"或"未知=0xFFFFFFFF"，接收端以块尾标记 `0x00` 终止 |
| 进度码本身被压缩 | 进度码**永不压缩、永不进霍夫曼表**，明文 4B |

**关键原则：进度层是"传输层"概念，编码层是"表示层"概念，两者分层，进度码不进任何压缩管道。**

## 四、接收端进度事件生成

```
recv loop:
  read 4B progress_code      → emit(ProgressEvent{block, pct})
  read 4B block_len
  read block_len bytes       → 解压/解码块 → 追加到输出
  if progress_code & 0xFF == 0xFF: break   // 结束哨兵
```

- 进度事件可**去重/节流**（如百分比变化 ≥1% 才发），避免高频事件刷爆。
- 支持**乱序到达**：进度码带块序号，接收端可维护"已完成块位图"，进度 = popcount / 总数，天然容忍重传/乱序。
- 断点续传：记录"最大连续已完成块号"，重启从该块之后请求。

---

## 五、发送端如何生成进度

发送端在**切块时**就知道每块对应的逻辑进度（如"已序列化第 256/1024 个数组元素"）。所以：

1. 序列化器按块产出，每块产出时计算 `pct = 已处理元素 / 总元素`。
2. 写入 `[进度码][长度][块数据]`。
3. 若流式且总数未知，进度码低 24 位改用"已发送字节数"，接收端按已知总长（帧头）折算百分比。

## 六、几个必须注意的坑

1. **进度码不能依赖块内容**：块数据损坏时进度码仍应可读，所以它在块数据**之前**且不压缩。
2. **块边界必须字节对齐**：霍夫曼比特流在块内可任意打包，但块尾要 padding 到字节边界，否则下一个进度码读不对。
3. **CRC 分层**：块级 CRC 放块尾，进度码不参与 CRC（否则坏块导致进度丢失）。
4. **结束哨兵**：最后一块进度码用保留值（如 `0xFFFFFFFF`）标记流结束，避免接收端等超时。
5. **背压**：进度事件是"通知"不是"确认"，别让进度事件反向阻塞数据接收；二者用独立队列。
6. **安全**：进度码里的块序号要被接收端校验（防伪造超大块号导致位图内存爆炸），块号必须 ≤ 帧头声明块数。

## 七、和你整体方案的关系

- **键表/霍夫曼码表/值字典**：放帧头，块间可共享（形态 A）或每块自带（更独立）。
- **进度码**：块边界固定 4B，**属于传输封装层，不属于你设计的"语义扁平数组"**——别把它塞进 `[键表,值表]` 里，那会污染数据结构语义。它应该是数组外面的一层"帧/块封装"。
- **JSONL 场景**：天然按行/按块切，进度 = 已处理行数 / 总行数，和 DSH 的 chunk 帧思路一致，只是把 zstd 帧头换成你的 `[进度码][长度]` 块头。

一句话：**把进度码做成"块级旁路前缀"，固定 4B、字节对齐、明文不压缩、带块序号和结束哨兵，接收端按块边界跳读即可产生进度事件；它属于传输层，不要混进霍夫曼语义数组内部。**

## 二、让 A 成立的关键设计（在你现有块结构上补三条）

你已有的块结构：

```
[进度码 4B][块长度 4B][块数据...]
```

要支持"中断后重建完整前缀"，需补充：

### 1. 块必须**原子且自包含**
- 每块自带：键表/码表/值字典（或引用帧头表但帧头必须最先收到并已校验）。
- 块内是**整数个完整逻辑单元**（若干完整行 / 若干完整数组元素），**绝不把一个 JSON 对象跨块切**。
- 块尾 padding 到字节对齐 + 块级 CRC。
- 效果：**收到完整块 = 能完整解出该块内所有对象**；收到半块 = 整块丢弃，不影响前面。

### 2. 块头带"逻辑单元计数 + 边界索引"
```
[进度码 4B][块长度 4B][单元数 2B][单元偏移表...][块数据][CRC 4B]
```
- 单元偏移表记录块内每个 JSON 行/元素的起始偏移。
- 即使块数据 CRC 失败，仍可**按单元偏移表尝试逐个恢复**（降级 B），能救多少救多少。

### 3. 帧头带"总单元数 / 总块数"与全局检查点
- 接收端维护：`已完整接收块位图`、`最大连续完整块号`、`已恢复单元总数`。
- 恢复时只信任"CRC 通过的完整块"，按块序号连续拼接。

## 三、接收端中断恢复流程

```
1. 收帧头（总块数、总单元数、码表）→ CRC 校验，失败则整个流不可信，报错
2. 循环收块：
   a. 读 [进度码][块长度][单元数][偏移表][块数据][CRC]
   b. 若块数据 + CRC 完整且通过 → 解块 → 追加完整单元 → 位图置位
   c. 若中断在半块 → 丢弃该块（或按偏移表尽力恢复完整单元，标"部分恢复"）
   d. 若块乱序到达 → 存起来，等连续前缀补齐
3. 输出：已完整恢复的单元序列（每个都是合法 JSON 对象/元素）
4. 元信息：恢复率 = 已恢复单元 / 总单元；缺口块号列表
```

**结果**：你得到的是一个**合法 JSON 数组/JSONL 的前缀**——每个元素结构完整，只是后面缺了一些元素。这在语义上是"一半完整结构的 JSON 数据"，可直接被下游消费。

## 四、必须接受的边界（做不到的部分）

1. **不能保证"对象的字段级完整"**：如果一个对象在发送端就被拆到两个块（设计禁止，但若发生），截断后无法保证字段全。→ 用"对象不跨块"规则杜绝。
2. **霍夫曼比特流截断不可解**：半块内的比特流可能停在码字中间，无法判定边界。→ 靠块原子性规避；降级时只能按单元偏移表跳到下一个单元起点。
3. **帧头丢失则全盘不可解**：码表/键表在帧头。→ 帧头重复发送（每块头附带码表 CRC 或码表副本），或帧头 + 首块双写。
4. **CRC 之前的数据不可信**：块数据坏了，块内单元即使偏移表能定位，内容也可能损坏。→ 标记"疑似损坏"，让上层决定是否采用。
5. **流式未知总长**：中断时不知道"还差多少"，恢复率只能报"已收块数/已声明块数"，若总数未知则报绝对值。

## 五、和"下载到一半的 JSON 文件"对比

传统做法下载一个巨大 JSON 文件，中断后得到的是**语法非法的半截文本**（`[{...},{...},{"a":` 这种），任何 JSON 解析器都拒绝。

你的方案中断后得到的是：
- **一批完整合法的 JSON 对象**（已收块内全部单元），可直接逐行 `JSON.parse`；
- 或重组成一个**合法的 JSON 数组前缀**（只含完整元素，尾部无残缺）；
- 加上元信息（缺口、恢复率），上层可决定"够用了"还是"续传补齐"。

这正是块级原子性 + 单元偏移表带来的价值：**把"字节流中断"转化为"逻辑单元级的部分成功"**。

## 一、把结构统一成"分段平铺数组"

你举的形态：

```
[段1数据], 0, 234, 111, [段2数据], ...
```

本质是：**顶层不是一棵树，而是一条扁平的"段流"**，段与段之间用辅助位（标量）分隔/描述。这解决了两个问题：

1. **整体数组 `[全部数据]` 不可恢复**——因为它是"一个大对象"，尾部残缺就整体非法。
2. **分段后每段是独立可解单元**——收到哪几段，就重建哪几段。

我把它规范化成一种**帧内线性布局**：

```
[帧头: 总段数/码表/全局字典]
[辅助位A0][段0] [辅助位A1][段1] [辅助位A2][段2] ...
[结束哨兵]
```

其中每个"辅助位"是一个**定长或变长标量槽**，承载：

- **段序号**（第几段，用于乱序重组）
- **段进度**（该段完成后累计进度 → 就是你要的进度位）
- **段类型/长度/CRC 引用**
- **段间关系**（如 0=独立段、234=引用段、111=续接段 等语义码）

`[段k]` 本身是自包含块：`[键表/码表(可引用帧头)][值流][CRC]`，解出来是**若干完整 JSON 对象/元素**。

## 二、辅助位的语义设计（对应你举例的数字）

你举例的 `0, 234, 111` 可以定义成**辅助位里的"段控制码"**，每个数字有固定语义，接收端只读辅助位就能决策，不必解段内容：

| 辅助位字段 | 宽度 | 语义 |
|---|---|---|
| `seg_id` | 变长 | 段序号，重组排序用 |
| `seg_type` | 1B | `0`=数据段, `1`=字典/码表段, `2`=续接段, `3`=结束哨兵, `4`=重传标记 |
| `progress` | 3B | 段完成后的累计进度（单元数或字节数低 24 位） |
| `elem_count` | 变长 | 本段含多少个完整逻辑单元 |
| `seg_len` | 4B | 段数据字节长（固定宽，便于跳读） |
| `crc_ref` | 4B | 段 CRC，或帧头 CRC 表索引 |

于是你的 `0, 234, 111` 可以读作：`seg_type=0(数据段)`、`progress=234`、`elem_count=111`——**接收端读到这三个数就立刻知道"这是一段数据、到此累计进度 234、含 111 个完整单元"，可以先发进度事件，再去读段体**。

**关键：辅助位在段体之前、字节对齐、明文不压缩。** 这就是你前面要的"进度位"，现在它同时兼任"段边界声明 + 可恢复性元数据"。

---

## 三、为什么这样能"收到几段重建几段"

接收端状态机：

```
state = { 已收段: map<seg_id, 解出的单元列表>, 连续前缀: [], 进度: 0 }

读到辅助位:
  if seg_type == 结束哨兵: 完成
  if seg_type == 数据段:
     发 ProgressEvent{progress}
     读 seg_len → 读段体 → CRC 校验
     if 通过: 解段 → units → 已收段[seg_id] = units
              if seg_id == 连续前缀下一个: 前推连续前缀，进度更新
     if 中断/CRC失败: 丢弃该段，连续前缀停在上一段
```

**恢复产物**：
- 若只要"结构完整的前缀" → 输出连续前缀里所有单元（合法 JSON 数组前缀 / JSONL 前缀）。
- 若要"尽力全收" → 输出已收段的并集，用 `seg_id` 排序，缺口段显式标注。
- 进度事件在每个辅助位处即可发出，**不依赖段体解码**。

---

## 四、段外辅助位还能干更多事（你提到的"数组外辅助位置"）

把这些辅助位当成**段流的"侧信道"**，可放：

1. **全局字典/码表引用**：段0 可以是"码表段"，后续数据段只引用，不必每段重复。
2. **段间引用码**（你的 234/111 可扩展）：如"本段是第 k 段的续接""本段复用第 j 段键表"，减少重复。
3. **重传请求位**：接收端可反向往这个结构写"缺段号"，形成双向协议。
4. **校验链**：辅助位里放前一段的 CRC 或滚动哈希，做**链式完整性**——某段坏可定位到具体段。
5. **压缩参数**：本段用的霍夫曼表版本、是否 zstd 叠加、块大小。

---

## 五、和"整体数组"方案的取舍

| 形态 | 中断恢复 | 结构合法性 | 开销 |
|---|---|---|---|
| `[全部数据]` 单一数组 | ❌ 尾部残缺整体非法 | 强 | 低 |
| **分段平铺 + 辅助位（你的方案）** | ✅ 收几段恢复几段 | 每段合法，前缀合法 | 每段辅助位固定开销（约 8–16B） |

**代价**：每段多几十字节辅助头 + 段边界 padding + 段内码表可能重复（可用帧头共享表摊薄）。对于"值得恢复"的大数据流（日志、批量导出、长数组），这个代价完全值得；对几十字节的小对象则不必分段。

---

## 六、必须注意的坑

1. **段不可跨逻辑单元**：一段内必须是整数个完整对象/元素，否则恢复出半个对象。→ 编码器按单元边界切段。
2. **辅助位定长优先**：`seg_id` 若变长，接收端跳读困难；建议 `seg_id/seg_len/progress` 定长，`elem_count` 可变长。
3. **乱序与重复**：`seg_id` 必须唯一，重复段丢弃（幂等），乱序段缓存等待前缀补齐。
4. **帧头可靠性**：总段数、码表在帧头，帧头坏了全盘不可信 → 帧头 CRC + 首段冗余一份码表。
5. **结束哨兵必须显式**：否则接收端不知道"是流结束了还是网络断了"，会一直等。哨兵用保留 `seg_type=3`。
6. **进度语义要一致**：`progress` 是"单元数"还是"字节数"要在帧头声明，别混。
7. **安全**：`seg_len`、`elem_count` 要有上界校验，防伪造导致内存爆炸。

---

## 七、一句话总结

**你描述的 `[段],辅助,辅助,[段]...` 正是"可恢复分段流"的标准形态：顶层线性平铺、段原子自包含、段间辅助位承载 `seg_id/类型/进度/长度/CRC`。接收端只读辅助位就能发进度事件并决定段取舍，收到哪些完整段就重建哪些段，输出的是"结构合法、单元完整"的 JSON 前缀或段并集；整体单一数组做不到这一点，分段平铺 + 辅助位才是中断可恢复的正解。**

# 因为 jsonl 是一个按照时间正序包含所有类型事件的数组级json对象，那么在实际传输过程中 关注对话消息要高于 思考过程或者工具调用的 那么我是不是可以通过重组json结构来让压缩保证 对话消息类型数据在  "分段平铺数组" 的前面 即使尚未传输完毕 但是已经可以恢复出完整的对话消息数据了

# 按优先级重排段序：可行且正是"分段平铺 + 辅助位"的杀手级用法

**结论：完全可以，而且这是你这个架构最优雅的地方——把"传输顺序"从"时间顺序"里解耦出来。JSONL 的逻辑时间序由每行的 `seq/time` 字段保证，物理传输顺序则按"对话消息优先、思考/工具调用后置"重新排列分段。接收端按段收齐就能先重建完整对话，后到的段再补齐其余事件，最终靠 `seq` 做逻辑重排，语义完全无损。**

---

## 一、关键前提：重排不破坏语义，因为顺序信息在数据里

JSONL 的"时间正序"是**逻辑属性**，靠每条事件的 `seq`（或 `time`）字段表达，而不是靠"文件里谁先出现"。

所以：
- **物理上**：段可以任意顺序发（对话段先、思考段后）。
- **逻辑上**：每个事件带 `seq`，接收端最后按 `seq` 排序即可还原"时间正序"。
- **恢复上**：只要"对话消息段"先到齐，就能先产出一份**只含对话消息、内部按 seq 有序**的 JSONL——这就是"完整对话数据"。

这正是重排的安全边界：**重排的是段，不是事件；事件的相对时间序由 `seq` 锁定，不因段序改变而错乱。**

---

## 二、段序设计：优先级分层

给每个段在辅助位里加一个**优先级字段 `prio`**，并在帧头声明"优先级分层方案"：

```
prio=0  P0 对话消息（user/assistant message 主体内容）
prio=1  P1 消息元数据（request/header、usage、角色、模型）
prio=2  P2 工具调用/结果（tool/call、tool/result）
prio=3  P3 思考过程（reasoning chunks、step 边界）
prio=4  P4 其他（approval、诊断、chunk 打包）
```

发送端**按 prio 升序发段**：所有 P0 段先发，再 P1，再 P2……同一 prio 内按 `seq` 升序。

辅助位扩展：

| 字段 | 语义 |
|---|---|
| `prio` | 本段优先级层（1B） |
| `seg_id` | 段序号（物理顺序） |
| `first_seq/last_seq` | 本段覆盖的事件 seq 区间（4B×2），供接收端判断"某 seq 区间是否已到齐" |
| `progress` | 累计进度（你原来的进度位） |
| `elem_count/seg_len/crc` | 同前 |

`first_seq/last_seq` 是新加的关键字段——它让接收端**不解段体就能知道"这段覆盖哪段时间窗"**，从而判断"对话消息是否已完整"。

---

## 三、接收端如何"边收边产出完整对话"

```
state = {
  P0_段集合: map<seg_id, units>,   // 对话消息段
  P0_已覆盖seq区间: interval_set,
  P0_期望seq区间: 由帧头声明（对话消息的 seq 范围）
  其他层段: ...
}

每收一段:
  读辅助位 → 发 ProgressEvent{prio, progress}
  解段 → 按 prio 归入对应层
  if prio==P0:
    把该段 units 按 seq 合并进 P0 池
    更新 P0_已覆盖seq区间
    if P0_已覆盖 == P0_期望:
        emit "完整对话就绪" 事件   // 关键：此刻可产出完整对话 JSONL
  // P1~P4 照常累积，不影响"对话就绪"判定
```

**产出时机**：
1. **对话消息全部 P0 段到齐** → 立刻输出一份"完整对话 JSONL"（只含 message 事件，内部 seq 有序），即使 P1–P4 还没传完。
2. 后续 P1 到齐 → 输出"带元数据的对话"。
3. 全部到齐 → 输出"完整时间序 JSONL"（所有事件按 seq 排序）。

这天然支持"渐进交付"：下游可以先消费对话内容，再等工具/思考细节补全。

---

## 四、为什么这个重排对压缩也是正收益

不只是恢复体验，**压缩率也提升**：

1. **同类聚簇**：P0 段全是 `assistant/message`，字段同构度极高 → 块内键表更小、霍夫曼码字更集中、枚举值（role/type）重复率更高。
2. **跨段字典复用**：P0 段之间共享"消息键表 + role 枚举字典"，摊薄开销；P3 思考段又是另一套高度同构结构，各自建表更干净。
3. **长文本隔离**：对话 `content` 是长文本（走字面量+zstd），思考 `reasoning` 也是长文本但独立成层，不会和短结构混在一个块里互相拖累。

也就是说，**按 prio 分段 = 按"结构相似度"聚类**，这本来就是压缩的最佳实践。你为了恢复优先做的重排，顺带把压缩也优化了。

---

## 五、段序重排必须守住的三条边界

1. **段内事件仍按 seq 升序**：一个段内的单元不要乱序，保持块内可顺序解析；乱序只发生在"段与段之间"。
2. **引用完整性**：`tool/result` 引用 `tool/call` 的 id、`assistant/message` 引用 `parentId`——若工具段后置，接收端在"仅 P0 就绪"阶段会遇到**悬空引用**。处理：
   - 在 P0 段里附带被引用 id 的"最小占位"（仅 id + 类型），或
   - 产出"对话就绪"时显式标注"引用未解析"，等 P2 到齐再补全。
3. **seq 连续性校验**：帧头声明"P0 期望 seq 区间"，接收端据此判定"是否真到齐"；若发送端因过滤只发了部分 P0，要在帧头声明"P0 仅含 message，不含 X 子类型"，避免接收端永远等不齐。

---

## 六、和"时间正序 JSONL"的兼容

最终产物可有两种视图，由接收端**按需生成**，数据只存一份：

- **视图 A（渐进）**：按 prio 分层，先出对话，后出其余——适合流式 UI/首屏。
- **视图 B（规范）**：所有事件按 `seq` 全局排序，还原标准时间正序 JSONL——适合归档/回放。

两份视图都从同一份"已收段池"派生，不重复传输。这正好回答你最初的"对话优先"诉求：**传输层按 prio 排，消费层按 seq 排，两者解耦。**

帧头新增：

```
priority_scheme: [{prio:0, name:"dialog", type_filter:[...]}, ...]
P0_expected_seq_range: [min, max]
total_elems_per_prio: [n0, n1, ...]
```

辅助位新增 `prio` 和 `first_seq/last_seq`。其余字段不变。

## 八、一句话总结

**可以。把 JSONL 的"物理传输序"从"逻辑时间序"中解耦：事件靠 `seq` 保序，段按 `prio`（对话 > 元数据 > 工具 > 思考）重排发送，辅助位加 `prio + first_seq/last_seq + progress`。接收端按 `prio` 归层，P0 段覆盖的 seq 区间到齐即可先产出"完整对话 JSONL"，后续层渐进补齐，最终按 seq 可还原标准时间序。且按 prio 聚簇顺带提升压缩率。唯一要处理的是跨层引用（工具结果晚到导致悬空 id）和帧头期望区间声明，避免"永远等不齐"。**
