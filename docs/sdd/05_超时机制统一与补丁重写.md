### 1.3 "0" 的四种含义

1. 底栏"工具执行"组：0 = 不限制（`minMs: 0`）

4. **已发布但 key 缺失**：`timeoutValues[key] ?? 0` → 当作 0 → 静默关闭

## 2. 根因：四种"时间"被一种原语表达

上游设计里，这四件事分得很清楚，补丁把它们压成了一个数：

1. **执行时长**：命令/请求本身允许跑多久 → 到点终止（kill / abort / 报 TIMEOUT）
2. **等待时长**：调用方等多久 → 到点返回"仍在运行"，**工作继续**
3. **连接健康**：长时间无字节 → 判死并重试（上游 `idleWatchdog`）
4. **用户取消**：唯一应当永远有效的终止源

002 为了"去除所有超时"，把 1、2、3 全部改成永不触发；012 又把 1、2 改成读同一张表。结果：

- 想"允许长命令"→ 必须把等待也归零 → 卡死；
- 想"等待有界"→ 只能改常量 → 长命令被杀；
- 想要 3（连接判死）→ 只能靠 1/2 的定时器 → 一起被关掉。

## 3. 目标模型

### 3.1 三种模式

| 模式 | 到期行为 | 允许 0 | 典型能力 |
| --- | --- | --- | --- |
| `budget` | 终止工作（杀进程 / abort 请求 / 返回 TIMEOUT） | 是（0 = 只受用户取消） | bash、持久终端、web_fetch、MCP 调用、LSP、terminal、ssh、worktree |
| `wait` | 结束等待并返回当前状态，**不终止工作** | **否**（最小 1000ms） | bash 前台等待、job_output、wait_agent、session 等待 |
| `off` | 永不武装定时器（策略固定） | 固定 0，锁死 | 模型请求、人工审批 |

**不变量**：任何 `wait` 型能力都必须有有限上限，且上限与执行预算相互独立。这样"命令允许跑 24 小时"和"工具调用 2 分钟必须回到模型"可以同时成立。

### 3.3 解析算法

```ts
export function resolveTimeout(code: string, requested?: number): { ms: number; mode: TimeoutMode } {
  const rule = RULE_BY_CODE.get(code)
  if (rule === undefined) {
    // 未注册的 code 绝不静默关闭：回退到调用方预算，并只告警一次
    warnOnce(`timeout code "${code}" is not registered; falling back to the caller budget`)
    return { ms: requested ?? FALLBACK_BUDGET_MS, mode: 'budget' }
  }
  if (rule.mode === 'off') return { ms: 0, mode: 'off' }

  const configured = store.get(rule.key!) ?? rule.defaultMs   // 未保存 = 上游默认

  // budget 的 0 表示"不限制"，此时仍然尊重调用方给出的更紧预算
  const base = configured === 0
    ? (requested ?? 0)
    : Math.min(requested ?? configured, configured)

  if (rule.mode === 'wait') {
    if (base <= 0) throw new Error(`wait timeout ${rule.key} must stay finite`)
    return { ms: Math.max(rule.minMs, Math.min(base, rule.maxMs)), mode: 'wait' }
  }
  return { ms: base === 0 ? 0 : Math.max(rule.minMs, Math.min(base, rule.maxMs)), mode: 'budget' }
}
```

必须成立的不变量：

- **I1** 调用方只能收紧，不能放宽；设置是上限，模型的 `timeoutMs` 不会被丢掉
- **I2** `wait` 永远有限；`wait` 型 key 提交 0 直接被 HTTP 400 拒绝
- **I3** `off` 只由注册表决定，不允许用户用 0 表达"关闭"
- **I4** 设置未发布时用注册表默认值（**不是**调用方预算），发布后即生效；发布必须同步完成
- **I5** 运行时 `packages/*/*/src` 里不允许裸 `setTimeout` / `AbortSignal.timeout`，除非带 `// timeout-policy: hygiene <原因>` 注释
- **I6** 到期行为由 `mode` 决定，调用点不得自行决定 kill 还是返回

### 3.4 API 变化

```ts
// budget：到期终止工作
export function deadline(upstream: AbortSignal | undefined, code: string, requested?: number): Deadline

// wait：到期返回状态（改名，避免与 deadline 混用）
export function waitWindow(upstream: AbortSignal | undefined, code: string, requested?: number): Deadline

// 设置：校验 key 必须注册、值必须落在 [minMs, maxMs]
export function configureTimeouts(values: Readonly<Record<string, number>>): void
export function timeoutRule(key: string): TimeoutRule | undefined
```

- 删除公开的 `timeoutSetting()`：调用点不再自己查表，避免"查表 + deadline 二次钳制"的双重语义
- `idleWatchdog` 保留但只在 `llm.idle`（`off`）下工作，或直接删除（模型请求政策为不超时）
- `MAX_TIMER_DELAY_MS` 保留，仅用于 `maxMs` 边界

### 3.5 底栏生成与校验

```ts
// packages/bundle/web-app/src/night-timeouts.ts
export const NIGHT_TIMEOUT_GROUPS: readonly TimeoutGroup[] =
  groupTimeoutRules(TIMEOUT_RULES)   // 来自 registry，不再手写数字

const values = mergeDefaults(stored) // 默认值 = rule.defaultMs
```

- 保存时逐 key 校验：`key` 必须存在、`value` 在 `[minMs, maxMs]`、`wait` 型禁止 0
- 加载时**同步**读文件再 `configureTimeouts()`，消除 I4 的竞态
- 底栏 UI 不动（013 的 unit 转换继续适用）

### 3.6 门禁

`scripts/check-timeouts.mjs`（`pnpm lint:timeouts`）：

1. 扫描 `packages/*/*/src/**/*.ts`、`apps/*/src/**/*.ts`
2. 命中 `setTimeout(`、`setInterval(`、`AbortSignal.timeout(` 且无 `// timeout-policy: hygiene` 注释 → 报错
3. 扫描所有 `deadline(` / `waitWindow(` 的第一个字符串参数，必须存在于 `TIMEOUT_RULES`
4. 扫描 `TIMEOUT_RULES` 的每个 `key`，必须能在底栏 catalog 中出现

这样"新增能力忘了接超时"和"新增超时忘了注册"都会在 CI 失败，而不是等下一次卡死。

| `llm` 长请求 | 不被任何定时器打断（仅用户取消） |

### 6.2 手工场景

1. 复现本案例：`Chrome --headless --screenshot` + 不存在的 URL → 工具应在 2 分钟内返回"仍在后台"，会话继续
2. 黑洞 HTTP：`curl` 到 `10.255.255.1` 的工具调用 → 30s 失败
3. MCP：指向一个会接受连接但不回包的假 server → 启动超时
4. 子 agent：让它跑一个永不作答的任务 → 等待到期返回当前状态
5. 底栏：把"命令执行"设 0、恢复默认、设 24h，各保存一次，重启后值仍在

### 6.3 回归

- 底栏保存后立即生效（不需要重启）
- 未保存过设置时行为与上游默认一致（除了 `llm` 仍为 off）
- `pnpm test`（night-cruising 的 patch 工具测试）与 `patch:verify` 通过

## 7. 风险与回滚

| 风险 | 处理 |
| --- | --- |
| 等待预算过短，长命令被转后台 | 这是预期行为；job 仍在，模型可用 `job_output` 继续，且 `wait.foreground` 可调到 24h |
| 恢复上游后某些"整夜跑"的场景被杀 | 把对应 `budget` 设为 0 或调大；默认值只在无人配置时生效 |

| 打包缓存 digest 变化导致首次构建变慢 | 一次性成本 |
| 回滚 | `git checkout pre-timeout-rewrite-<date> -- patches/` 并重跑 `patch:verify` |
