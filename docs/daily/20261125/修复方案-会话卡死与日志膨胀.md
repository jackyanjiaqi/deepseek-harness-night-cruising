## 0. 一句话方案

把「**阻塞等待**」和「**模型请求超时**」在机制上分开：新增只服务于阻塞等待的真实计时器 `waitDeadline()`，让 `job_output` / `wait_agent` 恢复“到期返回状态、绝不终止任务”；把重复调用守卫从「连续计数 + 8 次封顶提醒」升级为「窗口签名 + 持续升级 + 可选阻断」；再让 job 状态行带「已运行 / 已静默」时长、workflow 补齐子智能体进度心跳。**四件事分别落在 4 个补丁里，可单独上线、单独回滚。**

## 3. 详细改动

### 3.1 `011` — 等待层：让 `job_output` / `wait_agent` 真正到期

#### 3.1.1 新增 `waitDeadline()`（`packages/util/timeout/src/index.ts`）

`deadline()` 被本地策略改成 no-op（只转发上游取消），这是“等待永不到期”的总闸。**不要动 `deadline()`**（模型请求仍按政策无超时），而是新增一个语义明确的兄弟函数，只给“到期返回状态”的等待用：

```ts
/**
 * Arm a real timer for a caller-facing blocking wait.
 * Unlike {@link deadline}, this helper is *not* a model-request deadline:
 * its expiry returns the current state to the caller and never aborts work.
 * Local policy disables request deadlines, not wait polling.
 * @param upstream - the caller's cancellation, forwarded unchanged.
 * @param timeoutMs - the wait expiry, clamped to MAX_TIMER_DELAY_MS.
 * @param code - capability-owned timeout code carried by the abort reason.
 */
export function waitDeadline(upstream: AbortSignal | undefined, timeoutMs: number, code: string): Deadline {
  const controller = new AbortController()
  const signal = upstream === undefined ? controller.signal : AbortSignal.any([upstream, controller.signal])
  const timer = setTimeout(() => {
    if (!controller.signal.aborted) controller.abort(new TimeoutReason(code, timeoutMs))
  }, Math.min(timeoutMs, MAX_TIMER_DELAY_MS))
  let disposed = false
  return {
    signal,
    [Symbol.dispose]() {
      if (disposed) return
      disposed = true
      clearTimeout(timer)
    },
  }
}
```

配套单元测试（`packages/util/timeout/tests/`）：到期触发 `TimeoutReason`；`dispose` 后不再触发；上游 abort 立即转发且不叠加计时器；`timeoutMs` 超 2^31-1 时被 clamp（不产生 1 ms 立即触发的 Node 行为）。

#### 3.1.2 `jobs-local` 的 `waitJob` 换用它（1 行）

`packages/jobs/jobs-local/src/index.ts:515`：

```diff
-      using d = deadline(signal, timeoutMs, TASK_WAIT_TIMEOUT)
+      // 到期只结束这次等待；job 继续跑，跟模型请求超时无关。
+      using d = waitDeadline(signal, timeoutMs, TASK_WAIT_TIMEOUT)
```

`waitJob` 已有的分类逻辑（`timeoutOf(d.signal, TASK_WAIT_TIMEOUT)` → `resolve()` 而非 `reject`）不需要改：计时器到期 → 解析 → `job_output` 读到当前 ring 内容并返回状态行。

#### 3.1.3 `job_output` 的等待缺省/上限回调正常值（`packages/jobs/tool-jobs/src/index.ts:69-70`）

当前被 `002` 补丁改成 `Math.max(30_000, 2_147_483_647)`。**这是本方案唯一需要覆盖 002 的地方**，用新补丁显式改回并在注释里写清理由（002 其他 320 处不动）：

```diff
-  waitTimeoutMs: z.number().min(1).default(Math.max(30_000, 2_147_483_647)),
-  maxWaitTimeoutMs: z.number().min(1).default(Math.max(600_000, 2_147_483_647)),
+  // 等待是轮询便利，不是模型请求期限：模型没给 timeout_ms 时 30 s 返回一次状态。
+  waitTimeoutMs: z.number().min(1).default(30_000),
+  maxWaitTimeoutMs: z.number().min(1).default(600_000),
```

模型显式传 `timeout_ms` 仍走 `Math.min(args.timeout_ms ?? waitDefault, waitCap)`，语义与工具描述一致。

#### 3.1.4 `wait_agent` 同一处病（`packages/subagent/tool-subagent-control/src/wait-agent.ts:73`）

```diff
-    const timer = setTimeout(() => { finish(() => { resolve({ timedOut: true }) }) }, (void (timeoutMs), 2_147_483_647))
+    const timer = setTimeout(() => { finish(() => { resolve({ timedOut: true }) }) }, Math.min(timeoutMs, MAX_TIMER_DELAY_MS))
```

依赖细节：`tool-subagent-control` 当前**没有**依赖 `@deepseek-ai/dsh-timeout`（其 deps 只有 `schemastery`、`util-values`）。两条路：

- **推荐**：在 `packages/subagent/tool-subagent-control/package.json` 加 workspace 依赖 `@deepseek-ai/dsh-timeout: workspace:*`（会改 `pnpm-lock.yaml`，但属正常的内部依赖）；
- **零依赖备选**：在文件内写 `const MAX_TIMER_DELAY_MS = 2_147_483_647` 并注释“与 util/timeout 常量同值”，避免 lockfile 变动（补丁更小、更易回滚）。

同样，`waitDeadline` 的实现文件已导出了 `MAX_TIMER_DELAY_MS`（`util/timeout/src/index.ts:25`），无需新增常量。

### 3.3 `013` — 守卫层：窗口签名 + 持续升级（+ 可选阻断）

现状四个盲区（纯建议、只比连续、阈值封顶 8、无终止）。改动集中在 `packages/guard/repeat-tool-reminder/src/index.ts`：

```ts
export interface Config {
  thresholds?: number[]            // 连续阈值，默认 [3, 5, 8]（不变）
  windowSize?: number              // 默认 24：最近 N 次调用
  windowThresholds?: number[]      // 默认 [8, 16, 32]：窗口内同签名次数
  repeatEvery?: number             // 默认 20：超过最大阈值后每 +20 次再提醒
  escalation?: 'advisory' | 'block' // 默认 'advisory'
  blockAfter?: number              // 默认 40，仅 escalation==='block' 生效
  // 既有 include/exclude/argumentsPreviewChars 不变
}
```

`observe()` 内部状态从 `{key,count}` 扩为：

```ts
interface Chain {
  key: string
  count: number              // 连续相同
  ring: string[]             // 最近 windowSize 次签名（FIFO）
  window: Map<string, number> // 签名 → 窗口内出现次数
}
```

判定顺序（每步只发一条提醒，避免上下文膨胀）：

1. 连续计数命中 `thresholds` → 现有 gentle / detailed 文案（不变）；
2. 否则窗口内该签名计数 ∈ `windowThresholds` → detailed 文案 + `consecutive_calls` 改为 `calls_in_window`；
3. 否则窗口计数 > `max(windowThresholds)` 且 `(n - max) % repeatEvery === 0` → “仍在重复”提醒（短文案，带累计次数）；
4. `escalation === 'block'` 且窗口计数 ≥ `blockAfter` → 返回 `{ kind: 'block', feedback: [...], additionalContexts: [reminder] }`，把这次调用变成 `isError`，强迫模型读结果、换做法。

保留现有的 `agent/pre-step` 用户插话重置（`chains.delete(agent)`）。

测试（`repeat-tool-reminder.spec.ts`）：

| 用例 | 期望 |
| --- | --- |
| A/B 严格交替 20 次 | 在第 8 次左右出现窗口提醒（修复事故里的 0 提醒） |
| 同一调用 100 次 | 第 3/5/8 次 + 28/48/68/88 次都有提醒（不再静默） |
| 不同参数不误报 | 0 条 |
| block 模式 | 第 40 次返回 `isError`，其余正常 |
| 用户插话后 | 连续链清零，窗口同清 |

**政策注意**：`escalation:'block'` 按调用内容判定、不涉及请求次数/用量门控，但仍属“强制中断单次调用”，默认关闭，需产品显式开启。

### 3.4 `014` — 子智能体心跳进 job progress

现状：`workflow` 镜像只在 `phase / log / agent-start / agent-end` 写 ring，单个子智能体长跑期间没有事件，父会话的状态行 6 小时不变。

1. `packages/workflow/workflow/src/index.ts`：事件表新增
   ```ts
   'workflow/agent-progress'(info: WorkflowRunInfo, agent: WorkflowAgentInfo & { step: number }): void
   ```
2. `packages/workflow/workflow-ptc/src/index.ts`：`agentStart` 时用 `agent.childId` 找 live agent，订阅其 `agent/pre-step`（节流 60 s），emit `workflow/agent-progress`；`agentEnd` 时退订。
3. `packages/workflow/tool-workflow/src/record.ts`：收到 progress 后
   ```ts
   job.updateProgress(`${currentPhase ?? ''}${currentPhase ? ' · ' : ''}step ${agent.step}`)
   ```
   `log` 通道只在阶段切换时追加，避免 ring 膨胀。
4. 与 `012` 组合后，模型每次 poll 都能看到 `[status: running 2h05m, implementation · step 1240; idle 1m]`。

测试：workflow 的 stub provider 跑一个 3 步子智能体 → 断言 `updateProgress` 至少被调用一次且末尾是 `step N`；`agent/agent-end` 后不再刷新。

## 6. 回归验证场景（复现本次故障）

1. **等待到期**：脚本起一个 `sleep 600` 的后台 bash job → `job_output(wait:true, timeout_ms:2000)` → 2 s 返回 `[status: running]`，job 仍在，随后 `job_kill` 正常。
2. **子智能体重复环**：workflow 用一个 stub 子智能体（或本地小模型）连续发同一条 `bash` 调用 40 次 → 断言：第 3/5/8 次有提醒；第 28 次仍有提醒；父会话 `job_output` 每次在 30 s 内返回，状态行 idle 时间递增。
3. **A/B 交替**：子智能体交替发 A/B 各 30 次 → 第 8 次左右出现窗口提醒（旧实现 0 提醒）。
4. **端到端**：复用本次事故的 workflow 脚本骨架，把子智能体换成“只重复不产出”的假模型，断言整轮在 `maxWaitTimeoutMs × 轮数` 内结束，父会话能自主发现并 `job_kill`——不再需要用户看墙钟。
