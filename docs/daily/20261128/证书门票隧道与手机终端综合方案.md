## 0. 结论先行

| # | 结论 | 一句话理由 |
|---|---|---|
| D1 | **第三张网不是第三套 VPN，而是"公网可达性平面"**：发现板 + 中继 + 直连，三种承载跑同一套帧协议 | 真 VPN（Nebula/WireGuard/Tailscale）在手机上要系统 VPN 权限、TUN、后台保活，重且不可控；我们要的是"持票能连上服务"，不是"拿到一个 IP" |
| D2 | **一张票 = 一张 Ed25519 签名的能力证书（DSH-CERT）**，同时承担网络准入、服务授权、保险柜条目三种角色 | 三种用途共用同一套字段与验签逻辑，省掉 X.509/CA/mTLS 和"证书 vs 票据"的双轨 |
| D3 | **子账号是长期身份票，门票是短期能力票**；同一 cert 结构，靠 `kind` 与 `renew` 策略区分 | 身份需要可改口令、可识别、可提权；能力需要固定到期、可批量、不可转让。两者本质不同但可以同构 |
| D4 | **票的 TTL 与场次解耦**：`exp` 是短租约，`hardExp` 是硬上限，中间用"续期链"在保险柜里本地兑换 | 节目 2 小时固定散场，游戏可能 6 小时；既不把票签成 6 小时（撤销窗口太大），也不要求全程在线 |
| D5 | **手机是 T4 节点：根密钥保管 + 审批 + 消费终端**，不是 VPN 节点、不跑 Agent、不默认中转流量 | 手机的价值在"人在这里、钥匙在这里"，不在带宽和算力 |
| D6 | **服务按名字发布，不建 L3 网段**：host 发布 `service`，guest 通过 `(hostId, sid)` 访问；手机用 app 内代理渲染 | 免 TUN、免路由、免系统信任库；"虚拟局域网"对用户成立，对内核不成立 |
| D7 | **Tauri 能做，但"Electron 级自由"只在应用层**：Rust 侧几乎无限制，WebView 侧没有证书校验钩子 | 所以把 TLS 终止在 Rust，WebView 只渲染本地回环页；绕开而不是硬碰系统 WebView 的限制 |
| D8 | **净精简：5 层 → 3 实体、2 套证书 → 1 套、8 个新模块 → 5 个组件、删 PAKE、删 CA、删手机网关** | 上一轮两份文档把"安全正确"做到了，但把"可实施"做没了；这份按"一个人两周能起 P0"来砍 |

**直答四个问题**

1. **"类似 tailscale auth-key 但更轻"怎么做？** 票就是 auth-key 的替代：一串码换一张短期 cert，cert 绑定设备公钥，凭 cert 进板、进中继、进服务；没有账号、没有控制台、没有 ACL 语法，权限写在 cert 的 `acts/scope` 里。
2. **"游戏时长不固定"怎么办？** 票带 `hardExp`（比如 8 小时）+ 一串预签的 15 分钟续期段；手机/桌面在自己的保险柜里逐段兑换，不需要 host 在线；撤销在下次连上 host 时收敛。
3. **"子账号和门票区别"是什么？** 子账号 = 有身份、有口令、可改口令、可绑手机号、可被手机提权、可长期续；门票 = 无身份、一次性兑换码、固定硬到期、批次签发、不可提权。二者共用 cert 与保险柜。
4. **"Tauri 能否像 Electron 一样自由？"** 应用层能（Rust 随便写、可起本地服务、可开原生窗口、可后台）；WebView 层不能（系统内核、无 `setCertificateVerifyProc`、自定义协议不流式）。本方案让 WebView 只做 UI，所以"不能"的部分用不上。

## 1. 需求转译与边界

### 1.1 七条硬需求

| # | 需求 | 验收形态 |
|---|---|---|
| R1 | 局域网、Tailscale 之外，再加一条"公网持票入网"通道 | 陌生人拿到一张票，不装 Tailscale、不加账号，能从公网连上 host 的服务 |
| R2 | 票/证书统一，存进各 peer 的保险柜 | 同一份 `cred` 对象既用于隧道认证，也用于服务授权；离线可读 |
| R3 | 门票有固定到期；长会话可在柜内续期 | 节目到点即断；游戏可续到 `hardExp`；续期不依赖 host 在线 |
| R4 | 手机本身是保险柜，权限高于桌面 | 手机持根密钥份额/审批密钥，能批准提权、发码、开柜；节点层级 T4 |
| R5 | 手机是独立 App（无 DSH 底栏）：收隧道消息、做交互终端、做消费终端 | 通知/审批/到期/报错/临时授权都在手机上完成；能打开 host 发布的网页服务 |
| R6 | 服务强制 HTTPS，且能区分不同时期建立的连接 | 上游 TLS 校验；每次连接有 `connSeq/joinedAt`，服务端可区分早鸟/迟到/重连 |
| R7 | 技术架构更简单，适合 DSH host ↔ 手机 | 新增组件不超过 5 个；手机端不要求 root/VPN 权限 |

### 1.2 非目标（本期明确不做）

- 不做 L3 虚拟网卡、不做网段路由、不做系统 VPN 配置（iOS NetworkExtension / Android VpnService 都不碰）。
- 不做全网 DHT、不做跨 host 自动发现（发现靠"板 + hostId"，不靠爬网）。
- 不做云端账号体系；票的签发权在 host/主账号，板只是公告栏。
- 不做"手机给别的节点当媒体中继"；手机中转只作为可选 P4。
- 不引入任何会中止在途模型请求的计时器；票的 `exp` 是**凭证有效期**，不是请求超时。

### 1.3 与两份旧文档的关系

- 保留：0ebfbe98 的"能力证书 + 角色/作用域 + 撤销代次 + 威胁模型"骨架；07c43f0e 的"门票批次 + 保险柜委托 + 入口鉴权"结论。
- 删除/替换：五层模型、DSH-CAP 与 ticket 双轨、PAKE、X.509/CA/mTLS、手机独立网关、8 模块清单、P0–P7 分期。
- 迁移：旧文档里的 `acts/scope/revEpoch` 词汇保留，`principal` 降为 cert 里的 `role`。

## 3. 归一模型

### 3.1 三个实体、一张证书、一个柜子

```text
Account（主账号，根密钥）          —— 只做三件事：签 host 证书、签 phone 证书、批准高危操作
  └─ Principal（主体）             —— 两种：sub（长期身份）/ ticket（短期能力）
       └─ Device（设备）           —— Ed25519 设备密钥 + 设备证书（绑定关系）
Credential：DSH-CERT               —— 签给设备的能力证书；网络准入、服务授权、柜内条目三用
Vault：NCV2S                       —— 每个 peer 一个；存 cert、续期链、撤销代次、名册
Tunnel：mesh 帧                    —— 一条帧协议，两条腿（DataChannel / WSS 中继）
```

不再有"账号域/主体/能力/对象"五层，也不再有"DSH-CAP + ticket"两套证书。`对象` 退回保险柜的通用对象，`域` 退回 `accountTag`/hostId。

### 3.2 DSH-CERT 字段

```jsonc
{
  "v": 1, "typ": "dsh-cert",
  "cid": "c_9f2…",                  // 证书 id，可公开
  "kind": "sub" | "ticket" | "phone" | "host" | "cross",
  "iss": { "pk": "ed25519:…", "kind": "account" | "host" | "phone" },
  "sub": { "pk": "ed25519:…", "dev": "device-id" },   // 绑定设备公钥 + deviceId
  "aud": { "host": "h_…", "svc": ["*"] },             // 受众：哪台 host、哪些服务
  "role": "owner" | "sub" | "guest" | "approver",
  "acts": ["svc/open", "http/get", "vault/open:game"],// 动作白名单
  "scope": { "kinds": ["game"], "objects": [], "rooms": [] },
  "iat": 1795, "nbf": 1795,
  "exp": 1795,                      // 当前租约（短，15 min）
  "hardExp": 1795,                  // 硬上限（场次结束 / 游戏 8h）
  "renew": { "mode": "none" | "chain" | "online", "every": 900, "chain": "ch_…", "seq": 1, "maxSeq": 32 },
  "batch": "b_…",                   // 门票批次；子账号为 null
  "ident": { "phoneHash": "…", "name": "Beta 042" },  // 仅 sub/phone；门票为 null
  "revEpoch": 3,
  "parent": null,                   // 委托链，深度 ≤ 2
  "sig": "ed25519:…"                // 对 JCS(去 sig) 签名
}
```

**为什么不是 X.509**：这张证书从不交给浏览器，也不进系统信任库；TLS 在 Rust 里终止，身份靠 `hello` 里的 Ed25519 证明。X.509 带来的 ASN.1、CA、链验证、吊销列表全是额外负担。若未来要让外部浏览器直接访问，再做一个"X.509 桥"（用同一把 account 根签短期叶证书），不影响本期。

**验证顺序**：签名 → `iss` 是否可信（account 根 / host 证书 / phone 证书）→ `sub.pk` 是否等于握手设备公钥 → `aud.host` 是否本机 → `nbf/exp`（时钟 ±5 min）→ `revEpoch ≥ 本机` → `acts ⊆ roleMax(role)` → `scope` 覆盖本次请求。任一步失败 fail closed。

### 3.3 子账号 vs 门票

| 维度 | 子账号（`kind=sub`） | 门票（`kind=ticket`） |
|---|---|---|
| 本质 | 长期**身份** | 短期**能力** |
| 生命周期 | `hardExp` 30 天，可滚动续期 | 签发即固定，最长不超过场次/测试周期 |
| 凭证 | 口令（可改）+ 设备证书 | 一次性兑换码 → 短期证书 |
| 身份识别 | 有：`phoneHash`、显示名、名册历史 | 无：只有票号/批次，不记手机号 |
| 设备 | 多设备（默认 2） | 首绑 1 台，换机要重发 |
| 提权 | 手机签名可临时提权（≤15 min） | 不可提权 |
| 签发方式 | 逐个签发、可改口令、可停用 | 批次签发、可整批回收 |
| 续期 | 在线续期（host 检查口令代次/撤销） | 续期链（柜内本地兑换）或不可续 |
| 撤销 | 单主体 / 换 `revEpoch` | 单票 / 整批 / 全场 `revEpoch` |
| 关系 | 可以**持有**多张门票 | 可以**升级**为子账号（host 允许时） |

一句话：**子账号是"你是谁"，门票是"你能进哪扇门、进多久"**。门票永远不携带身份，子账号永远不靠门票证明自己。

### 3.4 口令、手机号与提权

| 项 | 设计 | 理由 |
|---|---|---|
| 口令存储 | 子账号：host 存 Argon2id verifier（`t=3,m=64MiB,p=4`）；门票：host 存 HMAC(batchKey, code) | 不存明文；门票码 50+ bit 且一次性，HMAC 足够 |
| 口令传输 | 先 `cred/preauth` 取 `salt + challenge`；客户端本地算 `verifier = Argon2id(pass, salt)`，回 `HMAC(verifier, challenge)`；host 存 verifier 并校验 | host 看不到口令原文；challenge 防重放。verifier 仍是口令等价物，库泄露时可被冒用，靠限速与短租约兜底 |
| 改口令 | host 更新 verifier 并递增 `passGen`；已发证书不立即失效 | 改口令不应把用户所有设备踢下线 |
| 手机号 | 只存 `phoneHash = HMAC(accountKey, e164)`；只用于展示、找回、通知 | 号码不进认证/审批/恢复公式；补卡、复用都拿不到权限 |
| 提权 | 手机对 `{subId, scope, ttl}` 签名 → host 签 `elevate` 子证书（`acts ⊆ owner`、`exp ≤ 15 min`） | 显式、可审计、限时、绑手机设备 |
| 防爆破 | 单设备 5 次/5 分钟；单 IP 20 次/5 分钟；单批次 100 次/小时锁定；错误统一返回 `invalid` | 只挡兑换入口，不挡已入场流量 |

### 3.5 保险柜内的凭证布局

```text
$DSH_HOME/account-mesh/
  identity.json                  # 设备密钥（已有）
  vault/
    creds/<cid>.ncv2s            # cert + 续期链 + 可选解锁材料（kind=cred）
    creds/index.json             # cid → {kind, host, exp, hardExp, state}
    revocations.json             # revEpoch + 撤销列表（缓存，判定以 host 为准）
    roster.json                  # 仅 host：谁、哪张票、哪台设备、何时进
  hosted-vault/                  # 已有：root.key / ledger.json
```

- 手机端同构：`creds/` 放票，私钥放 Secure Enclave/StrongBox，票的解锁材料用设备密钥包裹。
- 证书不是秘密（可以公开），**设备私钥才是**；柜里存的是"证书 + 私钥引用 + 续期链"。
- 子账号的口令默认不落柜：柜里存"解锁票的密钥"，口令只用于向 host 换新票。若产品要"记住口令"，柜里存的是用设备密钥包裹的口令密文（可选，默认关），且不进日志、不进备份。

## 4. 第三张网：公网可达性平面

### 4.1 为什么不用 Nebula / WireGuard / Tailscale

| 方案 | 优势 | 在本场景的代价 |
|---|---|---|
| Tailscale auth-key | 穿透成熟、运维少 | 账号体系、控制面在云端；发票要管理员；手机要装 Tailscale |
| Nebula | 证书即门票、原生 PKI、Lighthouse 自主 | 要维护 CA、TUN 网卡、系统路由；iOS 要 NetworkExtension，Android 要 VpnService；DSH 插件里嵌 Go 守护进程 |
| WireGuard/boringtun | 简单、快 | 同上：L3、root/管理员、手机 VPN 权限；NAT 穿透要自己做 |
| **本方案：应用层隧道** | 无 TUN、无系统权限、票即身份、和现有 WebRTC 复用 | 不是"真局域网"：只支持我们发布的服务；UDP 打洞失败要靠中继 |

结论：**用户要的是"持票能连上 host 的服务"，不是"拿到一个 IP"**。把"网"降级成"服务目录 + 加密信道"，复杂度直接砍掉一个数量级。桌面若确实需要 L3（比如联机游戏的原生 socket），再单独开一个可选模式，不影响本期。

> 可选桥接：若以后桌面端确实需要 L3（原生游戏联机、非 HTTP 协议扫描），可以加一个 Nebula 适配层——把 DSH-CERT 映射成 Nebula 的短时主机证书，L3 只作为桌面可选腿，手机端仍走应用层隧道。本期不做，但证书字段预留 `net: ["app", "l3"]`。

### 4.2 三个角色

```text
          ┌───────────────┐   签名快照（15s）   ┌──────────────┐
          │  Board 发现板  │◀──────────────────│  Host 主机    │
          │ 静态/边缘只读  │                    │ 发布 descriptor│
          └───────┬───────┘                    └──────┬───────┘
                  │ 读 descriptor                     │ 出站 WSS
                  ▼                                   ▼
          ┌───────────────┐   配对转发（不解析）  ┌──────────────┐
          │ Guest 手机/桌面│◀──────────────────▶│ Relay 中继    │
          └───────┬───────┘     直连（优先）      └──────────────┘
                  └──────────── ICE / STUN / TURN ──────▶ Host
```

- **Board**：只读签名快照。host 每 15 秒写一次 `{hostId, hostCert, relay, ticketPolicy, services, revEpoch}`；guest 按 `hostId` 或票面短码读。可直接复用 SDD 06 的"布告板 + 边缘"，也可以先放对象存储。
- **Relay**：WSS 长连接。host **出站**连中继，guest 也出站连中继；中继按 `hostId+room` 配对，只转发密文帧。好处：host 不需要公网入站端口、不需要 DDNS、不需要端口映射。复用 06 的边缘（WSS）最省。
- **Direct**：WebRTC ICE。候选通过中继/板交换，STUN 打洞；失败回退中继；企业网可开 ICE-TCP。媒体（电台）以后走同一条 WebRTC，不另起栈。

### 4.3 取票 → 入网 → 连服务（时序）

```text
Host                         Board                 Guest（手机/桌面）
 │ 建批次、印码（离线）          │                        │
 │ 发布 descriptor ───────────▶│                        │
 │                            │◀── 按 hostId/短码读 ────│
 │                            │─── descriptor + 指纹 ──▶│  显示 host 指纹/场次
 │◀── preauth {hostId, subId?} ──▶ {salt, challenge} ───│  走中继或直连
 │◀──────────── redeem {code, proof, devPub} ───────────│  proof=HMAC(verifier, challenge)
 │ 校验批次/限速/首绑/revEpoch  │                        │
 │──────────── cert + 续期链 + hints ──────────────────▶│  存柜
 │◀════════ hello {cert, nonce, sig} ══════════════════▶│  双向验签
 │════════════ hello-ack {hostCert, sid} ══════════════▶│
 │◀──────────── svc/list → svc/open → http/req ────────▶│
```

要点：

- **先验 host 再交票**：guest 在输入口令/兑换码之前，先拿到 host 的 `hostCert` 与指纹并展示；防止"设备码钓鱼"（你在给 A 授权，实际给了 B）。
- **兑换走已加密信道**：直连时是 DTLS；中继时是 TLS + 应用层 X25519/AES-GCM。口令/码不出现在 URL、日志、板里。
- **host 不入站**：host 只主动连板和中继；直连候选由 host 在 `redeem` 响应里给出（或经中继交换），不把家庭 IP 写进公开板。
- **信任锚随票走**：邀请链接/二维码里带 `hostId + account 根公钥指纹 + hostCert`，guest 离线就能验完 host 证书链；板只负责把 `hostId` 解析成端点，**不承担信任**。这样即使板被换掉，也换不掉 host 身份。
- **票的交付形态**：`dsh://join?h=<hostId>&r=<rootFp>&c=<code>`（code 放 fragment，避免进访问日志）、二维码、CSV；码只出现一次，兑换后作废。

### 4.4 帧协议：一套帧，两条腿

沿用现有 `mesh-rpc` 信封，新增流帧：

```text
{ t: "req", id, op, body }        // 请求
{ t: "res", id, ok, result|err }  // 响应
{ t: "evt", topic, body }         // 事件（通知/名册/撤销）
{ t: "str", sid, seq, fin, data } // 流（HTTP body / 文件 / 媒体分片）
```

- 载体 A：WebRTC DataChannel（现有，DTLS 加密）。
- 载体 B：WSS 到中继，帧外面再套一层 `seal(box)`（X25519 + AES-GCM，复用 `link-crypto.js`），中继只看到密文。
- 同一套 `hello`、同一套 `cert` 验证、同一套 `ops`；切换载体对上层透明。
- 流控：每流窗口 256 KiB；断线重连按 `sid/seq` 续传；**不用超时判定失败**，只由对端 `res/err`、断链或调用方取消结束。

### 4.5 公网发现与 NAT

| 场景 | 路径 | 备注 |
|---|---|---|
| 同一 LAN | 现有组播发现 | 不变 |
| 同一 tailnet | 现有 tailscale 探测 | 不变 |
| 公网、双方可打洞 | Board → ICE/STUN → DataChannel | 优先；候选经中继交换，不落板 |
| 公网、对称 NAT/企业网 | Board → Relay（WSS） | 兜底；host 只需出站 443 |
| 纯媒体（电台） | WebRTC 直连 → TURN → 06 边缘 SFU/HLS | 沿用 06 的四级降级，不新造 |

### 4.6 安全边界

- **票即准入**：没有有效 cert，板只给公开 descriptor，中继拒绝配对，直连 `hello` 失败。
- **设备绑定**：cert 里 `sub.pk` 必须等于握手设备公钥；复制 cert 到另一台设备无效。
- **端到端**：中继腿用 X25519 + AES-GCM；中继无法解密，也无法伪造（帧带会话密钥 MAC）。
- **重放**：`nonce` 一次性、`challenge` 5 分钟、`connSeq` 单调；证书 `exp` 短。
- **撤销**：`revEpoch` 单调 + 单票黑名单；在线立即，离线到下次连接；敏感操作（开柜、提权、发码）要求 `revEpoch` 新鲜 ≤ 5 分钟，否则 fail closed。
- **限速**：板读、兑换、中继配对三层限速；错误统一，不泄露"票是否存在"。

## 5. 长会话：票的三段时间与柜内兑换

### 5.1 三段时间

| 段 | 字段 | 含义 | 谁能改 |
|---|---|---|---|
| 兑换窗口 | `nbf` ~ `nbf+24h` | 码/口令可换票的时间 | host |
| 租约 | `exp` | 当前证书到期；到期必须续 | host 预签或在线续 |
| 硬上限 | `hardExp` | 这张票绝对不能再用的时间 | 签发时固定，不可延 |

节目票：`hardExp = 散场 + 30 min`，续期链只有 1 段（或不续）。
游戏票：`hardExp = 测试窗口上限`（例如 8 小时/7 天），续期链 32 段 × 15 分钟。
子账号：`hardExp` 30 天，可滚动到新的 30 天；每次续期 host 在线检查 `passGen/revEpoch`。

### 5.2 续期链（离线可兑换）

```text
host 签发时：
  chain = [seg(1), seg(2), …, seg(N)]
  seg(i) = sign(hostKey, { cid, seq:i, nbf:i*every, exp:(i+1)*every, hardExp, revEpoch })
guest 柜内：
  到期前 1/4 租约 → 取出 seg(i+1) → 验签 → 替换当前 cert → 清零旧段
  任一段验签失败/超 hardExp → 标记 expired，停止服务
```

- **不需要 host 在线**，适合局域网活动、弱网、host 休眠。
- 代价：撤销在离线期间不生效；所以**敏感动作**（开柜、提权、发码）必须重新在线校验，普通收听/游戏可到 `hardExp`。
- 若 host 在线：优先 `renew.online`，每 15 分钟向 host 换新（host 可立即拒绝），链只作为离线兜底。

### 5.3 节目 vs 游戏

| | 节目（电台/演出） | 游戏测试 |
|---|---|---|
| 到期语义 | 散场即失效，不续 | 到 `hardExp` 才失效，期间可续 |
| 续期 | `none`（一段到底） | `chain` 或 `online` |
| 撤销 | 单票/整批/全场 `revEpoch` | 单票/批次/封测结束 |
| 名册 | 在场/迟到/早退 | 在线时长/崩溃上报 |
| 票面 | 场次、座位/分区（可选） | 构建号、功能位 |

### 5.4 撤销的收敛

| 操作 | 在线 | 离线 | 敏感操作 |
|---|---|---|---|
| 单票撤销 | 下一次请求即拒 | 下次连上 host 即拒 | 立即 fail closed |
| 整批撤销 | `revEpoch+1` 广播 | 回连时比对 | 立即 |
| 换组密钥 | 旧密钥解不开 | 回连失败 | 立即 |
| 手机丢失 | 手机证书撤销 + `revEpoch+1` | 同上 | 立即 |

### 5.5 本项目的真实形态：网页小游戏 + 电台语音

游戏不是原生游戏，而是 **AI 在 DSH agent 里写出来的网页**，由 host 用"类似 doc-server 的网页服务"发布，其他终端用 WebView 加载游玩；同时可以开电台语音。这个形态把很多问题简化了，也把两个要求提前了。

#### 5.5.1 游戏侧：网页 + WebSocket，底下就是同一条 WebRTC

```text
AI 在 host 上生成 game/（HTML/JS/CSS/assets）
  → host 起一个只监听 127.0.0.1 的网页服务（doc-server 式托管；它出厂 patch 是 0.0.0.0，必须改回回环）
  → descriptor 发布 { sid, kind:"web", ws:true, version:"<hash>", upstream:"127.0.0.1:PORT" }
  → guest 打开 dsh://host/sid/ → 本地代理 → 同一条 PeerConnection（DataChannel + 媒体轨）→ host
  → 网页里照常 new WebSocket("ws://127.0.0.1:<port>/ws")（标准写法，完全不感知 WebRTC）
  → 本地代理把 WS 帧映射到 DataChannel `game-control`；静态资源走 http/stream
```

- **页面只写标准 WebSocket/HTTP**；底下是 DataChannel 还是 WSS 腿，由 App 决定。AI 生成的代码不需要懂 WebRTC，换承载也不用改页面。
- **两条 DataChannel**：`game-control` 可靠有序（加入、结算、道具、聊天）；`game-state` 无序可丢（`ordered=false, maxRetransmits=0`，位置/输入高频包）。单条可靠通道会队头阻塞，快节奏必须分开。
- **资源不走 DataChannel**：首屏/大文件走 `http/stream`。大资源塞进 DC 会挤占同一条 PC 的带宽估计，最后受伤的是语音。
- **身份由代理注入**：host 代理写入 `X-DSH-Ticket`、`X-DSH-Conn`、`X-DSH-Joined`，剥掉客户端伪造的同名头；游戏后端不信网页自报身份。
- **版本与缓存**：每次 AI 改动生成内容哈希，URL 带 `/v/<hash>/`；同场锁同一版本；静态资源长缓存。
- **安全隔离**：游戏页独立 origin，CSP 禁外链/`eval`；WebView 不向游戏页暴露 App 的隧道/票柜 API。AI 生成的代码按不可信代码跑。

#### 5.5.2 语音 + 游戏共用一条 PeerConnection（你最初的直觉是对的）

**一条 PeerConnection 同时承载：一条 Opus 媒体轨 + 两条 DataChannel。** 一次 ICE/DTLS、一个 TURN 分配、一次重连、一份带宽估计，语音和游戏状态在同一条路径上同步，这是本项目的默认形态。

| 关注点 | 做法 |
|---|---|
| 优先级 | libwebrtc 的拥塞控制优先音频、DataChannel 是 best-effort；所以语音不会被游戏状态挤掉，但**游戏资源不能走 DC** |
| 连接归属 | **App 持有 PC**：建连、申请麦克风、管音频会话；游戏页只看到本地 WS。页面刷新/导航不会断语音 |
| 手机听 | `recvonly` 音频轨 + 两条 DC |
| 手机说 | `sendrecv` 音频轨 + `audio_session`/回声消除；这是 Tauri 最吃力的地方 |
| 失败耦合 | PC 挂了语音和游戏一起挂。保底：游戏腿回退 WSS 隧道（语音仍需 TURN），或语音单独一条 PC；P2 实测后定 |

**host 侧的现实约束（重要）**：媒体栈现在在 Electron 渲染进程（WebAudio 混音，见 SDD 06 D3），而 account-mesh 的 DataChannel 在 Node 主进程（`node-datachannel` 只做数据通道）。所以"一条 PC"要求**把访客侧 PC 挪到渲染进程**：渲染进程持有 PC（音频 + DC），Node 插件通过 IPC 把游戏帧转给渲染进程/游戏服务；否则只能两条 PC（主进程跑数据、渲染进程跑音频），NAT/重连各做一遍。

- host 端混音按 06 的"主播是混音器"：麦克风 + 音乐 + 坐客混成一路 Opus；小规模 P2P 网状，规模上来 TURN/SFU。
- 游戏页只放"静音/音量/谁在说话"的 UI，通过 postMessage 调 App 的音频控制；麦克风权限永远由 App 申请，不给网页。

#### 5.5.3 带宽账（先给量级，后面你实测校正）

| 流量 | 量级 | 说明 |
|---|---|---|
| 语音（每人） | 30–40 kbps | Opus 24–32 kbps + RTP/UDP 开销 |
| 语音（host 上行，P2P 网状） | N × 35 kbps | 10 人 ≈ 350 kbps；30 人 ≈ 1.05 Mbps；50 人 ≈ 1.75 Mbps |
| 语音（经 TURN/SFU） | host 1 路上行 + 中继 N 路 | 中继 3 Mbps 约 60–70 路 32 kbps（与 06 的口径一致） |
| 游戏首屏资源 | 0.5–10 MB/人 | AI 生成的页面差异大；同版本二次进入走缓存 |
| 游戏状态 | 1–20 kbps/人 | 回合制 <1 kbps；实时动作 20–50 kbps |
| 控制/心跳 | <1 kbps/人 | 隧道帧开销 |

**结论：稳态带宽由语音主导，首屏由游戏资源主导。** 优化顺序应是：先压游戏资源（分包/压缩/缓存/版本化），再压语音（DTX、单路混音、SFU），最后才是协议开销。

#### 5.5.4 你要做的体验/带宽实验（建议口径）

| 场景 | 变量 | 采集 |
|---|---|---|
| 局域网 / tailnet / 公网中继 | 三种承载 | 首屏时间、加入语音时间、卡顿次数 |
| 1 / 3 / 5 / 10 人 | 并发 | host 上行 kbps、中继 egress、CPU |
| 有语音 / 无语音 | 是否开麦 | 游戏输入延迟、语音抖动/丢包 |
| 资源 1 MB / 5 MB / 10 MB | 首屏 | 冷启动、二次进入（缓存命中） |

采集手段：host 代理按 `sid` 计字节；`RTCPeerConnection.getStats()` 取 `bytesSent/Received`、`packetsLost`、`jitter`、`roundTripTime`；手机侧记 `first-paint`、输入到渲染的 p95；中继侧记 egress。

**判据**：若语音占稳态带宽 >70%，优先做单路混音/SFU；若首屏 >3 s 且资源 >5 MB，优先拆包与缓存；若输入到渲染 p95 >150 ms，才考虑把游戏状态从 WSS 换到 WebRTC DataChannel。

#### 5.5.5 语音和游戏对"实时"的要求正好相反

容易误判的一点：**语音不是"实时性差"，它是延迟最敏感的那一路**；游戏数据也不是"整体要快"，而是"状态要新鲜、事件要可靠"。

| 维度 | 语音 | 游戏状态（位置/输入） | 游戏事件（加入/结算/道具） |
|---|---|---|---|
| 码率 | 恒定 30–50 kbps（含开销） | 突发，均值 1–20 kbps | 极低，事件触发 |
| 包节奏 | 每 20 ms 一帧，连续 | 10–30 Hz 快照 | 不定 |
| 延迟预算 | 会话 <150 ms 单程；听 <250 ms | 动作 50–100 ms；休闲 100–200 ms | 200–500 ms 可接受 |
| 丢包策略 | PLC/FEC 掩盖，不重传（迟到的包没用） | 下一帧快照覆盖，可丢 | 必须可靠、有序 |
| 传输 | RTP/SRTP（UDP） | SCTP DataChannel，无序可丢 | SCTP DataChannel，可靠有序 |
| 拥塞待遇 | 优先保护 | best-effort | best-effort |
| 失败表现 | 卡顿、机械音、延迟累积 | 瞬移、回拉、橡皮筋 | 状态错乱、结算丢失 |

**一条 PC 里其实是两条传输**：媒体走 SRTP/RTP，数据走 SCTP over DTLS；两者共享同一条 ICE 路径和 DTLS 握手，但队列、重传、抖动缓冲各自独立。所以"一条连接"省的是 NAT/握手/重连，不是把语音塞进 DataChannel。

工程规则：

1. **游戏按 tick 发包，不要按事件发包**：20 Hz 打包一次快照，比每次输入发一条省得多；小包多了会挤占 pacer。
2. **状态用不可靠通道**：`ordered=false, maxRetransmits=0`；丢了等下一帧，不要重传旧状态。
3. **事件用可靠通道**：结算、道具、加入/离开；可靠通道会队头阻塞，所以绝不能用它跑高频状态。
4. **语音不重传**：Opus 20 ms 帧 + FEC/DTX + 30–80 ms 抖动缓冲；宁可丢一帧，不要等重传。
5. **资源不进 DC**：首屏走 HTTP；DC 只承载小状态与小事件。
6. **监控分 kind 看**：`getStats()` 里音频看 `jitter/packetsLost/ concealedSamples`，数据看 `bytesSent/Received` 与 `bufferedAmount`，不要混在一起算平均值。

> 另一种"流式"要区分：HLS/LL-HLS 也是流式，但延迟 2–6 秒，适合单向收听；"一起语音"必须 WebRTC（100–300 ms），不要拿 HLS 当语音。

## 6. 服务发布与手机浏览

### 6.1 service descriptor

host 在 descriptor 里发布服务，而不是开放端口：

```jsonc
{
  "sid": "radio-42",
  "name": "凌晨两点的合成器电台",
  "kind": "web" | "ws" | "http",      // 网页游戏/电台页用 web；纯接口用 http
  "version": "sha256:…",              // 内容哈希；同场玩家锁同一版本
  "ws": true,                          // 是否需要 WebSocket upgrade
  "upstream": "127.0.0.1:8787",       // 只在本机
  "tls": "verify" | "pin" | "off",    // 上游是否 HTTPS，怎么校验
  "pin": "sha256/…",                  // tls=pin 时的 SPKI 指纹
  "auth": "cert" | "session",
  "requireTLS": true,                 // 强制 HTTPS 语义
  "maxConns": 200
}
```

- guest 只能看到自己 `acts/scope` 允许的 `sid`；descriptor 本身公开可读，但**连不上**没有票。
- host 侧代理只连 `upstream` 白名单，禁止任意 SSRF；路径规范化，禁止 `..`。

### 6.2 隧道内 HTTP

- 新增 ops：`svc/list`、`svc/open`、`http/req`（小请求）、`http/stream`（大响应/流式）。
- P0 只做 `http/req`（静态页/JSON，单次响应 ≤ 2 MiB）；**P1 必须加 `ws/open` 与 `http/stream`**——网页小游戏的多人逻辑默认走 WebSocket，没有 WS upgrade 就只能做单机页。
- WebSocket 升级在本地回环代理里完成：`Upgrade: websocket` → `ws/open {sid, path, headers}` → 双向帧；承载可以是同一条 PC 的 `game-control` DataChannel（首选），也可以是 WSS 隧道腿（兜底）。代理剥掉客户端伪造的身份头，注入 `X-DSH-Ticket/Conn`。
- WebSocket 在 P1 就上（`ws/open` + `str` 帧）；媒体流放 P2。

### 6.3 手机怎么渲染

**原则：WebView 不直连自签证书，TLS 在 Rust 里终止。**

```text
WebView ── http://127.0.0.1:<ephemeral> ──▶ Rust 本地代理 ── 隧道 ──▶ Host 代理 ──HTTPS──▶ 上游服务
```

- `http://127.0.0.1` 是 W3C 定义的 **potentially trustworthy origin**（安全上下文），Service Worker、WebCrypto、Cookie 都正常；同设备回环不经过网络，不需要 TLS。
- Rust 代理到上游按 `tls` 策略校验：`verify` 用系统根，`pin` 比对 SPKI，`off` 仅限明示的内网服务。
- 这样做的收益：iOS/Android 的 WebView 证书回调（`onReceivedSslError` / `didReceive challenge`）完全不需要碰；Tauri 没有 `setCertificateVerifyProc` 也不影响。
- 自定义协议（`dsh://`）只用于 App 自己的页面，不用于第三方服务页——避免自定义协议与 Cookie/流式加载的坑。
- **每个服务一个临时端口**（或同端口按 `sid` 路径前缀 + 独立 Cookie 名），避免同一 origin 下多个服务的 Cookie/Storage 互相串。

### 6.4 强制 HTTPS 与"不同时期的用户"

- `requireTLS=true` 的服务，host 代理拒绝非 TLS 上游；手机侧只接受 `https://` 上游。
- 每次连接 host 生成 `connSeq`（单调）、`joinedAt`、`ticketId` 哈希、`role`：
  - 注入请求头 `X-DSH-Conn`、`X-DSH-Joined`、`X-DSH-Role`（上游可读）；
  - 下发签名 Cookie `dsh_sess`（绑定 `cid + connSeq + epoch`），服务端可区分早鸟/迟到/重连；
  - 名册记录 `{connSeq, device, joinedAt, lastSeen}`，场控可看到"谁是什么时候进来的"。
- 重连 = 新 `connSeq`，旧会话按 `lastSeen` 过期；不把"连接时长"当权限。

### 6.5 外部浏览器（可选，不做）

若以后要让普通浏览器直接打开，需要：公网域名 + 每票子域 + 公网 CA（Let's Encrypt DNS-01）或让用户安装私有 CA。两条都破坏"不碰系统信任库"的初衷，故本期只支持 App 内打开。

## 7. 手机端：Tauri 方案

### 7.1 分层

```text
┌─────────────────────────────────────────────┐
│ UI（WebView：票夹/服务/通知/审批/设置）        │
├─────────────────────────────────────────────┤
│ Rust core                                    │
│  tunnel（DataChannel / WSS 两条腿）           │
│  cred（cert 验签、续期链、柜内兑换）           │
│  vault（NCV2S 兼容；私钥在 SE/StrongBox）      │
│  proxy（本地回环 HTTP，TLS 终止）              │
│  notify / approve（签名、生物识别）            │
└─────────────────────────────────────────────┘
```

- 手机**不是 DSH shell**：不渲染 DSH 底栏、不加载会话列表；只保留票夹、服务目录、通知/审批、设置五个面。
- 手机**不加载** DSH 的 agent 运行时、不挂工具面、不跑模型；它只做四件事：收消息、审批、看服务、管票。
- 通知走系统通知（Tauri notification 插件）；审批走 App 内页面 + 生物识别；后台只做重连与拉取，不做常驻隧道（iOS 不允许）。

### 7.2 节点权限层级

| 层级 | 角色 | 能做什么 | 典型设备 |
|---|---|---|---|
| T0 | 陌生 | 只能读公开 descriptor | 任意 |
| T1 | 门票 guest | 票面 `acts/scope` 内的服务 | 测试玩家、听众 |
| T2 | 子账号 sub | 会话/文件/服务（按 acts），可持票 | 助手、长期测试者 |
| T3 | owner-device | 主账号桌面：签发普通票、管理设备 | 主播桌面 |
| T4 | phone-approver | 根密钥保管、提权、发码、开柜审批、注销设备 | 主账号手机 |

- T4 不是"更多 ops"，而是"能批准 T3 的高危动作"；T4 自己发起的普通请求仍受 `acts` 限制。
- 手机可同时是 T4 和 T1/T2（自己拿票看服务），但两种身份分开记账。

### 7.3 手机作为保险柜

- **根密钥**：`account.root` 的私钥只在手机的 Secure Enclave/StrongBox 内（或由它包裹），桌面只持 30 天设备证书。
- **审批密钥**：独立于根密钥的 `approval.key`，每次签名要求生物识别；`opDigest + challenge + nonceCounter` 一次性。
- **票柜**：手机保存自己的票、续期链、host 指纹；可离线查看、离线续期（链模式）。
- **灾备**：根密钥导出用 2-of-3（手机芯片/纸质恢复码/第二台设备）；恢复动作本身要审批 + 延迟 + 全设备告警。
- **可选：手机当小型托管方**（`vaultMode=hosted`）：只托管票、配置、名册这类小对象，不托管大归档；手机离线时 A 端回退直连 B 或完整拉取。这样"手机本身是保险柜"既指钥匙，也指柜子。

### 7.4 交互消息（"到期/报错/超时/临时授权"）

| 事件 | 触发 | 手机动作 |
|---|---|---|
| `cred.expiring` | 租约剩余 1/4 | 提示续期（链模式自动；在线模式拉 host） |
| `cred.expired` | 到 `hardExp` | 停止服务、显示原因、可重新购票 |
| `svc.error` | host 代理 5xx/上游不可达 | 展示错误码与重试；可转诊断 |
| `op.timeout` | host 侧**操作**超时（非模型请求） | 展示"操作超时"，给重试/取消；不实现模型层超时 |
| `auth.temp` | 手机批准了临时授权 | 显示剩余时长、可提前撤销 |
| `approval.request` | 提权/发码/开柜/加设备 | 展示 host 渲染的摘要 + 指纹 → 生物识别 → 签名 |
| `roster.update` | 有人入场/被踢 | 场控视图 |

> "超时"只作为 host 上报的**事件**展示；DSH 不设应用层模型请求超时，手机也不设。

### 7.5 Tauri vs Electron：自由度对照

| 维度 | Electron | Tauri 2 |
|---|---|---|
| 渲染引擎 | 自带 Chromium，版本统一 | 系统 WebView（WKWebView / WebView2 / WebKitGTK / Android WebView） |
| 主进程 | Node.js | Rust |
| 渲染层 Node | 有 | 无（只能 IPC） |
| 证书校验钩子 | `setCertificateVerifyProc` / `certificate-error` | **无公开等价 API**（[issue #4039](https://github.com/tauri-apps/tauri/issues/4039) 讨论过忽略证书错误，主线未提供） |
| 自定义协议 | `protocol.handle`，可流式 | `register_*_protocol`；Windows/Android 可映射 `https://<scheme>.localhost`；流式支持有限 |
| 原生能力 | Node 生态 | Rust + 官方/社区插件 |
| 移动端 | 无官方支持 | iOS/Android 官方支持 |
| 包体/内存 | 大 | 小一个量级 |
| 调试 | Chromium DevTools | 平台 WebView 调试（移动端受限） |
| 安全边界 | 需自己收敛 | 默认更严（capabilities/scope），但历史上出过 `is_local_url` 误判（2.10.3 修复），要跟版本 |

**结论**：

- "像 Electron 一样自由"——**应用层可以**：Rust 能开 socket、起本地 HTTP、读密钥库、调系统通知、做后台服务、写文件、跑子进程；桌面端还能开多窗口、托盘、自动更新。
- "像 Electron 一样自由"——**WebView 层不行**：系统 WebView 版本碎片化、不能替换内核、没有证书钩子、自定义协议能力受平台限制。
> 先澄清一个常见误解：Tauri 嵌入的是**系统 WebView 组件**（macOS/iOS 的 WKWebView、Windows 的 WebView2、Android 的 System WebView），不是打开系统浏览器 App。它和系统浏览器共享内核，但进程、Cookie、证书策略都由 App 自己控制；"系统自带浏览器"这个说法只在"用系统内核"这一层成立。

- 本方案把"需要 WebView 自由"的部分（TLS、代理、流）全部挪到 Rust，WebView 只负责渲染本地回环页，因此**Tauri 的限制不构成阻塞**。
- 如果未来一定要"内嵌 Chromium + 证书固定"，那应选 Electron/CEF，而不是 Tauri；但那会把手机端排除在外。

### 7.6 建议的 Rust 组件

| 组件 | crate/插件 | 用途 |
|---|---|---|
| 异步运行时 | `tokio` | 隧道/代理/定时任务 |
| TLS | `rustls` + `webpki-roots` | 上游 HTTPS 校验、WSS |
| HTTP | `hyper` / `axum` | 本地回环代理 |
| 序列化 | `serde` + `serde_json`（JCS） | 帧/证书 |
| 签名 | `ed25519-dalek` | cert 验签、设备证明 |
| 密钥交换 | `x25519-dalek` + `hkdf` + `aes-gcm` | 中继腿 E2E |
| 口令 | `argon2` | 子账号 verifier（桌面端 Node 用 `argon2` 包） |
| WebRTC | `webrtc`（webrtc-rs） | 直连腿（P2 起） |
| WSS | `tokio-tungstenite` | 中继腿（P0 起） |
| 通知 | `tauri-plugin-notification` | 系统通知 |
| 生物识别 | `tauri-plugin-biometric` | 审批签名前确认 |
| 深链 | `tauri-plugin-deep-link` | `dsh://join?…` |
| 密钥库 | `tauri-plugin-stronghold` 或平台 keystore 插件 | 根密钥/票柜解锁 |
| 存储 | 自研 NCV2S（与桌面同格式） | 票柜 |

### 7.7 框架选型补充：Flutter vs Tauri（待拍板，倾向 Flutter）

§7.1–7.6 以 Tauri 为基线写。若团队已有 Flutter 经验，按下面这张表重新权衡；**协议层（DSH-CERT、帧、柜内续期）不随框架变化**，换框架只换壳。

| 维度 | Flutter | Tauri 2 | 本项目权重 |
|---|---|---|---|
| 团队熟悉度 | 已有经验，直接开工 | Rust + 移动工具链 + WebView 调试，学习曲线陡 | **高** |
| WebRTC / 电台音频 | `flutter_webrtc` 封 libwebrtc，DataChannel/音频/回声消除成熟 | **WebView 里可直接跑 JS WebRTC**（WKWebView/Android WebView），收听够用；Rust 侧无 WebRTC，麦克风/后台音频要原生插件 | 中（手机只当听众时） |
| 隧道（WSS 腿） | `web_socket_channel` 够用 | `tokio-tungstenite`，同样够用 | 中 |
| 服务页 WebView | 平台 WebView（`webview_flutter` / `flutter_inappwebview`） | 平台 WebView | 中（两边一样） |
| TLS 终止 / 本地代理 | `dart:io HttpClient` + `HttpServer`，可 pin | `rustls` + `hyper`，可 pin | 中（两边都能做） |
| 安全存储 / 生物识别 | `flutter_secure_storage` + `local_auth`，成熟 | 插件较新，移动端要自己补 | 高 |
| 后台 / 通知 | `flutter_foreground_task`、`flutter_local_notifications`、FCM 成熟 | 需写 Kotlin/Swift，通知插件可用但推送要自己接 | 高 |
| UI 一致性 | 自绘 Skia，双端一致 | 系统 WebView，双端有差异 | 中 |
| 复用 DSH Web UI | 不能，要重写 5 个页面 | 可以复用 React/样式 | 低（手机只 5 个面） |
| 包体 | ~20–25 MB | ~8–12 MB | 低 |
| 移动端成熟度 | 高，生态大 | 中，v2 移动仍在补 | **高** |
| 未来桌面复用 | Flutter desktop 可用 | Tauri desktop 强 | 低（桌面已有 DSH） |

**结论（条件式）**：

| 条件 | 选择 |
|---|---|
| 手机只当听众、能接受 **WebView 持有 PC**（音频在页面里播）；不开麦、不做后台音频 | **Tauri**：包体小、网页游戏 + WebView 音频够用；代价是 App 对音频控制弱、页面导航会断语音 |
| 手机要开麦（连麦/坐客）、后台电台，或要求 **App 统一持有那条 PC**（音频 + DataChannel，页面刷新不断语音） | **Flutter**：`flutter_webrtc` 能同时管音频轨和 DC，`audio_session` 处理回声/路由；Tauri 这条路要自己补原生音频 |
| 团队不想学 Rust / 移动构建链，且包体不是硬指标 | **Flutter** |
| 用户量大、更新频繁、按流量计费，包体是硬指标 | **Tauri**（但先按 §7.7.1 把账算清） |

修正上一版判断：之前把"WebRTC 只有 Flutter 能做"当成硬条件，这是不准确的——**手机作为听众时，WebView 里的 JS WebRTC 就能收流**，不需要 Rust/native WebRTC。真正需要原生音频的只有"后台播放/麦克风"这两个场景。你是消费端，不是主播端，所以 Tauri 的短板没有上一版说的那么致命。

#### 7.7.1 包体与分发成本（按自建 OSS 场景算账）

**先对齐口径**：不要拿"Flutter universal APK"对比"Tauri 单 ABI APK"。

- Android：Flutter 用 `--split-per-abi` 后 arm64 包通常比 universal 小 40%–50%；Tauri 也应只发单 ABI。两者差距会从"2 倍多"缩到"1.3–1.6 倍"。
- iOS：App Store 有 App Thinning；走 OSS/TestFlight 时是通用 IPA，Flutter 的绝对体积劣势更明显，但 iOS 本来就不适合"OSS 直接下载安装"。
- 功能完整的 Tauri 会长大：加 `rustls`、`tokio`、SQLite、通知/生物识别插件、`webrtc-rs`（若走原生）后，Rust 二进制会从几 MB 涨到十几 MB；拿"Hello World 级 Tauri"对比"功能完整的 Flutter"不公平。

**带宽公式**：

```text
每次发布的额外流量 = 下载量 × (Flutter 单包 − Tauri 单包)
年成本 ≈ 每次发布额外流量 × 年发布次数 × OSS 外网单价
```

举例（按 0.25–0.5 元/GB、每月 1 版、单包差 4 MB）：

| 下载量/版 | 额外流量/版 | 额外成本/版 | 年额外成本 |
|---|---|---|---|
| 5 万 | 200 GB | 50–100 元 | 600–1,200 元 |
| 50 万 | 2 TB | 500–1,000 元 | 6,000–12,000 元 |
| 500 万 | 20 TB | 5,000–10,000 元 | 6–12 万元 |

结论：**百万级用户、月更节奏时，包体差才是一笔值得认真优化的钱；十万级以下，省下的流量通常小于"补原生 WebRTC/后台"的一个人月成本。** 如果你的用户量已经在百万级，Tauri 的包体优势成立，可以把它当 tiebreaker。

**把差距继续压小的手段**（两边都适用）：

- Android 按 ABI + 密度分包；Flutter 开 `--tree-shake-icons --obfuscate`；Tauri 开 LTO/`opt-level=z`/`strip`。
- 首发包只带票夹 + 隧道 + WebView，WebRTC/媒体作为可选模块后置（Flutter 的 `flutter_webrtc` 是包体大头之一）。
- 增量更新：Flutter 的引擎在同大版本内不变，bsdiff 补丁通常只有几 MB；Tauri 的 Rust 二进制变化也可做 delta。自建 OSS 分发要自己实现，但一次投入长期省流量。
- OSS 前面挂 CDN、开压缩、设长缓存；版本目录不可变，避免回源放大。

**iOS 的现实**：如果目标用户包含 iPhone，"传到自己的 OSS 让用户下载"这一步本身走不通（企业证书/Ad Hoc 有设备和合规限制）。iOS 侧要么 App Store（有 thinning，包体影响小），要么 TestFlight（90 天/1 万测试者）。**iOS 的分发约束比包体大小更值得先决定。**

**若选 Flutter，建议的落地栈**：

| 能力 | 选型 |
|---|---|
| UI | Flutter + Material 3（或团队现有设计系统） |
| 状态 | Riverpod / Bloc（按团队习惯） |
| 隧道 P0 | `web_socket_channel`（WSS 中继腿） |
| 隧道 P1 | `flutter_webrtc`（DataChannel；与桌面 `node-datachannel` 同为 WebRTC 标准） |
| 服务页 | `webview_flutter` 或 `flutter_inappwebview` + 本地 `HttpServer` 代理 |
| 证书/加密 | `cryptography`（Ed25519/X25519/AES-GCM/HKDF）+ `hashlib`（Argon2id） |
| 柜子 | `flutter_secure_storage` 存解锁密钥；票/续期链用 AES-GCM 文件（NCV2S 同构） |
| 生物识别 | `local_auth` |
| 通知 | `flutter_local_notifications`；需要后台唤醒时再加 FCM/APNs |
| 后台 | `flutter_foreground_task`（Android）；iOS 只做回前台重连 |
| 深链 | `app_links` |
| 媒体（P4） | `flutter_webrtc` + `audio_session` |

**跨端一致性风险**：Dart 版会把证书/帧/柜子逻辑重写一遍，必须和 Node 实现共用一套测试向量（`spike/fixtures/cred/*.json` + 帧黄金样本），否则"两端都自测通过、互通失败"。若以后想把核心收成一份，再用 `flutter_rust_bridge` 把 Rust 核心接进来，协议不变。

## 8. 精简账本：相对两份旧文档砍了什么

| 旧设计 | 本方案 | 省掉的复杂度 |
|---|---|---|
| 五层模型（域/设备/主体/能力/对象） | 三实体（Account/Principal/Device）+ 一证书 | 少两层概念、少一套命名空间 |
| DSH-CAP 与 ticket 两套证书 | 一套 DSH-CERT，`kind` 区分 | 少一套编解码/验证/撤销 |
| PAKE（SPAKE2/OPAQUE） | Argon2id verifier + 限速 + 加密信道 | 不自己写密码学 |
| X.509/CA/mTLS/系统信任库 | Ed25519 证书 + 应用层身份 | 不维护 CA、不碰证书库 |
| 手机独立网关认证 | cert 直接挂 `hello` | 少一个网关服务 |
| 第三套 VPN（Nebula/WireGuard） | 可达性平面（板/中继/直连） | 不装 TUN、不要 VPN 权限 |
| 8 个新模块、P0–P7 | 5 个组件、P0–P4 | 一个人能起步 |
| 16 条威胁 + 12 条不变量 | 12 条威胁 + 攻击清单 | 保留关键项，去掉重复 |

保留的硬约束：证书只能收窄不能扩张、撤销是硬状态、敏感操作 fail closed、发码/审批不进模型面、票的 TTL 不是请求超时。

## 9. 分期落地

| 期 | 交付 | 验收 | 依赖 |
|---|---|---|---|
| **P0 证书与柜** | `cred.js`（签发/验证/续期链）、`vault/creds` 存储、桌面 host 发票给桌面 guest、`/api/cred/*` | 改一位即验签失败；复制票到另一设备打不开；柜内续期成功；到期拒绝 | 无 |
| **P1 公网平面** | Board（签名快照）、Relay（WSS 配对）、host 出站连接、公网兑换入口、`ws/open` 升级（网页游戏先导） | 无公网入站的 host 可被 guest 连上；网页游戏能经隧道开 WebSocket；中继抓包看不到明文；打洞失败自动降级 | P0 |
| **P2 手机壳** | Tauri App：票夹、隧道（WSS 腿）、通知、审批、深链 | 手机扫码取票 → 连上 host → 收通知 → 批一次提权；iOS 后台回前台自动恢复 | P1 |
| **P3 服务发布** | `svc/*`、`http/req`、本地回环代理、上游 TLS、`connSeq` 名册 | 手机打开 host 网页服务；`requireTLS` 生效；早/晚连接可区分；断线重连 | P2 |
| **P4 根托管与批量** | 手机 SE 根密钥、`elevate`、批次发票、跨账号 `cross` 票 | 手机丢失可注销；提权重放被拒；批量 500 张可回收 | P3 |

排期建议：P0/P1 可并行（不同人）；P2 等 P1 的 WSS 协议稳定；P3 依赖代理与帧流；P4 最后做，避免过早引入根密钥托管。

### 9.1 P0 的最小文件与 op 清单

| 文件 | 职责 | 说明 |
|---|---|---|
| `src/cred.js` | 证书编解码、签发、验签、续期链 | 复用 `identity.js` 的 `signBytes/verifyBytes`、`util.js` 的 JCS |
| `src/cred-store.js` | 柜内存取（`kind=cred`） | 复用 `vault2.storeObject`，不新造容器 |
| `src/cred-routes.js` | `/api/cred/issue`、`/api/cred/list`、`/api/cred/revoke` | 仅本机同源；手机不走这里 |
| `spike/p0-cred.mjs` | 签发/验签/续期/篡改/换设备 | 与现有 `spike/p0-*.mjs` 同风格 |

新增 op（先走现有 `mesh-rpc`）：

```text
cred/preauth { hostId, subId? }                 → { salt, challenge }
cred/redeem  { code, proof, devPub, nonce }     → { cert, chain, hostCert, hints }
cred/renew   { cid, seq }                      → { cert }        // 在线模式
cred/status  { cid }                           → { exp, hardExp, revEpoch, state }
svc/list     {}                                → [{ sid, name, tls, auth }]
svc/open     { sid }                           → { connSeq, joinedAt, token }
http/req     { sid, method, path, headers, body } → { status, headers, body }
```

P0 验收脚本要覆盖：证书改一位、换设备、过期、续期跨 `hardExp`、撤销后重连、`revEpoch` 落后。

## 10. 攻击面与验收清单

| # | 攻击 | 预期 |
|---|---|---|
| A1 | 拿别人的 cert 在自己设备上用 | `sub.pk` 不匹配，拒绝 |
| A2 | 改 cert 的 `acts/exp/aud` 一位 | 验签失败 |
| A3 | 重放 `hello` / 审批 | `nonce`/`challenge`/`nonceCounter` 拒绝 |
| A4 | 中继偷看/篡改 | AES-GCM 解密失败；中继无法伪造 |
| A5 | 过期票继续用 | `exp`/`hardExp` 拒绝；链段用完即停 |
| A6 | 被撤销的设备重连 | `revEpoch` 落后，拒绝 |
| A7 | 门票转卖 | 首绑设备 + 一次性核销 + `connSeq` 异常告警 |
| A8 | 手机号补卡 | 号码不进认证；提权要手机私钥签名 |
| A9 | 恶意 host 钓鱼 | 兑换前展示 host 指纹；票绑定 `aud.host` |
| A10 | 恶意 guest 读别人的服务 | `acts/scope` + host 代理白名单 |
| A11 | 服务端 SSRF | 上游白名单 + 路径规范化 |
| A12 | WebView 加载任意页面/协议逃逸 | CSP + capabilities + 只允许本地回环/内置页；跟进 Tauri 安全版本 |
| A13 | 根密钥丢失 | 2-of-3 恢复 + 延迟 + 全设备告警 |
| A14 | 用量/预算被票卡住 | 票只限制入场与能力，不限模型请求数/累计用量 |

**上线前硬门槛**：`mcpToken` 为空必须拒绝；doc-server 非 loopback 必须带票证；公网中继必须 TLS + E2E；手机端不得把票/私钥写入日志。

## 11. 未决问题

1. **Board 放哪**：复用 06 的边缘/对象存储，还是先用一台 DSH 节点兼职？建议 P1 先对象存储（最省），P2 再上边缘。
2. **中继容量**：06 的 3 Mbps 只能承载控制与小页面；媒体中继要另算，P3 前给带宽预算。
3. **手机后台**：iOS 不允许常驻 socket；是"回前台重连 + 本地通知"还是申请有限后台任务，需要真机验证。
4. **电台播放**：手机听电台走 WebRTC 音频（webrtc-rs）还是 HLS？前者延迟低但要集成媒体栈，后者简单但延迟高。
5. **外部浏览器**：是否永远只支持 App 内打开？若要做，需公网域名 + 每票子域 + 公网 CA。
6. **票的转让语义**：严格绑设备（不可转让）还是允许"转赠一次"（换绑 + 旧设备踢出）？建议前者，转赠走退票重发。
7. **移动端框架**：按 §7.7 的条件表定；如果手机只做前台收听，Tauri 的包体优势成立；如果要后台电台/麦克风，选 Flutter。
8. **iOS 后台**：WSS 在后台被挂起；是否接受"通知延迟到回前台"，还是引入 APNs 静默推送？
