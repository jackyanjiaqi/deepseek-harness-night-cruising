## 0. 结论先行

| # | 结论 | 依据 |
|---|---|---|
| D1 | **口令只用来「证明持有票」，永远不直接充当密钥材料。** 口令 → PAKE（SPAKE2 / OPAQUE）→ 会话密钥；口令本身不进日志、不进磁盘明文、不做 `sha256(password)` 直接当 KDF。 | 口令直接做 KDF 会被离线字典攻击；PAKE 让「拿到口令的人」只能登录一次，不能离线爆破（[RFC 9382 SPAKE2](https://datatracker.ietf.org/doc/rfc9382/)、[OPAQUE 草案](https://datatracker.ietf.org/doc/draft-irtf-cfrg-opaque/)） |
| D2 | **子账号 = 一张「票根 + 入场凭证」的组合**，不是一个小账号。票根（`ticket_id`）稳定、可吊销、可审计；入场凭证（口令派生的会话令牌）短时、可轮换、绑定设备。 | Ticketmaster SafeTix 每 15 秒换码而票根不变（[帮助页](https://help.ticketmaster.ca/hc/en-us/articles/26584359203473-Why-do-my-tickets-have-a-moving-barcode)）；Google Wallet RotatingBarcode 用 TOTP 轮换（[文档](https://developers.google.com/wallet/tickets/events/resources/rotating-barcodes)） |
| D3 | **权限由「票根 + 设备绑定的会话令牌」共同决定，二者缺一不可。** 票根决定「能做什么」（权限等级/能力位），会话令牌决定「谁在做」（设备身份）。 | DPoP 把令牌绑到持有私钥的客户端，令牌被偷走也不能在别的设备重放（[RFC 9449](https://datatracker.ietf.org/doc/html/rfc9449)）；Macaroons 用链式 HMAC 做「只能收窄、不能放宽」的离线衰减（[NDSS 2014](https://research.google/people/arnarbirgisson/)） |
| D4 | **手机是「信任节点 + 授权中心 + 保险柜钥匙」，不是 Agent。** 手机持有独立设备密钥，负责强通知与人工确认；保险柜的开柜钥匙由手机派生并只在已认证链路上释放。 | Tailnet Lock 用「签名节点」给新节点签名，未签名节点被锁出（[Tailscale 文档](https://tailscale.com/docs/features/tailnet-lock)、[lock CLI](https://tailscale.com/docs/reference/tailscale-cli/lock)）；Cloudflare Access 用短时证书替代长期凭证（[changelog](http://cloudflare-docs.cloudflare-docs.workers.dev/cloudflare-one/changelog/access/)） |
| D5 | **「手机号一致 ⇒ 子账号提权到主账号等级」这条规则必须改写。** 不能只看手机号，必须同时满足：手机设备密钥已与主账号绑定、子账号票根处于有效期、提权是显式的一次授权而不是隐式推断。 | 仅凭手机号一致属于「单一属性推断权限」，可被 SIM 换卡/号码复用击穿；同类系统的正确做法是「设备密钥 + 显式绑定 + 可撤销」（见 §5） |
| D6 | **门票（发给大量测试玩家/听众）与子账号是同一套机制的两个档位**：门票是「低权限、短时、批次化」的子账号；子账号是「长期、可提权、可托管」的门票。 | Steam Playtest 用「名额 + 账号授权」而非裸码（[文档](https://partner.steamgames.com/doc/features/playtest)）；Discord 邀请用 `max_uses + max_age + temporary`（[邀请对象](https://discord.com/developers/docs/resources/invite)） |
| D7 | **临时授权必须「到期即失效、撤销即断链、换钥即回收」三条同时成立**，且都不依赖对方配合。 | TestFlight 构建 90 天硬过期（[文档](https://developer.apple.com/testflight/)）；撤销是持久状态而不是删除条目（本仓 rc.13 修复经验，见 `docs/daily/20261127/account-mesh信任交互修复.md`） |
| D8 | **保险柜钥匙不能由「数据所有者」单方面保管**：所有者只持有根密钥，开柜票据一代一用、绑定设备、带挑战与签名；手机作为「钥匙保险柜」时只做「票据的中转与人工放行」，不存明文内容。 | NCV2 现有协议：`vault/open` 返回 `K_g + K_{g+1}`，签名绑定 `depositId/gen/archiveSha/challenge/expiresAt`（`plugins/account-mesh/src/vault2.js`）；RFC 8693 的 `act` 链要求「谁代表谁」显式记录（[Token Exchange](https://datatracker.ietf.org/doc/html/rfc8693)） |

## 1. 现状核实（本仓代码为准）

### 1.1 账号身份只有「主账号」一层

`plugins/account-mesh/src/account.js` 只读 `deepseekAccount.getPlatformSession()` / `getDeviceIdentity()`，产出 `{ userId, deviceId, accountTag }`。`accountTag = sha256("dsh-mesh/v1:" + userId)` 前 22 字符（`src/identity.js`），**发现层只认这个 tag**：`src/discovery.js` 收到 `frame.tag !== this.accountTag` 就计入 `otherAccounts` 并丢弃。

→ 结论：当前没有任何「子账号」概念。两个不同口令的终端若登录同一 `userId`，会被当成同一账号下的两台设备；若登录不同 `userId`，彼此完全看不见。**子账号必须新增一层「票根身份」，不能复用 `userId`。**

### 1.2 信任表是「设备级」的，没有「等级」维度

`src/trust.js` 每条记录是 `{ deviceId, name, publicKey, fingerprint, accountTag, trustedAt, lastSeen, address, port, revoked, revokedAt }`，只有「信任 / 撤销」二元状态，`revoked` 是持久状态（`save()` 写入 `version: 2`）。

`src/mesh.js`：
- `refreshPendingTrust(peer)` 在 `autoTrustSameAccount && entry === undefined` 时排队一条待确认请求；
- `onSignal` 对未信任设备只排队、不发信令；
- `connect()` / `call()` / `serve()` 全部用 `trust.isTrusted()` 把关。

→ 结论：信任表可以承载「等级」，只需在条目上加 `role` / `ticket` / `expiresAt` / `capabilities` 字段，**不必新建第二张表**。

### 1.3 只读数据面是固定白名单

`src/data.js` 的 `runOp` 只接受 `sessions/list`、`sessions/events`、`sessions/index`、`workspaces/list`、`files/list`、`files/stat`、`files/read`；文件访问被 `allowedRoots()`（`allowRoots` + `workspaceRegistry` + 会话 cwd）限制在 `realpath` 之后的根内。

→ 结论：权限分级可以直接落在「op → 能力位」的映射上：门票档只给 `sessions/*`，子账号档再加 `files/*`，主账号档再加保险柜与管理路由。

### 1.4 托管保险柜（NCV2）已具备「一代一用钥匙」

`src/vault2.js`：
- A（观看方）存 `.hdr` + `.dat`，`.dat` 用随机 DEK 加密，`.hdr` 里 DEK 被 `K_g` 包裹；
- B（所有者）持 `root.key` + `ledger.json`，`derive(depositId, peerId, archiveSha, gen) = HKDF(rootKey, depositId, "dsh-mesh/vault/v2/K|peer|sha|gen")`；
- `hostOpen` 校验 `peer/gen/archiveSha/kind/variant`，返回 `K_g`、`K_{g+1}`、`expiresAt`、`fresh`，并用 `signBytes(identity.privateKey, payload)` 签名；
- `hostPrepare` 对同一 `(peer, kind, objectId, variant)` 把旧 deposit 标 `superseded`；
- `revokePeer` 把该 peer 全部 deposit 标 `revoked`；
- 策略 `ownerPolicy()`：`release ∈ {auto, confirm, deny}`，`keyTtlMs` 读底栏 `vault.keyTtl`，`retentionDays` 默认 30。

→ 结论：保险柜已有「票据 + 代次 + 签名 + 撤销」四件套。**缺的是「钥匙持有者」这一角色**：现在钥匙只由 B 派生，A 拿到票据即可解密；手机要成为「钥匙保险柜」，需要新增一个**票据中转层**（见 §6）。

### 1.5 外部入口的鉴权现状（重要）

- 面板路由：`src/routes.js` 只做 `ctx.get('connection')?.requestRejection?.({ headers })` —— 依赖 Host 的同源会话 cookie，**没有自己的令牌**。
- MCP 端点：`src/mcp.js` 的 `authorized(request, token)` 是 `if (!token) return true`，即 **`mcpToken` 为空时完全放行**；`host` 默认恒为 `127.0.0.1`（`config.mcpHost ?? '127.0.0.1'`），且 `cordis.patch.yml` 未暴露 `mcpHost`。
- 文档服务：`plugins/doc-server` 的 `bindHost` 默认 `0.0.0.0`，其 `cordis.patch.yml` 注释明写「the service has no authentication of its own」；控制路由同样只靠 `requestRejection`。

→ 结论：**门票/子账号如果复用现有 HTTP 入口，会直接暴露在无鉴权的 LAN 服务上。** 统一设定必须为「终端服务入口」新增独立令牌层，不能依赖 Host cookie 或「绑定 127.0.0.1」这种部署假设。

### 1.6 链路与信令

`src/transport.js`：`mesh-rpc`（可靠有序）、`mesh-ping`（无序）、`mesh-bin`（JLC 二进制），>48 KiB 文本按 `__chunkId` 分片重组；`src/signaling.js` 每帧带 Ed25519 签名（覆盖 `room|kind|from|id|frag|sha256(data)`），`roomOf(accountTag, a, b)` 决定房间。

→ 结论：链路本身已经是「设备密钥认证 + 签名信令」，门票只需要在**握手后**加一层「票根声明」，不需要改传输层。

## 2. 同类安全设计的机制形状（外部调研）

### 2.1 口令认证：PAKE 而不是「哈希口令」

| 机制 | 形状 | 为什么抄 |
|---|---|---|
| [SPAKE2（RFC 9382）](https://datatracker.ietf.org/doc/rfc9382/) | 双方各持口令，交换带盲化因子的群元素，得到共享密钥；口令不传输 | 对称 PAKE，实现简单，适合「口令 = 票」的一次性登录 |
| [OPAQUE（IRTF 草案）](https://datatracker.ietf.org/doc/draft-irtf-cfrg-opaque/) | OPRF 隐藏口令，服务器只存「口令的盲化映像」，客户端拿到会话密钥与 export key | 服务器（主办方）即使被拖库也无法离线爆破口令；export key 可派生「保险柜钥匙」 |
| [NIST 2024 OPAQUE 讲座](https://csrc.nist.gov/csrc/media/presentations/2024/crclub-2024-10-16/images-media/crypto-club-20241016--hugo--OPAQUE.pdf) | 明确区分「不可避免的在线猜测」与「可避免的离线字典攻击」 | 在线猜测只能靠限流/二次确认，离线攻击靠 PAKE 消除 |

→ 落地：子账号口令走 PAKE；主办方只存 `OPRF` 记录或 `salt + 盲化映像`；口令失败计数只用于限流，**不用于判定「口令对不对」**。

### 2.2 令牌绑定：DPoP / 短时证书 / 能力令牌

| 机制 | 形状 | 为什么抄 |
|---|---|---|
| [DPoP（RFC 9449）](https://datatracker.ietf.org/doc/html/rfc9449) | 每个请求附带用客户端私钥签的 proof（含 `htm`/`htu`/`ath`），令牌被偷也不能在别处用 | 门票令牌绑定终端设备密钥，复制令牌无效 |
| [RFC 8707 Resource Indicators](https://raw.githubusercontent.com/ze-software/ze/refs/heads/main/rfc/short/rfc8707.md) | 令牌带 `aud`，只能用于指定资源 | 一张门票只能进指定房间/电台，不能拿去开保险柜 |
| [RFC 8693 Token Exchange](https://datatracker.ietf.org/doc/html/rfc8693) | `act` 链记录「谁代表谁」，链深度受限 | 手机替子账号做动作时，审计里必须写清「手机代表 c 子账号」 |
| [Macaroons（NDSS 2014）](https://research.google/people/arnarbirgisson/) | 链式 HMAC + caveat，只能加限制不能放宽 | 门票从主账号下发到子账号再到终端，每一跳只能收窄权限 |
| [Cloudflare Access 短时证书](http://cloudflare-docs.cloudflare-docs.workers.dev/cloudflare-one/changelog/access/) | 用短时 SSH 证书替代长期密钥 | 终端授权用短时证书，到期自然失效 |

### 2.3 设备身份与人工确认：WebAuthn / Tailnet Lock / SAS

| 机制 | 形状 | 为什么抄 |
|---|---|---|
| [WebAuthn passkey](https://cheatsheetseries.owasp.org/cheatsheets/Passkey_Security_Cheat_Sheet.html) | 凭据绑 RP 域名，私钥在安全硬件；BE/BS 标志区分「可同步」与「设备绑定」（[解析](https://mojoauth.com/blog/webauthn-be-bs-flags-synced-vs-device-bound-passkey)） | 手机端用 passkey 做「人工确认」，确认动作绑定手机硬件而不是短信 |
| [Tailnet Lock](https://tailscale.com/docs/features/tailnet-lock) | 新节点必须被「签名节点」签名才可通信，未签名节点被锁出 | 手机作为「签名节点」给子账号终端签名，等价于「入场盖章」 |
| [Matrix SAS 验证](https://raw.githubusercontent.com/matrix-org/matrix-spec-proposals/4d9345cd001705b5000e307f198e578526a959d7/specification/modules/end_to_end_encryption.rst) | 两台设备互相比较 emoji/数字，确认后才互相签名 | 手机与桌面首次配对用「配对码」（本仓已有 `pairCode`，6 位、两公钥决定） |
| [Signal safety number](https://pkg.go.dev/github.com/GoCodeAlone/libsignal-go/fingerprint) | 60 位数字，双方各自计算一致 | 手机与子账号终端显示同一串数字，用户肉眼核对 |

## 3. 统一设定：身份模型

### 3.1 三层身份

```
主账号（Account）        userId → accountTag（发现层唯一可见的身份）
   └─ 票根（Ticket）     ticket_id + 口令（PAKE 记录）+ 权限档 + 有效期 + 批次
        └─ 终端（Device） deviceId + Ed25519 设备密钥 + 会话令牌（DPoP 绑定）
```

- **主账号**：沿用 `accountTag`，不做任何改动，保证与现有发现层兼容。
- **票根**：新增 `ticket_id`（随机 16 B base64url），由主账号签发；票根是「子账号」的正式身份。
- **终端**：沿用现有 `deviceId` + `identity.json` 里的 Ed25519 密钥；每台终端登录一个票根，得到一个**设备绑定的会话令牌**。

### 3.2 票根字段

| 字段 | 含义 | 约束 |
|---|---|---|
| `ticket_id` | 票根 id | 稳定，吊销单点 |
| `account_tag` | 所属主账号 tag | 必须等于签发者 tag |
| `batch_id` | 批次 id（门票批量发放时） | 批次吊销用 |
| `role` | `owner` / `sub` / `guest` | 权限档 |
| `capabilities` | 能力位掩码（见 §4.2） | 只能收窄，不能放宽 |
| `issued_at` / `expires_at` | 签发与到期 | 门票档必须短；子账号档可续期 |
| `max_uses` | 入场次数（0 = 不限） | 门票档必填 |
| `bind_device` | 首次入场绑定的 `deviceId` | 绑定后不可换设备（除非主账号显式解绑） |
| `parent_ticket` | 若由子账号再下发，记录父票根 | 链深度 ≤ 2 |
| `revoked` / `revoked_at` | 持久撤销状态 | 与 `peers.json` 同风格 |

口令本身不存明文：存 `{ salt, oprf_record }`（OPAQUE）或 `{ salt, verifier }`（SPAKE2+）。口令由主账号设定与修改，子账号无权修改（与需求一致）。

### 3.3 会话令牌

登录成功后签发：

```
token = {
  ticket_id, account_tag, device_id, role, capabilities,
  issued_at, expires_at,   // 门票档 ≤ 场次时长；子账号档 ≤ 24h
  nonce                  // 一次性，用于首次绑定
}
sig = Ed25519(主账号或手机签名节点, JCS(token))
```

终端每次 RPC 附带 `DPoP` proof：`Ed25519(device_key, htm|htu|ath|ts)`。服务端校验 `token.sig` + `proof` + `token.device_id == proof.jwk`，三者一致才放行。这样即使令牌被复制到另一台设备，也无法使用。

## 4. 权限分级

### 4.1 三档

| 档位 | 谁能拿 | 默认能力 | 典型场景 |
|---|---|---|---|
| `owner`（主账号） | 主账号终端 + 已绑定的手机 | 全部：会话、文件、保险柜管理、签发/撤销票根 | 主播本人、主办方 |
| `sub`（子账号） | 主账号签发的子账号票根 | 会话读 + 文件读（限 `allowRoots`）；可被手机提权到 `owner` | 主播的助手、固定测试玩家 |
| `guest`（门票） | 批次门票 | 只给 `sessions/*` 与房间内聊天/抢麦；无文件读；无保险柜 | 大量测试玩家、电台听众 |

### 4.2 能力位

```
session.list    session.read    session.index
file.list       file.read
vault.open      vault.admin     ticket.issue    ticket.revoke
room.join       room.chat       room.mic
```

映射（与 `src/data.js` 的 `runOp` 一一对应）：

| op | 能力位 | owner | sub | guest |
|---|---|---|---|---|
| `sessions/list` / `sessions/events` / `sessions/index` | `session.*` | ✓ | ✓ | ✓ |
| `workspaces/list` / `files/list` / `files/stat` / `files/read` | `file.*` | ✓ | ✓ | ✗ |
| `vault/open` / `vault/commit` | `vault.open` | ✓ | ✗（除非手机提权） | ✗ |
| `vault/host/*` 路由 | `vault.admin` | ✓ | ✗ | ✗ |
| `ticket/issue` / `ticket/revoke` | `ticket.*` | ✓ | ✗ | ✗ |
| 电台 `room.*` | `room.*` | ✓ | ✓ | ✓ |

**收窄规则**：子账号下发的票根，`capabilities ⊆ 父票根.capabilities`；违反即拒绝签发（Macaroons 式「只能加限制」）。

### 4.3 提权规则（改写需求草案）

需求草案写「检测到手机号属于主账号 ⇒ 子账号提权到主账号等级」。这条规则有三个漏洞：

1. 手机号是**单一属性**，SIM 换卡/号码复用即可冒用；
2. 子账号口令泄露后，只要对方手机号一致就自动提权，等于口令 + 号码双因素但号码可伪造；
3. 隐式推断无法审计「谁批准了这次提权」。

**改写为显式三步**：

| 步骤 | 动作 | 校验 |
|---|---|---|
| ① 手机绑定 | 手机首次登录主账号，生成手机设备密钥，主账号签发 `phone_binding` 票根（`role=owner`, `device=phone`） | 手机设备密钥 + 主账号口令（PAKE） |
| ② 子账号登录手机 | 手机用子账号口令登录，得到 `sub` 令牌 | PAKE + 手机设备密钥 |
| ③ 提权请求 | 手机向主账号发 `ticket/elevate`，声明「手机代表子账号 c，请求 owner 能力，有效期 T」 | 主账号在手机上弹出阻塞确认（本仓已有 `shell.overlay` 阻塞对话框范式），确认后签发 `elevated` 令牌，`act` 链记录 `phone → ticket c` |
| ④ 生效范围 | 提权令牌只对**手机这台设备**生效，且 `expires_at` 短（默认 15 分钟，底栏可调） | DPoP 绑定手机密钥 |

→ 效果：满足「手机在子账号下登录即可提权」的体验，但提权是**显式、可审计、可撤销、限时**的，不是隐式推断。

## 5. 手机端独立设计

### 5.1 定位

手机端**不是 Agent**：不跑模型、不执行工具、不持有会话数据。它是：

1. **信任节点**：持有独立 Ed25519 设备密钥，参与握手与签名；
2. **授权中心**：所有强通知与人工确认走手机；
3. **保险柜钥匙**：持有票据中转能力（§6）；
4. **消费终端**：文档服务与电台/小游戏的入口。

### 5.2 终端特征

需求草案写「手机 5G + Tailscale 将成为其终端特征」。这个特征**不能作为身份**，只能作为「提示信号」：

- 身份仍是设备密钥；
- `5G + tailnet 地址` 作为「网络画像」，用于：
  - 判断是否「异地同时在线」（并发检测）；
  - 提示「这台设备最近换了网络」，触发一次轻量复核；
- 网络画像**不参与授权判定**，只参与风险提示（与 Netflix「主位置」思路一致但更弱：只提示不阻断，[报道](https://www.slashgear.com/1714284/why-netflix-says-device-not-part-of-household-how-fix/)）。

### 5.3 主界面

- 底部栏移动端布局（与桌面底栏同一套配置项，`bottom-settings.mjs` 为文档真值源）；
- 远程管理多端底部栏全局配置：一键同步、一键换主题；
- 通知中心：待确认信任、待确认提权、待确认开柜、待确认目录选择（对应桌面 `pendingTrust` 与 `vault/host` 的 pending 列表）。

### 5.4 远程 Agent 终端

需求草案写「手机连接远程 dsh 主机后可全编辑发送消息，对比其他 dsh 主机只能发送固定文本」。这条**与当前只读数据面冲突**：`src/data.js` 没有任何写入/prompt 通道。

**统一设定**：手机端的「全编辑」不是新增写入通道，而是**复用 Host 自身的会话输入接口**：

- 手机通过 tailnet 访问远端 Host 的 Web 界面（同源 cookie 或独立令牌）；
- 输入走 Host 的应用层输入接口（与桌面端一致），不新增 `mesh` 写入 op；
- 若远端 Host 不允许远程输入，手机只能读——这与「受信程度更高」不矛盾：**受信的是手机设备，不是手机上的任意网页**。

### 5.5 批量账号管理

- 手机可同时登录多个主账号：每个主账号一个 `accountTag` 命名空间，票根互不串；
- 每个主账号下可登录多个子账号：手机为每个子账号持有一个 `sub` 令牌；
- 跨 tailnet 交叉受信：手机切换 Tailscale 账号后，用「手机设备密钥 + 主账号签名」建立交叉受信；**交叉受信必须让手机作为钥匙保险柜**（§6.3）。

## 6. 手机作为保险柜钥匙

### 6.1 现状缺口

NCV2 现在：B（所有者）派生钥匙 → 经已认证链路把票据给 A（观看方）→ A 解密。钥匙的**唯一持有者**是 B。手机要成为「钥匙保险柜」，需要新增一层：

```
B（所有者）──签发票据──▶ 手机（钥匙保险柜）──放行──▶ A（观看方）
```

手机不存明文内容，只存**票据的短期缓存 + 放行策略**。

### 6.2 协议扩展（在现有 NCV2 上加一层，不改容器格式）

新增两个 RPC op：

| op | 方向 | 参数 | 返回 |
|---|---|---|---|
| `vault/delegate` | B → 手机 | `depositId, gen, archiveSha, kind, variant, phone_device, ttl` | 手机记录「本票据由 B 委托给手机保管」，返回 `delegation_id` |
| `vault/release` | 手机 → A | `depositId, gen, challenge, delegation_id` | 手机向 B 申请票据，B 返回 `K_g + K_{g+1}`（签名不变），手机把票据转发给 A |

关键约束（全部复用现有机制）：

1. **票据仍是 B 派生**：手机不持有 `root.key`，只持有「委托凭证」；
2. **一代一用不变**：`hostOpen` 仍返回 `K_g + K_{g+1}`，`hostCommit` 推进 `confirmedGen`；
3. **签名绑定不变**：`payload = {depositId, gen, nextGen, archiveSha, kind, variant, challenge, expiresAt, fresh}`，手机转发时原样透传，A 用 B 的 hello 公钥验签；
4. **委托可撤销**：B 调 `vault/revoke` 或新增 `vault/undelegate`，手机下次 `vault/release` 返回 `delegation-revoked`；
5. **手机掉线不阻塞**：A 仍可直接向 B 申请票据（现有路径不变），手机只是「更快/更安全的中转」。

### 6.3 交叉受信

需求草案写「多个账号不在同一局域网时，可通过切换 tailscale 账号交叉受信；交叉受信必须让登陆手机作为密钥保险柜」。

统一设定：

- 交叉受信 = **主账号 A 的票根被主账号 B 的手机显式接受**；
- 手机持有 A 的票根（`sub` 或 `owner`），在 B 的 tailnet 里登录；
- 手机向 B 发 `ticket/cross-trust`，B 弹出阻塞确认，确认后 B 签发一张 `cross` 票根给手机；
- `cross` 票根的能力位**只含 `session.*` 与 `room.*`**，不含 `vault.*`；
- 保险柜钥匙仍由手机中转（§6.2），因此「交叉受信必须让手机作为钥匙保险柜」在实现上是「手机持有 `delegation_id`」。

## 7. 门票：发给大量测试玩家与听众

### 7.1 门票 = 低权限、短时、批次化的子账号

| 维度 | 子账号 | 门票 |
|---|---|---|
| `role` | `sub` | `guest` |
| 有效期 | 可续期（默认 30 天） | 场次时长或测试周期（默认 2 小时 / 7 天） |
| 次数 | 不限 | `max_uses` 必填 |
| 绑定 | 首次入场绑设备 | 首次入场绑设备，绑定后不可换 |
| 能力位 | `session.* + file.*` | `session.* + room.*` |
| 撤销粒度 | 单票根 / 批次 | 单票根 / 批次 / 换组密钥 |
| 发放方式 | 主账号逐个签发 | 批次签发（`batch_id` + 种子派生） |

### 7.2 批次签发

- 主办方输入：`batch_id`（随机）、数量 N、有效期、能力位、口令策略；
- 口令由 `HMAC(batch_seed, index)` 派生 → 转成人类可读的 8 位码（避免随机口令撞库）；
- 每个口令对应一个 `ticket_id`，主办方导出 CSV/二维码；
- 批次吊销：`ticket/revoke { batch_id }` 一次性把 N 张票标 `revoked`；
- 换组密钥：`batch_id` 的 `group_key_epoch + 1`，已入场终端下次握手拿不到新密钥即断链。

### 7.3 入场凭证轮换

- 门票登录后，终端持有 `guest` 令牌；
- 房间内入场码 = `TOTP(HMAC(token, room_id), 30s)`，手机端显示、桌面端可显示；
- 服务端只接受当前窗口 ±1 的码；
- 票根不变，所以「踢一个人」仍是单点操作。

### 7.4 终端设备的临时授权

需求草案写「其使用的终端设备 dsh 实例或手机终端可以做到临时授权并享受服务」。

统一设定：

| 终端类型 | 授权方式 | 到期行为 |
|---|---|---|
| DSH 实例（桌面） | 门票口令登录 → `guest` 令牌（DPoP 绑定设备密钥） | 令牌到期 → 断链；票根到期 → 拒绝续签 |
| 手机终端 | 门票口令登录 → `guest` 令牌 + 手机设备密钥 | 同上；手机可提前撤销 |
| 临时访客（无 DSH） | 浏览器 + 一次性 URL（能力令牌，TTL ≤ 场次） | URL 到期即失效；不绑设备，但 `max_uses=1` |

## 8. 撤销与回收（三档粒度）

| 粒度 | 操作 | 生效范围 | 依赖对方配合？ |
|---|---|---|---|
| 单票根 | `ticket/revoke { ticket_id }` | 该票根全部终端 | 否（持久 `revoked`，心跳不复活） |
| 批次 | `ticket/revoke { batch_id }` | 批次内全部票根 | 否 |
| 换组密钥 | `group_key_epoch + 1` | 已入场终端下次握手失败 | 否（服务端拒绝旧 epoch） |
| 保险柜 | `vault/revoke { peer }` | 该 peer 全部 deposit | 否（A 下次开柜返回 `revoked`，删除本地容器） |
| 委托 | `vault/undelegate { delegation_id }` | 手机票据中转失效 | 否 |

全部遵循本仓 rc.13 的教训：**撤销是持久状态，不是删除条目**；撤销通知走签名帧，离线对端靠 announce 重发收敛。

## 10. 验收口径

| 验收项 | 判定 |
|---|---|
| 口令不落明文 | `tickets.json` 中无口令原文；日志无口令；`mesh.log` 无口令片段 |
| 令牌绑设备 | 把 `guest` 令牌复制到另一台设备，DPoP proof 不匹配 → 拒绝 |
| 门票到期 | 令牌到期后 RPC 返回 `token-expired`；票根到期后登录返回 `ticket-expired` |
| 单票根撤销 | 撤销后心跳不复活；重启后仍撤销（沿用 `p0-mesh.mjs` 断言风格） |
| 批次撤销 | 批次内全部票根同时失效 |
| 提权显式 | 提权必须经过手机阻塞确认；审计记录 `act` 链 |
| 保险柜委托 | 手机中转票据，A 用 B 公钥验签通过；撤销委托后 A 回退完整拉取 |
| 交叉受信 | `cross` 票根不含 `vault.*`；手机持有 `delegation_id` |
| 无鉴权入口关闭 | `mcpToken` 为空时 MCP 端点拒绝；`doc-server` 非 loopback 绑定必须带令牌 |

## 11. 风险与边界

| 风险 | 说明 | 缓解 |
|---|---|---|
| 口令泄露 | 门票口令被转发 | PAKE + 首绑设备 + `max_uses` + 短 TTL；主办方批量吊销 |
| 手机丢失 | 手机是钥匙保险柜 | 手机设备密钥可撤销；`vault/undelegate` 立即失效；主账号可远程解绑 |
| 提权滥用 | 手机提权后长期有效 | 提权令牌 TTL ≤ 15 分钟，底栏可调；每次提权写审计 |
| 交叉受信过度 | 两个账号互相看见 | `cross` 票根能力位只含 `session.* + room.*` |
| 只读面被绕过 | 门票档不应读文件 | `runOp` 前置能力位检查；`allowedRoots` 不变 |
| 现有入口无鉴权 | MCP / doc-server | 统一令牌层，默认拒绝 |
| 超时政策 | 本仓禁止应用层超时 | 令牌 TTL 是**凭证有效期**，不是请求超时；到期只拒绝本次授权，不终止在途模型请求 |
