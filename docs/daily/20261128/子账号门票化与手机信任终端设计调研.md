## 0. 结论摘要（先看这一节）

1. **子账号 = 门票，不是账号**：子账号没有密码，只有一个**一次性兑换口令**；兑换时终端生成/复用设备密钥，换回一张 `DSH-CAP` 能力证书（绑定设备公钥、角色、动作集、资源作用域、TTL、撤销代次）。此后每一个请求都由**设备私钥签名**，口令不再出现在任何协议帧里。口令泄露 ≠ 账号被接管：它不能改主账号、不能提权、不能再发子账号。
2. **主账号 = 账号根**：主账号的根密钥（`AK`）不放在桌面机普通文件里，而是由**手机安全芯片持有或封装**（iOS Secure Enclave / Android StrongBox；PWA 降级为不可导出 WebCrypto 密钥）。桌面机只持主账号签发的**设备委派证书**（role=`owner-device`，短周期）。这是"手机本身就是保险柜钥匙"的第一层含义。
3. **分级权限 = 角色 × 资源 × 动作**：与 DSH 核心已有的 `remote-access`（`role` / `binding` / `policy` / `snapshot`，见 `.build/.../packages/api/remote-access/README.md`）同构。不新造权限语言，只把 mesh 侧的设备证书与门票映射成同一套 principal 词汇。
4. **手机端是独立 principal，不是"远程控制器"**：四个身份面——`phone-approver`（强通知与审批中心）、`vault-key`（保险柜钥匙）、`consumer`（电台/小游戏/文档服务）、`owner-delegate`（远程 Agent 终端：可编辑消息、可发文件，受 session 作用域约束）。手机**不跑 Agent 运行时**（不加载 agent/LLM 工具面），只加载 Connection + RemoteAccess + 播放器/游戏/审批界面。
5. **手机作钥匙三档**（推荐顺序 A→C→B）：**A 审批签名**（默认；不把 `K_g` 放到手机上）→ **C 2-of-2 门限**（高危：开 session 类保险柜、提权、跨账号链接）→ **B passkey PRF 包裹密钥**（可选的恢复/只读兜底，明确标注安全等级更低）。
6. **手机号绝对不进认证/恢复路径**：NIST SP 800-63B-4 把 PSTN 带外认证列为唯一 restricted authenticator；FBI IC3 2021 年记录 1,611 起 SIM swap、损失 >6,800 万美元（B §5）。"同手机号 → 提升到主账号权限"必须否决，替换为"**已配对手机的设备密钥签名 + 作用域化提升 + 每次生物识别**"。
7. **门票 = 批次 × 单码 × 设备首绑 × 短时能力证书**：批次可整批回收，单码可单人踢出，`revEpoch + 1` 可全场清场，TTL 到期自动失效。防转卖的目标不是"绝对防住"，而是"**转卖成本 > 票价**"——Ticketmaster SafeTix 被逆向重放（C §6）证明轮换只挡截图、不挡提取种子，所以种子必须留在主办方、客户端只拿派生结果。
8. **电台/游戏是同一套门票的两个 `kind`**：电台 = 场次票 + 在场名册 + 组密钥轮换（沿用 SDD 06 的 `epoch`）；游戏 = 测试批次票 + entitlement 功能位 + 保险柜 `kind=game` 托管对象（`托管保险柜与本地缓存.md` §17 已预留位）。两者共用保险柜的通用对象容器，不需要第二套存储。
9. **无中心、可离线时撤销靠三件套**：短 TTL 能力证书 + 续期（`cap/renew`）+ 单调 `revEpoch`/撤销列表；撤销在主办方是**硬状态**（沿用 account-mesh 的 `revoked` 语义），不靠心跳复活；离线设备回连后 epoch 不符即 fail closed。
10. **与仓库既有约定不冲突**：门票限制的是**入场与能力范围**（设备数、并发席位、作用域、时限），不是模型请求次数/累计用量/预算。不引入任何会中止在途模型请求的计时器，审批等待由用户取消或真实错误结束。

## 1. 背景与目标

### 1.1 从原稿到本文

`docs/daily/20261127/子账号与手机信任终端.md` 给出了 6 组方向性设定：手机是信任节点+消费节点（不是 Agent）、手机作通知/授权中心、主界面是底栏移动端版、主账号/子账号两级受信、远程 Agent 终端、批量账号与交叉受信。原文明确"方向性的不代表正确"。本文做三件事：

1. **把方向翻译成可实现的实体与协议**（账号域、设备、主体、能力、对象五层）；
2. **把"信任"从身份叙事换成可验证的密码学**（设备密钥签名 + 能力证书 + 撤销代次），逐条修正会导致提权/接管的安全假设；
3. **把"发门票"落到两个真实场景**（测试玩家、电台听众/坐客），并给出与现有 mesh/保险柜/底栏代码的接入点。

### 1.2 四个使用场景（本文的验收对象）

| 场景 | 参与者 | 关键诉求 | 失败即不可接受 |
| --- | --- | --- | --- |
| **S1 测试玩家批次入场** | 主账号（测试服主办方）、50~5,000 名测试玩家 | 批量发口令；玩家装在任意 DSH 实例或手机上就能进测试房间；拿素材/状态；到期自动清场；能单人踢、能整批回收 | 口令被转发给无关的人；测试素材被外传；活动结束后仍能进 |
| **S2 电台听众/坐客/场次** | 主播（主账号）、预约听众、坐客（cohost）、值守 bot | 静音收听、匿名在场、抢麦、聊天；坐客要能上麦；一场演出两小时；结束后全部回收 | 演出链接被公开转卖；被踢的人还在听；听众反向读到主播文件 |
| **S3 手机远程办公** | 主账号持有者、主账号桌面机、手机 | 手机可全量编辑消息/发文件驱动远端；强通知与审批走手机；多端底栏配置/主题一键同步 | 桌面机被攻破即可静默扩大权限；审批被"盲点确定"；手机丢失后无恢复 |
| **S4 多主账号 + 跨 tailnet 交叉受信** | 两个不同主账号、各自的手机与桌面 | 一台设备可登录多个主账号；两个账号在不相邻 tailnet 之间临时互通某些服务 | 单台被控桌面能偷偷建立跨账号链接；账号间默认互相读会话 |

### 1.3 非目标（本文不承诺）

- 不做"同一自然人"的证明：本文只证明**设备持有 + 角色授权**，不证明屏幕前是谁。
- 不做云端推送/云端审批中继：没有自建推送服务时，"强通知"只能是链路通知 + 下次连接送达（见 §4.8.5）。
- 不做企业组织账号（team/org）、跨组织的管理员层级；一期只有"一个主账号 + N 个子账号/门票"。
- 不改变"不设应用层模型超时、不做用量/预算门控"的仓库约定；门票的 TTL/并发是**服务入场券**，不是模型请求门控。

## 2. 现状基线（以 2026-11-28 代码为准）

> 本节只写可核对的现状；行号/路径来自 D（`research/D-现有机制现状.md`）。设计稿与实现的漂移单独列出，避免在错误前提上继续设计。

### 2.1 账号与设备

| 事实 | 现状 | 对本文的影响 |
| --- | --- | --- |
| 账号身份 | `deepseekAccount` 平台 `userId` → `accountTag = base64url(sha256("dsh-mesh/v1:"+userId))[:22]`（`src/identity.js:15-18`） | 只能表达"一个账号"，**没有主/子账号、没有手机号字段** |
| accountTag 的用途 | 只用于发现过滤与 UI 展示，**不参与授权**；`isTrusted` 不校验 accountTag（`src/trust.js:58-62`） | 子账号/门票必须是**新授权层**，不能靠 tag |
| announce 是否签名 | **不签名**（`src/discovery.js:192-206`）；过滤只在对方带 tag 时生效 | "同账号"是自报；应用层闸门只能是人工确认或能力证书 |
| 设备身份 | 每 `$DSH_HOME` 一个 Ed25519 密钥对（`src/identity.js:49-77`）；`deviceId` 来自平台设备身份 | 设备密钥是**唯一可靠持有证明**；门票/证书都绑它 |
| 换账号 | `deviceId` 不变、`accountTag` 变；`peers.json`/`hosted-vault/` 留在 `$DSH_HOME` 不清理 | 多主账号必须做**账号作用域命名空间**（§4.12.1），否则换回原账号会静默恢复信任 |
| 重新安装 | 新公钥、`deviceId` 不变 → 已信任条目自动 rebound（`src/mesh.js:217-231`）；保险柜账本只绑 `deviceId` → 旧托管项仍可开 | "钥匙绑设备 id 而非公钥"是既有事实；引入账号根后要收紧（§7.3） |

### 2.2 mesh 受信（设备级，不是账号级）

- 协议：UDP 发现（47831，未签名 announce）→ 签名信令（`offer/answer/ice/revoke`，签名覆盖 `room|kind|from|id|frag|sha256(data)`）→ WebRTC DTLS → `hello/hello-ack` 双向 Ed25519 互认 → RPC 白名单（`sessions/*`、`workspaces/list`、`files/*`、`sessions/export/*`、`vault/*`）。
- 首次接触：**首次不受信 + 本机阻塞式对话框**（`mesh.js:250-266` + `client.js:1388-1497`）。`autoTrustSameAccount` 只决定是否排队，关闭则直接丢弃信令（`mesh.js:395-400`）。
- 撤销：`forget()` → `trust.revoke()` 持久写 `revoked/revokedAt`，先发签名 `revoke` 帧再断链；对端离线时靠每次 announce 重发收敛（`mesh.js:980-994, 420-436`）。
- **没有**：账号级信任、信任委托、角色、跨设备强通知、非本机审批入口。

> **结论**：现有受信是"**全有或全无的只读设备信任**"。加子账号/门票不能把票据塞进 `trusted:true`，必须新增"**带角色的、可过期的主体表**"，否则一张测试票等于一台永久受信设备。

### 2.3 托管保险柜（rc.15 实现）

| 项 | 实现（代码为准） | 与设计稿的差异 |
| --- | --- | --- |
| 容器 | `.dat` = `NCV2D` + archiveBox + projectionBox；`.hdr` = **JSON 文本**（magic/gen/kind/variant/priority/depositId/archiveSha/wrap） | 设计稿 §6.1 写"约 120 B 二进制头"，实现是 JSON（D §3.2） |

### 2.6 DSH 核心已有的授权积木（本文直接对齐）

| 机制 | 位置 | 可复用什么 |
| --- | --- | --- |
| `Principal` 与 `Peer` 分离 | `.agents/notes/implemented/architecture/2026-10-12-peer-principal-and-remote-access.md` | 一个 principal 有 N 个 peer；身份由**进程内 Host 代码**赋值，线上字段不可覆盖 |
| `remote-access`：role/binding/policy/`decide()`/`allows()`/snapshot 流 | `packages/api/remote-access` | 方法级 RBAC、列表过滤、访问快照推给前端——**分级权限的现成引擎** |
| liveshare：viewer 票 = 每 share 一个 principal、`view`/`write` 层级、fork 开关、撤销即取消调用与流 | `packages/experimental/liveshare` | "观众票"的成熟实现：门票 → principal → 绑定角色 → Host 端强制 |

> **结论**：DSH 已经有"身份≠连接""角色×资源×动作""访问快照"三件事。本文的分级权限应当**复用这套词汇**，只在 account-mesh 自己的 P2P 数据面上实现一个同构的窄门。

## 3. 外部调研：可抄的机制与要避开的坑

> 完整笔记见 `research/`：A/B/C 三篇外部调研 + D 篇仓库现状核对；本节只留对本文设计有约束力的结论与出处。

### 3.1 委托授权与临时票据（A）

#### 3.1.1 先把四类凭证分开（A §0）

| 层 | 凭证 | 生命周期 | 签发者 | 谁来验 | 本文对应 |
| --- | --- | --- | --- | --- | --- |
| **L0 身份** | 主账号根 AK | 长期，可轮换 | 手机安全芯片 | 主账号设备/手机 | 账号根（§4.4.1） |
| **L1 引导** | 子账号口令 / 门票码 | 分钟~天，一次性或首绑 | 主账号 | host（在线） | 口令（§4.5） |
| **L2 会话** | 设备绑定的 DSH-CAP | 小时~天，可续期 | host / 上级证书 | 任意 DSH 节点离线可验 | 能力证书（§4.7） |
| **L3 服务票** | mesh 入场、电台、游戏、保险柜子票 | 分钟~小时，范围极窄 | host / 服务方 | 目标服务/托管方 | `vault/open` 票据 + 房间 cap |

> 关键：**L1 口令只承担"首次兑换"，不承担日常鉴权**。把 6~10 位口令当长期密码用，等于把可转发、可截图、可转卖的 bearer 凭证当账号密码。

#### 3.1.2 能力式委托：五个工业标准怎么选

| 机制 | 原理 | 衰减（能否收窄） | 离线验证 | 撤销 | 关键参数 | 本文取用 |
| --- | --- | --- | --- | --- | --- | --- |
| **Macaroons**（NDSS 2014） | 链式 HMAC + caveat 谓词；第三方 caveat 用 discharge macaroon 兑现 | ✅ 持票人只能追加 caveat | 有根密钥即可本地验 | 无内建撤销（靠 caveat 时限/换根密钥） | caveat 谓词、root key | ✅ 借"衰减"思想；不用 HMAC bearer 形态 |
| **Biscuit** | Ed25519 签名 + 追加式 block + Datalog check；任何持公钥者可验 | ✅ 新 block 只能加 check | ✅ 完全离线 | 每个 block 有 revocation id，可拒绝该 token 及其派生 | block/check、revocation id、third-party block | ✅ **最贴近本设计**：签名 + 逐级收窄 + 撤销 id |
| **UCAN** | DID 主体 + 委托链（delegation/invocation） | ✅ 只能收窄；有效期取链上最早 `exp` | ✅ | 撤销是不可伪造消息，撤销库只增不减、可 gossip | `iss/aud/sub/exp/nbf/prf`、`{can,with}` | ⚠️ 借"链式证明 + 过期优先"，不引入 DID |
| **ZCAP-LD** | JSON-LD 能力链，`parentCapability` + `invocationTarget` | ✅ `expires` 只能更短、target 只能加前缀 | ✅ | 验证方保存撤销项到过期 | `capabilityChain`、`allowedAction` | ⚠️ 只借"父子能力 + 前缀收窄" |
| **SPIFFE/SVID** | 工作负载身份：X509-SVID/JWT-SVID，短 TTL + 自动轮换 | 身份不衰减，靠受众/策略 | ✅ 信任包本地验 | 不逐证书 CRL，靠短寿命（SPIRE 默认 X509 1h / JWT 5m） | `SPIFFE ID`、`aud`、`exp` | ❌ 只适合节点间身份，**不要发给不特定听众** |

#### 3.1.3 OAuth 家族：陌生终端、降权、绑定与撤销

| 规范 | 解决什么 | 必须抄的具体参数 | 撤销/失效 | 本文落点 |
| --- | --- | --- | --- | --- |
| **RFC 8628 设备授权** | 输入受限终端凭短码换 token | `user_code`（示例 8 位 base20 ≈34.5 bit）、`expires_in`、`interval`（默认 5s）、`slow_down`（+5s）；GitHub 实例 `expires_in=900`、`interval=5` | 短 `expires_in` + 用户码限速 | 口令兑换的唯一原型（§4.5.3） |
| **RFC 8693 Token Exchange** | 主体令牌换更窄的下游令牌 | `subject_token`、`actor_token`、`requested_token_type`、`audience`、`resource`、`scope`、`expires_in`；`act` 嵌套链、`may_act` | 交换不自动传播撤销 | 子账号会话 → 电台/游戏/保险柜子票；`act` 记录"谁代表谁"（手机代签） |
| **GNAP（RFC 9635）** | 通用授权协商 | `access[]`（`type/actions/locations/datatypes`）、`interact.user_code`（6~8 位、几分钟）、`continue{uri,wait}`、每个 token 带管理 URI | `POST` 轮换、`DELETE` 撤销（204） | "每张票一个管理入口" + `durable` 标志 |
| **RFC 9449 DPoP** | 发送方约束：令牌绑终端公钥 | proof JWT：`typ=dpop+jwt`、`jwk`、`jti`（≥96 bit/UUID）、`htm`、`htu`、`iat`、`ath`（令牌 SHA-256）；令牌含 `cnf.jkt` | 支持 `DPoP-Nonce` 防预生成；私钥丢失即失效 | 防复制/防重放核心（§4.7.1 的 `sub` 绑定等价物） |
| **RFC 8705 mTLS** | 证书绑定令牌 | `cnf.x5t#S256` + 客户端证书 | CRL/OCSP + 短 TTL | 若节点已有设备证书可复用 |
| **RFC 9396 RAR** | 结构化授权范围 | `authorization_details[]`，必填 `type`，可选 `actions/locations/datatypes` | 随令牌撤销 | cap 的 `scope` 用结构化对象（§4.7.1） |
| **RFC 7009 撤销** | 统一撤销端点 | `token` + `token_type_hint`；无效令牌也回 200 | 在线立即 | `ticket/revoke`、`cap/revoke` 的形态 |
| **RFC 9700 安全 BCP** | 基线 | access token 应 sender-constrained + audience-restricted；public client 的 refresh token 必须绑定或轮换，检测重放即撤销整个 grant | — | 一票一设备、刷新即换票、重放即全撤 |

#### 3.1.4 短口令的熵与限速（A §3）

| 口令形态 | 组合数 | 熵（bit） | 用途判断 |
| --- | --- | --- | --- |
| 6 位数字 | 10^6 | ≈19.9 | 只能当一次性 OTP |
| 6 位 base20（去元音） | 20^6 | ≈25.9 | 必须强限速，不建议 |
| 8 位 base20 | 20^8 | ≈34.5 | RFC 8628 示例值；配 5 次尝试仅 2⁻³² 猜中概率 |
| 10 位 base20 | 20^10 | ≈43.2 | **批量发不特定人群的下限** |
| 10 位 Crockford base32 | 32^10 | 50 | 本文门票码的数据位（可读性略差、抗爆破更好） |

| 控制点 | 工业做法 | 来源 |
| --- | --- | --- |
| 失败限速 | NIST：同一认证器/账号**连续失败 ≤100 次**即禁用，允许更低；接近上限时 30s~1h 递增等待 + bot 检测 | NIST SP 800-63B-4 |
| 锁定对象 | 计数器绑**账号/口令本身**，不绑源 IP（防换 IP 绕过）；建议 5~10 次/码/小时 | OWASP Authentication Cheat Sheet |
| 存储 | 口令不落明文；若必须可离线验证用 Argon2id（`t=3,p=4,m=64MiB,salt=128bit`）；**本文用带密钥 HMAC 存储，不存明文也不需要 Argon2**（见 §4.5.2） | RFC 9106 |
| 防转发 | 首兑绑终端公钥（等价 `cnf.jkt`）；第二设备默认拒绝；并发上限（测试 1、听众 2~3） | RFC 9449 |
| 防截图 | TOTP 30s（RFC 6238，至多允许 1 步延迟）或 15s 服务端轮换二维码 + 一次性核销 | RFC 6238、Ticketmaster SafeTix |

#### 3.1.5 批量发码、撤销与离线收敛（A §4-5）

| 手段 | 关键参数 | 撤销 | 适用 |
| --- | --- | --- | --- |
| 签名 URL / 预签名票据 | S3 预签名最长 7 天、STS 默认 1h；URL 即 bearer | 换密钥/短 TTL，无法单条撤销 | 一次性缓存包/回放包 |
| 轮换二维码 | TOTP 30s / 现场 15s；密钥 `K_ticket` 不出终端 | 短窗口 + 一次性核销 | 现场入场 |
| 批次签发 | `batch_id` + 逐票 `jti` + `gen` | 整批拉黑 / `gen+1` | 测试玩家、听众批次 |
| 撤销名单 | 位图/CRL 式，验证方缓存（Token Status List 的 `ttl`） | 在线拉取 + 本地缓存 | 离线设备 |
| 代次/快照 | 撤销任意票 → `auth_gen+1`；旧代全失效 | 粗粒度，可能误伤同代 | 大场次收场 |

**离线撤销的现实上界**（A §5 的验收准则，写进 §4.7.3）：

```text
assurance: 撤销延迟上界 = min(TTL, statusListTTL + heartbeatInterval)
sensitive 操作（开柜/改权限/跨账号）: 状态过期即 fail-closed
低风险操作（电台收听）: 可 fail-open 但降级（降码率/禁麦）并留痕
```

- **UCAN 的"过期优先"原则**值得直接抄：主动过期不需要在线信息，撤销需要；所以能力证书 TTL 要短。
- CAEP（共享撤销信号）只是加速器，不是离线方案（A §5）。
- 两级撤销：`gen/revEpoch`（粗、省带宽）+ 单 `jti/capId` 黑名单（细、精确踢人）。

#### 3.1.6 硬性结论

1. 票据必须**可衰减、不可扩张**：任何一方从上级票据派生新票据，只能收窄 `acts/exp/scope`；
2. 票据必须**绑受众**（audience = 具体 host/room/object）与**绑持有者**（设备公钥），否则复制即用；
3. **离线可验证 + 在线可撤销**是矛盾的，工业界统一折中：短 TTL + 撤销列表 + 代次（§4.7.3）；
4. **不要做"口令在 A 主机输入、token 发到任意 B 主机"**：设备码钓鱼（Storm-2372）的核心就是"用户以为在给 X 授权，实际给 Y"；兑换时必须显示**目标 host 的签名身份/指纹**（沿用保险柜"审批界面只渲染本地账本"的防钓鱼原则）；
5. **禁止身份启发式提权**：不把手机号/内网 IP/tailnet 成员当信任依据；提权必须显式确认并记 `act` 链；
6. **首次连接默认不受信**：未知 peer 必须凭门票或主账号确认进入，已受信 peer 也要按 `revEpoch` 定期重新验证（A §6 第 8 条）。

### 3.4 交叉结论：五条设计不变量

1. **公开内容可以匿名，任何带数据面的权限必须有身份**（设备密钥或能力证书）。
2. **授权必须绑"设备"而不是绑"号码/昵称"**；账号只是设备的集合。
3. **一切票据都要能回答三个问题**：谁签的（issuer 链）、给谁的（audience/设备）、什么时候失效（TTL/epoch）。
4. **撤销必须是硬状态**，且对离线设备有可判定的收敛方式（epoch/TTL），不能靠"下次心跳"。
5. **审批/发码/改权限这些动作不能暴露给模型面**（agent 工具/MCP），只能走人类界面 + 签名通道；否则 prompt injection 可以直接给自己发码。

## 4. 统一设定（本文核心）

### 4.1 五层模型

```text
账号域 accountDomain ── 主账号根 AK 签发的命名空间；子账号/门票都在域内
  └─ 设备 device ─────── 一对 Ed25519 密钥 + 主账号签发的设备证书
       └─ 主体 principal ── 角色(role)+动作集(acts)+作用域(scope)；由证书/门票/本机 owner 产生
            └─ 能力 capability ── DSH-CAP 或 ticket；有受众、TTL、撤销代次
                 └─ 对象 vault object ── (domainId, kind, objectId, variant) 的 NCV2 加密容器
```

各层"不变的东西"和"可变的东西"：

| 层 | 不变 | 可变 | 谁来证明 |
| --- | --- | --- | --- |
| 账号域 | `domainId`（主账号 id 的哈希） | 成员（子账号/门票）、设备清单 | 手机上的账号根 AK |
| 设备 | 设备公钥 / `deviceId` | 设备证书（角色、有效期）、信任状态 | 设备私钥签名 |
| 主体 | 角色枚举 | 动作集、作用域、TTL | 设备证书或门票 |
| 对象 | `depositId`（随机） | 代次 `gen`、撤销状态 | 托管方 B 的 root.key + 账本 |

对齐 DSH 核心：一个 `principal` 有 N 个 `peer`（连接）；principal 的权限由 `remote-access` 的 role/binding 决定；本机用户是 `{ kind: 'owner' }`，非 owner 主体（门票观众、子账号设备、手机）都必须**由 Host 进程内代码赋值**，线上字段不可自报（`.agents/notes/.../2026-10-12-peer-principal-and-remote-access.md`）。account-mesh 的 P2P 数据面走的是自己的 RPC，不在 Gateway 上，所以需要在 `src/mesh.js` 里实现同构的 `authorize(peer, op)` 窄门；两边的**角色词汇与动作名保持一致**，避免两套权限语言。

### 4.2 术语表

| 术语 | 定义 |
| --- | --- |
| **主账号 owner** | 持有账号根 AK 的自然人/团队；唯一能创建子账号、发门票、配手机、做跨账号链接的角色 |
| **子账号 subaccount** | 主账号在域内创建的主体模板：无密码、有一次性口令、有角色/作用域/TTL/设备数上限；**不能再创建子账号**（一期） |
| **门票 ticket** | 一张可兑换的凭证（批次 + 单码 + 元数据）；子账号是"长期门票模板"，测试/演出票是"临时票" |
| **口令 passcode** | 人类可读、一次性/首绑使用的短码；**只用于兑换**，不参与后续任何请求 |
| **能力证书 DSH-CAP** | 兑换产物：`{role, acts, scope, sub=设备公钥, exp, revEpoch, sig}`；所有请求的授权凭据 |
| **设备证书 DSH-DEVCERT** | 主账号根 AK 签给某台设备的身份：`{domainId, devicePub, role, acts, exp, sig}` |
| **角色 role** | 预定义动作集的名字（owner/phone-approver/cohost/member/tester/listener/bot） |
| **动作 act** | 具体操作名，与 mesh RPC op / UI 动作一一对应（如 `radio/listen`、`vault/open:game`） |
| **作用域 scope** | 动作可作用的资源集合：`kinds`（session/radio/game/config）、`objectHashes`、`workspace` |
| **撤销代次 revEpoch** | 域级单调计数器；`+1` 表示"所有旧证书/票据作废"，离线设备回连对不上即 fail closed |
| **在场名册 roster** | 主办方侧"谁在用哪张票、哪台设备、何时进、何时出"的表；踢人与审计的依据 |
| **组密钥 groupKey** | 电台/游戏房间的媒体/状态加密密钥，按 `epoch` 轮换；踢人 = 换 epoch |
| **审批签名 approval** | 手机对"操作摘要 + 一次性挑战"的签名；不是布尔值，不能由请求方代签 |
| **账号根 AK** | 主账号的根密钥对；默认由手机安全芯片持有/封装；签发设备证书与域级操作 |

### 4.3 不变量（实现与评审的硬约束）

| 编号 | 不变量 | 违反后果 |
| --- | --- | --- |
| I1 | 口令只在兑换时出现一次；之后所有请求靠设备私钥签名 | 口令进日志/重放 → 账号可被克隆 |
| I2 | 能力只能收窄，不能扩张：`acts ⊆ parent.acts`、`exp ≤ parent.exp`、`scope ⊆ parent.scope` | 子账号/观众自我提权 |
| I3 | 能力绑定 `sub=设备公钥` 且 `aud` 指定 host/room/object | 票据复制到另一台设备即可用 |
| I4 | 审批必须是签名，覆盖 `opDigest`+挑战+短过期+单调计数；禁止布尔 approve | "手机批准了 A、桌面执行了 B" |
| I5 | 发码、改权限、审批入口**不进模型面**（agent 工具/MCP）；只在人类 UI + 签名通道 | prompt injection 给自己发码/提权 |
| I6 | 撤销是硬状态 + 单调 `revEpoch`；不靠心跳/重启复活 | 旧设备撤销后自动恢复 |
| I7 | 手机号不进入认证、审批、恢复公式；只做通知与风控提示 | SIM swap 接管保险柜 |
| I8 | 保险柜不代解密、不接收密文（沿用现有设计） | B 变成解密神谕 |
| I9 | 默认 fail closed；只有"公开内容"（电台公开收听）允许无票 | 一处默认放行 = 全网域敞开 |
| I10 | 门票限制的是入场与能力范围，**不**是模型请求数/累计用量/预算 | 违反仓库"不设用量门控"约定 |
| I11 | 审计记录：谁（设备/主体）、何时、用哪张票（capId/ticketId 哈希）、批了哪个摘要 | 事故无法追溯、无法踢人 |
| I12 | 旧对端兼容：`hello` 缺 `caps` 时行为与 rc.15 一致；门票/证书是**新增可选能力** | 升级把老设备踢下线 |

**信任等级公式**（B §8.3⑥，用于"子账号按主账号受信"这类规则）：

```text
effectiveTrust = min(accountRoleTrust, deviceAssurance, holderProofFreshness, sessionRisk)
```

- `accountRoleTrust`：来自账号角色策略——**子账号登录时只继承自己角色允许的那一层**（这是唯一允许"继承"的维度）；
- `deviceAssurance`：attestation（SE > StrongBox > TEE > 无）+ `BE=0`（device-bound）才给最高；
- `holderProofFreshness`：本次签名 `authAge`（建议 ≤300s），过期即降级；
- `sessionRisk`：来源网络、异常时间、并发会话等；
- **手机号相同不进入公式**，只作为 `sessionRisk` 的提示项（例如"该号码近期发生过换卡"仅提示人工复核）。


### 4.4 主账号与子账号的实体模型

#### 4.4.1 主账号（域）

```jsonc
// $DSH_HOME/account-mesh/accounts/<domainId>/domain.json（0600）
{
  "v": 2,
  "domainId": "b64u-16B",            // = sha256("dsh-domain/v2:"+rootUserId)[:16]
  "rootUserId": "…",                  // 平台 userId，仅本机可见，不入日志
  "rootPub": "ed25519:…",            // 账号根公钥（私钥在手机/或本机加密）
  "rootCustody": "phone",            // phone（重档）| local-sealed（轻档，默认）
  "revEpoch": 3,                      // 域级撤销代次
  "phones": ["<devicePubFp>"],       // 已配对的手机审批器（可多台，建议 2 台）
  "devices": [ /* 设备证书列表 */ ],
  "subaccounts": [ /* 见 4.4.2 */ ],
  "batches": [ /* 见 §4.10.1 */ ],
  "createdAt": 0, "updatedAt": 0
}
```

**轻档 vs 重档（账号根的两种托管方式）**：

| 档位 | AK 私钥在哪 | 桌面被攻破能做什么 | 适用 |
| --- | --- | --- | --- |
| **轻档（默认）** | 桌面本机，用 OS 安全存储（`safeStorage`/Keychain）加密，**手机持一把审批公钥 APK** | 可签发设备证书；但发码/发子账号/跨账号链接/改根需要手机审批签名 | 个人自用单机 |
| **重档（推荐给共享/演示/多子账号账号）** | 只在手机安全芯片（SE/StrongBox）；桌面只有**有限 acts + 30 天 TTL** 的设备证书，续期要手机签名 | 只能在自己被授权的 acts 内活动；不能扩域、不能发子账号/门票 | 主播、测试服主办方、跨账号使用者 |

> 重档是"手机本身就是保险柜"的落点：**根密钥不落桌面磁盘**，桌面被拿走也签不出新设备/新票。代价是换手机、重装桌面都要走恢复或重新配对。

#### 4.4.2 子账号

```jsonc
{
  "subId": "sa_b64u-8B",
  "domainId": "…",
  "displayName": "Beta 玩家 042",
  "role": "tester",                     // member | tester | cohost（listener 走门票，不建长期子账号）
  "acts": ["mesh/join","game/join","game/state-read","game/state-write","vault/open:game"],
  "scope": { "kinds": ["game"], "objectHashes": [], "workspace": null },
  "notBefore": 0, "notAfter": 0,         // 默认：member 30 天、tester 30 天、cohost 单场次
  "maxDevices": 1,                       // 默认 1；member 可 2
  "maxConcurrent": 1,                    // 同时在线设备数
  "bindMode": "first-device",            // first-device | named | any（any 仅公开内容）
  "requirePhoneApproval": false,         // 高危角色（cohost/member）建议 true
  "passcode": { "hmac": "…", "algo": "hmac-sha256", "keyId": "tickets.key@v1" },
  "state": "active",                     // created | active | expiring | revoked | expired
  "createdBy": "<ownerDevicePubFp>", "createdAt": 0,
  "revokedAt": null, "revokeReason": null,
  "batchId": null                        // 属于某个批次时（批量发放）填
}
```

**子账号能力上限（`roleMax`，由主账号侧强制，不信任何客户端）**：

| 角色 | 允许的动作 | 永不允许 | 默认 TTL | 默认设备数 |
| --- | --- | --- | --- | --- |
| `cohost` | `radio/listen`、`radio/chat`、`radio/mic-request`、`radio/speak`、`vault/open:radio`（该场次） | 读会话/文件、`agent/*`、`config/*`、`ticket/*`、`account/*` | 单场次 + 2h | 1 |
| `member` | `radio/listen`、`radio/chat`、`radio/mic-request`、部分 `game/*`、`vault/open:radio\|game` | 读会话/文件、`agent/*`、`config/write`、`ticket/issue`、`account/*` | 30 天（可续） | 2 |
| `tester` | `mesh/join`、`game/join`、`game/state-*`、`vault/open:game`（该测试服对象） | 读会话/文件、`agent/*`、`config/*`、`ticket/*`、`account/*` | 30 天（构建过期即失效） | 1 |
| `listener` | 走**门票**而非子账号；只有 `radio/listen`（可选 `radio/chat`） | 一切写/读数据面 | 场次时段 | 1 |

**关键设计决定**：

1. **子账号不是"半个主账号"**：它不继承任何会话/文件读取权；即使子账号设备被完全控制，能读到的上限 = 该子账号 `acts/scope` 明确列出的对象（默认只有游戏/电台对象）。
2. **子账号不能再发子账号**，也不能改自己的 acts/exp（服务端只信主账号签发的记录）。一期不做"子账号邀请朋友"的裂变。
3. **子账号的手机登录不改变角色**（修正原稿）：子账号在手机上登录，principal 仍是 `mesh-member{tester}`；只有"主账号已配对手机"这一**具体设备**才是 `phone-approver`。见 §10 第 5 条。
4. **到期机制**：子账号到期前 3 天进入 `expiring`，UI 提示续期；到期后自动 `expired`，设备下次请求收到 `expired`，本地证书删除。

### 4.5 口令设计

#### 4.5.1 两种口令，同一形态

| | 子账号口令（长期/多人） | 门票码（批次/场次） |
| --- | --- | --- |
| 形态 | `XXXX-XXXX-XXXX`，Crockford Base32，**12 位 = 10 数据 + 2 校验** | 同形态（同一套输入/校验组件） |
| 数据熵 | 50 bit | 50 bit |
| 有效期 | 兑换窗口 24h；兑换后永久作废（换机重发新码） | 兑换窗口 = 场次窗口（默认 `notBefore-30min ~ notAfter`） |
| 使用次数 | 首绑一次 + 换机重发（旧码作废） | 一次性核销（`maxUses=1`）或首绑 |
| 分发 | 私聊/邮件/QR 卡片 | 群发链接、海报 QR、CSV、现场口令 |
| 目标 | 测试玩家、固定坐客、长期听众 | 一场演出、一次活动、一批测试 |

> 统一 12 位（约 50 bit）的理由：A §3.1 的结论是"批量发不特定人群的下限为 10 位 base20 ≈43 bit"，Crockford 32 进制 10 位数据 = 50 bit 已高于该下限，且比"14 位子账号码 + 10 位门票码"两套形态少一套实现。若主办方要更高标准，`batch.minCodeBits = 70` 生成 14 位数据（共 16 位）的加强码；若用户坚持更短，允许 `minCodeBits = 40`（8 位数据），但必须同时收紧限速并缩短兑换窗口。输入框做 O/0、I/1/L/1、U/V 归一与自动分组，两个校验字符挡手误。

**为什么 50 bit 够用**：口令**不能离线验证**（主机端用带密钥 HMAC 存储，`batchKey` 只在主办方）；在线暴力破解被四层限流挡住（见 4.5.4）；且单码只能核销一次、首绑设备，猜中一个码的收益仅是"占一个席位"。若 host 磁盘被拿走但没有 `batchKey`，攻击者也无法离线穷举。

#### 4.5.2 口令的生成与存储

```text
batchKey    = random 32 B               // 每个批次一把；存 host 的 hosted-vault/tickets.key（0600）
ticketId    = "T-" + b64u(6 B)          // 可读序号，非秘密
code        = crockford(50 bit random) + checksum2
ticket.hmac = HMAC-SHA256(batchKey, batchId | ticketId | code)
```

- 主机端**只存 HMAC**（与票根绑定），不存明文码；导出 CSV/QR 是唯一一次明文出现。
- `batchKey` 与 `root.key` 分开存放：泄露 `batchKey` 只能伪造该批次的码，不能开保险柜。
- **为什么不用 Argon2id**：Argon2 保护的是"低熵人类密码 + 无密钥哈希"；本文的码是 50 bit 随机构造、且用密钥 HMAC 校验，没有 key 的攻击者无法离线验证，因此密钥保护（0600 + 与 root.key 分离）比慢哈希更关键。若某部署要求"无密钥也能离线验证"，则改用 Argon2id 并接受 50 bit 码的离线爆破风险（不推荐）。
- 口令在终端**只存在于兑换请求的内存里**；兑换成功立即清零，不写日志、不写配置文件、不进 UI 历史。


#### 4.5.3 兑换流程（子账号与门票共用）

```text
Guest 终端                                          Host（主办方设备 B）
  │ 1. 拿到口令（打字/扫码）；扫码时 QR 还带 host 指纹、domainId、batchId、端点
  │ 2. 生成/复用设备密钥对（Ed25519）
  │── ticket/redeem {batchId, ticketId, code, devicePub, deviceName,
  │                  challenge, capRequest} ────────────────→│
  │                                                          │ 3. HMAC 校验（常量时间）
  │                                                          │ 4. 批次/单票状态、时间窗、revEpoch
  │                                                          │ 5. 首绑：ticket.devicePub 为空则绑定；非空则必须相等
  │                                                          │ 6. 并发/席位/限流
  │                                                          │ 7. 需要手机批准的角色 → 推送审批（§4.8.5）
  │                                                          │ 8. 签发 DSH-CAP（绑 devicePub，TTL）
  │←─ {cap, hostCertChain, hostEndpoints, epoch, rosterHint} ─│
  │ 9. 验签（到主账号根/批次根）、存 cap（0600）、清零口令
  │10. 用设备私钥签 hello + cap 加入；之后不再使用口令
```

**兑换页必须显示主办方身份**（防止设备码钓鱼）：host 用自己的设备证书签名一段"我是谁、域名、批次名、有效期"的展示信息；终端在输入口令前就展示并允许用户核对 6 位指纹。原稿的"只有口令"体验不变，但**口令不能在没有宿主身份提示的情况下被输入**——这是 §3.1.6 第 4 条与 A §2.1 防钓鱼建议的直接落地。

#### 4.5.4 抗爆破四层限流（主机侧，不是模型门控）

| 层 | 规则（默认，可配） | 目的 |
| --- | --- | --- |
| 单设备 | 5 次失败 / 5 分钟，之后指数退避 | 挡脚本 |
| 单 IP / 单 tailnet 节点 | 20 次 / 5 分钟 | 挡同一出口的批量尝试 |
| 单批次 | 100 次失败 / 小时 → 批次锁定 15 分钟，主办方手机收到告警 | 挡分布式猜码 |
| 全域 | 1,000 次失败 / 小时 → 暂停兑换，要求主办方手动解封 | 兜底 |

- 校验用常量时间比较；错误一律返回**同一个** `invalid-ticket`，不区分"码不存在/已核销/已过期"（避免枚举）。
- 失败计数只影响兑换入口，不影响已入场设备的收听/游戏（不做请求门控）。

#### 4.5.5 防转发 / 防截图

| 手段 | 做法 | 说明 |
| --- | --- | --- |
| 首绑设备 | 首次兑换写入 `devicePub`；后续必须同钥 | 转发给别人 = 别人兑换不了（或挤掉原设备，触发告警） |
| 一次性核销 | `maxUses=1`，`burn_after_join` | 截图在核销后无效 |
| 并发=1 | 同一票同时只允许一台设备在线 | 账号共享会互相踢 |
| 名册可见 | 主办方看到设备名/平台/入场时间 | "谁在场"是事后追责基础 |
| 轮换入场 token（可选） | 场次票显示 30s TOTP 入场码，票根不变 | 只挡截图，不挡提取种子（C 的 SafeTix 教训）；种子只在主办方 |
| ID 水印 | 聊天/游戏画面叠 `ticketId` 短码 | 泄露可定位到票 |
| 异常复核 | 同票多 IP/异地同时在线 → 挂起待审 | 误伤用人工队列兜底，不自动永久封 |

### 4.7 DSH-CAP 能力证书

#### 4.7.1 字段

```jsonc
{
  "v": 1, "typ": "dsh-cap",
  "capId": "b64u-8B",
  "domainId": "b64u-16B",
  "batchId": "T-2026-11-28-A",          // 门票来源；子账号可为 null
  "ticketId": "T-7K3M9QX2-00042",
  "iss": "<issuer device pubkey fingerprint>",
  "issRole": "owner-device",             // owner-device | delegated
  "sub": "<subject device pubkey fingerprint>",   // 受众/持有者绑定
  "aud": { "host": "<host device id>", "room": "radio-42", "kinds": ["radio"] },
  "role": "listener",
  "acts": ["radio/listen", "radio/chat"],
  "scope": { "kinds": ["radio"], "objectHashes": ["…"], "workspace": null },
  "iat": 1764, "nbf": 1764, "exp": 1765,  // 秒
  "revEpoch": 3,
  "parent": "b64u(capHash)",              // 委派链；根证书为 null
  "sig": "ed25519:…"                      // 对 JCS(去掉 sig 的 JSON) 签名
}
```

- **编码**：JCS 规范化 JSON + Ed25519（复用 `identity.js` 的 `signBytes/verifyBytes`），base64url；典型 < 1.5 KB。
- **受众绑死**：`sub` 必须等于当前链路 `hello` 里的设备公钥指纹；`aud.host` 必须等于接收方设备；复制给别人无法使用（签名不可伪造、密钥无法导出）。
- **衰减**：`parent` 存在时，验证器要求 `acts ⊆ parent.acts`、`exp ≤ parent.exp`、`scope ⊆ parent.scope`、`role` 相同或更窄。`trust/approve`、`account/manage`、`link/cross` **不可委派**（不能出现在任何 `issRole=delegated` 的证书里）。
- **TTL 参考值**：门票场次 ≤ 场次时长 + 30 分钟；测试玩家 ≤ 7 天（按次续期）；子账号 ≤ 30 天；手机设备证书 ≤ 30 天（重档）；owner 桌面证书 ≤ 30 天。

#### 4.7.2 验证与逐 op 授权

```text
onHello(entry):
  1. 验 hello 签名（既有）
  2. 若 hello 带 cap：verifyCap(cap)
       a. JCS 重算签名 → iss pubkey（来自设备证书链或 trust 表）
       b. iss 的 DSH-DEVCERT 有效、未过期、未撤销、acts 覆盖 cap.acts
       c. sub == entry.peer.publicKey 指纹
       d. aud.host == 本机 deviceId；时间窗 ±5 min 时钟漂移
       e. revEpoch >= 本机域当前 revEpoch；capId/batchId/ticketId 不在撤销表
       f. role 在白名单；acts ⊆ roleMax(role)
  3. 写入 guests.json（deviceId → {capId, role, exp, batchId}），不写 peers.json
onServe(peer, op):
  action = OP_TO_ACTION[op]                       // 见下表
  if !allow(peer.role, action, resource): return not-authorized
```

| RPC op | 动作 | 资源 |
| --- | --- | --- |
| `sessions/list` / `sessions/events` / `sessions/index` | `session/list`、`session/read` | session |
| `workspaces/list` / `files/*` | `workspace/list`、`files/read` | workspace |
| `sessions/export/prepare\|block` | `session/fetch` | session |
| `vault/open` / `vault/commit` | `vault/open:<kind>` | vault object |
| `radio/*`（新） | `radio/listen`、`radio/chat`… | room |
| `game/*`（新） | `game/join`、`game/state-*` | room/object |
| `ticket/redeem`、`cap/renew` | 公开入口（未认证也可，但要限流） | batch |
| `approve/submit` | 只接受 `phoneApprover` 设备 | approval |
| `ticket/issue\|revoke`、`account/*` | **不在 RPC 白名单**（只走本机 UI/手机通道） | — |

`peers.json` 的语义保持"设备信任"不变；新增 `guests.json`（或 `peers.json` v3 增加 `subjects` 段）存放门票主体。**二者不可混用**：一张票绝不写入永久信任表；一台受信设备也不是自动获得门票角色。

#### 4.7.3 撤销模型（无中心 + 离线）

| 粒度 | 操作 | 生效方式 | 收敛时间 |
| --- | --- | --- | --- |
| 单票/单设备 | `ticket/revoke {ticketId}` → 写 `revoked[]`，并断开该 `capId` 的链路 | 该设备下次请求收到 `revoked`（硬状态） | 在线立即；离线 ≤ 下次重连 |
| 整批 | `batch/revoke {batchId}` → `revEpoch += 1` | 所有该批次证书 `revEpoch` 落后 → 全部拒绝 | 同上 |
| 全场 | `room/close {roomId}` → 组密钥 `epoch += 1` + 在线踢出 | 旧组密钥解不开新媒体包；在线立刻静音 | 在线立即；重新入场被拒 |
| 设备/手机 | `device/revoke` → `revEpoch += 1`，扫描账本删除该设备的包裹/票据 | 沿用保险柜 `revoked` 与 `410 unlinked` 语义 | 在线立即；离线回连失败并擦除 |
| 到期 | `exp` 自然过去 | 客户端本地即可判定 | 精确到秒 |

- 客户端把 `revoked[]`/`revEpoch` 缓存在 `$DSH_HOME/account-mesh/revocations.json`（0600）；**只用于 UX，判定以 host 返回为准**；host 断网时 fail closed（已缓存内容的只读回放见 §4.9.1 B 档与 §5.1.3）。
- 续期 `cap/renew`：持有效 cap 的设备在到期前 1/4 TTL 起可续；host 复核票状态/名额/`revEpoch` 后签发新 cap（同 `capId` 或新 id 均可，推荐新 id + 旧 id 短宽限）。续期不是"重新兑换"，不需要口令。

### 4.8 手机端独立设计

#### 4.8.1 形态与运行时边界

| 形态 | 技术 | 能拿到 | 何时用 |
| --- | --- | --- | --- |
| **PWA（首选，先做）** | 与桌面同一个 Web shell 的 mobile 布局；Service Worker；WebCrypto 不可导出密钥；WebAuthn passkey | 不可导出 P-256/Ed25519 签名密钥（浏览器内，受 OS 保护）；通知能力弱 | 所有手机；跨账号/跨平台 |
| **原生壳（增强）** | iOS/Android 薄壳：WebView + 原生密钥模块 + 推送 | Secure Enclave / StrongBox 密钥、attestation、后台推送、扫码 | 主播/主办方/高危账号 |

**边界（原稿"手机端不作为 Agent"的落地）**：手机 shell 只挂载 `Connection` + `RemoteAccess` + 消费面（电台播放器、小游戏、文档服务）+ 审批面 + vault client。**不加载** `agent` 运行时、不挂 LLM 工具面（`bash`/`files`/`plugin_manager`/`schedule_*` 等在手机上不注册）；手机发出的 `agent/prompt` 是**转发到远端 host** 的远程调用，模型调用与工具执行都在远端主机上，并受远端 `remote-access` 与能力证书约束。

#### 4.8.2 连接模型（为什么不能复用桌面本机路由）

- 桌面的 `/account-mesh/api/*` 与本机 Web 路由受 **browser-auth** 保护：cookie 绑定 `authority`（Host 头）+ 本机密钥签名，`dsh web` 的 URL 是 `127.0.0.1:port`（`packages/client/connection/src/browser-auth.ts`）。手机通过局域网/tailnet 打开 `http://<局域网IP>:port` 时 authority 不同、签名对不上 → **拿不到本机同源权限**。
- 因此手机走**自己的认证通道**：`phone/challenge` → 手机用设备密钥签挑战 → host 返回短 TTL 的 `phone-session`（cookie 或 token），principal 来自 host 的 `device list`（手机是已配对的 `phone-approver`），不是"局域网内的匿名浏览器"。
- 传输：优先 WebSocket（复用 Connection/Gateway，A §2.3 的短令牌 + 每请求 DPoP 式绑定）；未来可加 WebRTC 直连（与 desktop mesh 同栈），但**手机不作为 mesh 的 UDP 发现节点**（浏览器无 UDP；原生壳才可选）。网络层依赖：手机已加入同一 LAN 或同一 Tailscale tailnet（用户已验证可行）。

#### 4.8.3 四个身份面

| 身份面 | 做什么 | 关键约束 |
| --- | --- | --- |
| **审批中心** | 收强通知 → 展示摘要 → 生物识别 → 签名 | 签名覆盖 `opDigest`；不能盲批；不能由请求方代签（§4.8.6） |
| **保险柜钥匙** | 开柜审批 / （可选）包裹钥匙 / 账号根托管 | 三档见 §4.9；默认不把 `K_g` 放手机 |
| **消费终端** | 听电台、玩小游戏、看文档服务 | 只需要 `radio/listen` 等最小动作；匿名/公开内容无票 |
| **远程 Agent 终端** | 编辑消息、发文件、驱动远端会话 | `agent/prompt:<sessionScope>`；受远端 remote-access；只能发给已配对的 host |

#### 4.8.4 手机配对（QR + 6 位校验码，无 BLE 版）

字段（借鉴 CTAP 2.2 hybrid，去掉 BLE 后加人眼校验）：

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| `v` / `type` | 1B / 字符串 | `dsh-pair` |
| `pairingId` | 8B random | 本次配对标识，防重放 |
| `desktopEphPub` | 33B | 桌面临时 P-256 公钥，配对后废弃 |
| `qrSecret` | 16B random | 一次性 secret；手机用它认桌面 |
| `issuedAt` / `expiresAt` | int64 | TTL ≤ 120s |
| `domainFingerprint` | 8B | `sha256(domainId)[:8]`，双端显示前 6 位供人眼核对 |
| `relayHint[]` | 字符串 | LAN IP:port / tailnet 名，按优先级 |
| `flowHint` | 枚举 | `bind-phone` / `approve` / `vault-key` |
| `caps` | bitmask | 手机可申请的动作面（审批/钥匙/消费/远程办公） |

流程：桌面显示 QR + 6 位 `checkCode` → 手机扫码（或输入 6 位）→ ECDH 派生 `K` → 手机经 LAN/tailnet 连桌面，双方各回一个 HMAC 证明（互认）→ 手机显示"账号指纹、桌面设备名+公钥指纹、申请能力、风险提示"→ 生物识别 → 手机设备密钥签配对 transcript → 桌面验签 + 记录设备清单（`deviceId/platform/attestation/pubkeyFp/role/createdAt/lastSeenAt/keyExpiresAt`）→ 双方分别保存对方证书。

- **一次只配一台手机/一台桌面**；配对请求在桌面必须本机点击开始（不能由远端 peer 发起）。
- 注销：`device/revoke` → `revEpoch+1` → 通知所有设备 → 被注销端后续请求收到 **`unlinked`（410 语义）** → 客户端擦除本地包裹密钥/票据并强制重新配对（B §8.3⑤）。
- 手机可配对多台桌面（一个主账号下 N 台），桌面可配 1~2 台手机；第二台手机自动获得"备份审批器"角色（`phone-approver-backup`），高危操作要求两台之一在线。

#### 4.8.5 强通知与审批请求的现实

**没有云推送时的三条送达路径**：

1. **在线**：手机与 host 有 WebSocket/mesh 链路 → 请求实时到达（≤1s）；
2. **同 LAN**：mDNS/UDP 唤醒（原生壳；PWA 无后台 UDP）→ 手机亮屏即达；
3. **离线补投**：请求**持久化**在 host（`$DSH_HOME/account-mesh/approvals/pending.json`），手机下次连接拉取未决列表；消息带 `expiresAt`，过期即作废并通知请求方失败（fail closed，绝不"迟到的自动批准"）。

**审批请求的 TTL**：默认 300s；账号/根/跨账号类高危操作 60s + 手机侧 30s 倒计时；到期即拒绝，不自动批准。

**"默认接受"不成立**（否决原稿"对比默认接受安全模型更高"这句里的隐含默认）：手机端**永远要求一次人类动作**（生物识别）；无人类动作的请求只能拒绝或超时。

#### 4.8.6 审批签名的覆盖字段与验证

```jsonc
// 手机签名对象（JCS JSON；手机侧优先 ES256/P-256 以便走 Secure Enclave，桌面设备用 Ed25519）
{
  "v": 1, "typ": "dsh-approval",
  "domainId": "…",
  "requesterDeviceId": "…",       // 发起请求的桌面（不是请求方说，是 host 记账）
  "approverDeviceId": "…",        // 手机自己
  "purpose": "vault.open",        // vault.open | trust.raise | agent.exec | ticket.issue | link.cross | account.manage
  "opDigest": "sha256(JCS(操作参数))",   // host 执行前必须复核一致
  "summaryHash": "sha256(手机展示的人类摘要)",
  "challenge": "b64u-32B",        // host 一次性生成，5 分钟有效
  "issuedAt": 0, "expiresAt": 0,  // 高危 ≤ 60s
  "nonceCounter": 42,             // 每手机单调递增，host 缓存已用值
  "sig": "…"
}
```

Host 验证（任一步失败即 fail closed）：签名可验（手机公钥）→ `domainId` 匹配 → 手机在 `phones` 且未撤销 → `challenge` 是 host 发出的未使用挑战 → 未过期 → `nonceCounter` 大于已记录 → `opDigest` 与"即将执行的操作"逐字节一致 → `summaryHash` 与 host 将要展示给用户的摘要一致。执行后写 `approvals.json`（审计：谁批的、批了什么摘要、何时）。

**防钓鱼 UI 规则**（照抄 B §4.2）：

- 号码匹配：桌面显示 6 位数字，手机上**输入**（不是点"是"）；
- 展示来源设备名 + 公钥指纹前 6 位 + 时间 + 操作摘要（对象、会话标题、房间）——摘要**由 host 的本地账本渲染**，不渲染请求方传来的字符串（沿用保险柜 §7.7 原则）；
- 生物识别且**无 passcode 回退**；连续请求限速（同 purpose 30s 内只能发起一次）；
- 高危（账号根/跨账号/新设备入域）加**安全延迟**：手机提示"此操作将在 X 分钟后可确认"（默认 10 分钟；账号根操作 1 小时可配），给撤销窗口；
- 手机侧显示"如果我拒绝：会发生什么"（fail closed 提示）。

### 4.9 手机作为保险柜钥匙（三档 + 账号根托管）

#### 4.9.1 三档架构

| 档 | 名称 | 密钥在哪 | 开柜流程 | 丢失/换机 | 适用与代价 |
| --- | --- | --- | --- | --- | --- |
| **A（默认）** | 审批钥匙 | `K_g` 仍只在 host B 与观看方 A 的一次开柜内存里；手机只持**审批私钥** | B 收到 `vault/open` → 校验策略/角色 → 生成 approval 请求 → 手机签名 → B 验签后才发 `K_g` | 换手机：重新配对即可，`K_g` 不受影响 | ✅ 最简单、不降低可用性；手机丢失不导致数据永久不可读 |
| **C（高危）** | 2-of-2 门限 | `K_g` 由手机与桌面各持一个 share（`K_g = HKDF(sharePhone, shareDesktop)`），或对开柜票据做 2-of-2 门限签名 | 两端同时在线各出一份 → 合成 → 开柜 | 单丢即锁死 → **必须有恢复码/第三 shard** | ✅ 桌面被攻破也开不了；⚠️ 必须配套恢复 |
| **B（可选）** | 包裹钥匙 / PRF | `K_g` 用手机公钥（或 passkey PRF 派生的 KEK）包裹，存在 A 侧 | A 本地解包（需手机在场/解锁）→ 开柜；host 可离线 | 依赖 passkey 同步或恢复码；删 passkey = 数据永久不可读 | ⚠️ 只作只读/离线回放兜底；UI 必须标注等级低于 A/C |

**推荐顺序：A 默认 → C 叠加到"session 类保险柜 + 账号根操作" → B 仅做可选离线通行证**（与 B 报告的结论一致：A 基线、C 高危、B 兜底）。

#### 4.9.2 与现有保险柜协议的接入

现有 `vault/open` 的校验是"账本存在 → peer 匹配 → 未撤销 → archive/kind/variant 匹配 → 代次窗口 → 策略 auto/confirm/deny"。新增：

1. **策略枚举扩展**：`vaultRelease: auto | confirm | phone | deny`；`phone` = 需要已配对手机签名才能发 `K_g`。
2. **入参增加 `approval`**（可选）：`{approvalPayload, sig}`；`hostOpen` 在策略为 `phone` 或对象满足"需审批集"（`kind=session` 或 `config`，或请求方角色级别 ≥ `member`）时校验审批签名，`opDigest` 绑定 `{depositId, gen, archiveSha, kind, objectId, peerDeviceId}`。
3. **账本条目增加** `purpose/expiresAt/subject/capId/approvedBy`：谁持哪张票开的；撤销票据时按 `capId` 级联撤销该票创建的托管项。
4. **审计补齐**：`releases.json`（谁、何时、哪个 `depositId`、第几代、审批人、结果），供主办方查看与导出。
5. **代次与审批序**：先审批后发钥；审批签名一次性消耗；`vault/commit` 仍按两阶段提交；审批失败不删容器（与现有"只有确定性拒绝才删"一致）。
6. **手机作为观看方 A**（消费缓存）：手机可以像桌面 A 一样持有自己的托管项（`peer=手机deviceId`），开柜时由**手机自己的设备密钥**签名审批（同一台设备既是 A 又是审批器），然后解包渲染——这就是"手机端离线看缓存"的合法路径，而 `K_g` 仍不落盘。

#### 4.9.3 账号根托管（"手机是保险柜"的完整形态）

- **重档**下 `AK` 私钥只在手机安全芯片内；桌面 `domain.json` 只存 `rootPub` + 设备证书 + 一个**密封的恢复材料**（用手机公钥包裹的 `AK` 备份，供灾难恢复，需手机+恢复码共同解封）。
- **必须手机签名的域级操作**（即使桌面 owner 已登录）：创建/修改/删除子账号、发码/整批回收、跨账号链接、更换账号根、添加新手机、导出恢复材料。
- **不需要手机的操作**（避免日常被手机绑架）：开/关保险柜的普通会话；发码属于域级高危，**默认需手机批**，但可配置"本场次内允许桌面自助发 N 张"（`ticket.selfIssueMax`，默认 0；活动主办方临时打开）。

#### 4.9.4 恢复

| 场景 | 方案 |
| --- | --- |
| 手机丢失（有第二台手机） | 第二台手机批准 → `revEpoch+1` → 注销丢失设备 → 用恢复码/密封备份重建根 |
| 手机丢失（唯一） | 恢复码（≥128 bit，Crockford 分组 + 校验）解封 `AK` 备份 → 强制安全延迟（默认 12h）→ 全设备通知 → 可中止 → 恢复后轮换恢复码 |
| 桌面丢失 | 手机注销该设备证书；账本撤销该设备全部托管项（复用 `vault/revoke`）；子账号/门票不受影响 |
| 全部丢失 | 恢复码 + 已配对第二设备之一；两者都没有 = 账号根不可恢复（诚实边界，必须在开通重档时明确告知） |

恢复材料：`2-of-3`（手机芯片 / 纸质恢复码 / 第二设备），SLIP-39 风格分组+校验；**恢复动作本身走审批 + 延迟 + 全设备告警**。

### 4.10 门票体系（批次 / 单码 / 在场）

#### 4.10.1 实体

```jsonc
// 批次（Batch）
{
  "batchId": "B-20261128-radio42",
  "domainId": "…",
  "kind": "radio" | "game",
  "label": "凌晨两点的合成器电台 · 1128 场",

  "bindMode": "first-device",
  "burnAfterJoin": true,                       // 场次票 true；测试票 false
```

#### 4.10.2 发放

| 渠道 | 形态 | 适用 |
| --- | --- | --- |
| 面板复制 | 纯文本口令列表 | 私聊发单人 |
| QR 卡 | 图片（含 host 指纹/端点/batchId） | 现场、海报、群公告（**注意：公开海报只用于公开场次**） |
| CSV 导出 | `ticketId,code,batchId` | 大客户/媒体名单 |
| 一人一链（可选） | `dsh://join?host=…&batch=…&ticket=…` | 邮件邀请；链接本身即票（需短 TTL） |
| **名单模式** | 先收手机号/邮箱/设备名，再逐人发码 | 测试玩家（名单制比裸码可靠，C §1） |

#### 4.10.3 回收（三种粒度 + 结束）

1. **单码**：`ticket/revoke` → 名册/撤销表 → 在线立即踢；
2. **整批**：`batch/revoke` → `revEpoch+1` → 该批全部拒绝；
3. **全场**：`room/close` → 组密钥 `epoch+1` + 在线静音/踢出 + 名册归档；
4. **到期**：`notAfter` 到点自动失效（客户端本地可判）。

#### 4.10.4 规模与成本

| 规模 | 存储 | 兑换校验 | 名册 |
| --- | --- | --- | --- |
| 50 | 全量 50 条 | 1 HMAC + 1 表查 | 内存 + 落盘 |
| 500 | 稀疏（只存 bound/burned/revoked） | 同上 O(1) | 内存 + 落盘（每场 ≤ 1 MB） |
| 5,000 | 稀疏 + 撤销位图 | 同上 O(1) | 落盘 + 分页 UI；手机只看聚合 + 搜索 |

- 兑换请求并发限流：每 host 10 次/秒（可配）；批量入场用"排队 + 重试"，不设"累计请求预算"。
- 手机端场控只拉聚合（在场人数/异常数），明细按需搜索，避免大场次把手机拖死。

#### 4.10.5 与 SDD 06 的关系

`06` 的 `invite_token`（10 分钟、绑房间/主播/用途）在本文里是**门票的特例**：`role=cohost`、`maxTickets=1`、`notAfter=+10min`、`bindMode=first-device`。建议把 06 的呼入邀请统一到门票表，避免"两套邀请/两套撤销"。

### 4.11 底栏配置 / 主题同步（托管对象 `kind=config`）

- **对象键**：`(domainId, kind="config", objectId="bottom-bar", variant="v1")`；内容 = `timeouts.json` 的键值 + 主题引用 + 每键 `updatedBy/updatedAt/configGen`。
- **权威端**：主账号手机（`config/write`）；桌面默认只读拉取，本机临时修改进入"待同步"队列，手机确认后广播。
- **同步路径**：复用保险柜 `vault/open`（`kind=config`，小对象，秒开）；离线时各端用自己的本地副本，重连后按 `configGen` 合并（每键 last-write + 设备归属显示）。
- **安全**：配置文件不含密钥；`config/write` 不进模型面；手机端渲染同一份 catalog（`bottom-settings.mjs` / `night-timeouts.ts`），避免手机与桌面两套文案漂移。
- **主题**：只同步主题 id/URL/色板参数，素材走 doc-server/OSS，不塞进配置对象。

### 4.12 账号域、多主账号与交叉受信

#### 4.12.1 域与命名空间

- `domainId = b32(sha256("dsh-domain/v2:" + rootUserId))[:16]`；`accountTag` 保留为"发现候选"的旧字段（兼容），但**授权一律用 domainId + 证书**。
- `$DSH_HOME/account-mesh/accounts/<domainId>/` 存该域的 `domain.json`、`trust/`、`hosted-vault/`、`guests/`、`tickets/`；设备主密钥 `seed` 全局一份，`K_dev(domainId) = HKDF(seed, "dsh-dev/v2|"+domainId)`，**一个物理设备在不同账号下用不同密钥**（不可关联、不串账本）。这一步同时修掉 D 指出的"换账号 trust/ledger 不清理"问题。

#### 4.12.2 多主账号并发登录

- UI 的"账号槽"：1~N 个主账号同时在线，每个槽独立 discovery/room/trust/vault 命名空间；手机端同理（可同时连多个主账号的 host）。
- 设备证书按域签发；**跨域默认零共享**；跨域共享必须走 4.12.3 的显式链接。

#### 4.12.3 跨 tailnet / 跨账号交叉受信（手机作保险柜）

- **网络层**：A 账号 guest 加入 B 账号 tailnet 时，B 的 tailnet 发 **ephemeral + pre-approved + tag=dsh-guest + 1–90 天** 的 auth key（B §7）；tag 只决定网络可达，不授予应用权限。
- **应用层**：两个主账号建立 `linkRecord`：

```jsonc
{ "linkId":"…", "domainA":"…", "domainB":"…",
  "acts":["radio/listen","radio/chat"],        // 只允许具体服务，不含 session/files/vault:session
  "rooms":["radio-42"], "notAfter": 0,         // 默认 7 天
  "revEpochA":0, "revEpochB":0,
  "sigs": { "A":"<phoneA 签名>", "B":"<phoneB 签名>" }   // 2-of-2
}
```

- **手机是保险柜**：`linkRecord` 的双方签名都来自**各自主账号的手机**（重档下即 AK 签名）；任一侧桌面都无法单独建立/延长链接。撤销任意一侧 `revEpoch+1` 即失效。
- **不继承**：链接不传递会话读取、文件读取、`agent/*`、`config/*`；只传递 `acts` 明列的服务动作。

## 5. 场景落地

### 5.1 电台（S2）

#### 5.1.1 房间角色

| 房间内角色 | principal | 怎么来的 | 能做什么 |
| --- | --- | --- | --- |
| 主播 / 主持人 | `owner-device`（主播主账号的 host） | 主账号登录 + 设备证书 | 开房、混音、麦位仲裁、踢人、换 epoch、结束场次 |
| 场控 | `phone-approver`（主播手机） | 已配对手机 | 看名册、踢人、静音、结束场次；**不能**替主播上麦 |
| 坐客 | `cohost` | 场次前发 cohost 门票（10 分钟邀请码是其特例）或长期子账号 | 听、聊、申请麦位；上麦需主播批准 |
| 持票听众 | `listener` | 场次票兑换 | 静音收听、聊天（可配只读）、抢麦排队 |
| 公开听众 | `public-listener` | 无票，经 06 的公开流/HLS 或公开房间 | 只听公开场次；无 mesh 数据面权限 |
| 值守 bot | `bot` | 主办方配置的 guest principal（必须带 `bot`/AI 标注） | 读知识库、TTS 发言；不可抢真人麦、不可当主持人 |

#### 5.1.2 场次流程（两小时演出）

```text
T-60min  主办方在手机/桌面建场次：batch{kind:radio, room:radio-42, notBefore/notAfter,
        role:listener, maxTickets:500, burnAfterJoin:true, bindMode:first-device}
T-60min  生成 500 张票：ticketId + code + HMAC；导出 QR 卡/链接/CSV；只把需要的渠道发出去
T-30min  主播开房（anchor 上线），房间状态 scheduled → live；布告板/局域网发布 host 指纹与端点
T-30..0  听众兑换：ticket/redeem → cap(listener) → hello+cap 加入 → 名册 +1；未兑换的码仍是"未用"
T+0      开场；组密钥 epoch=1 下发给在线听众；媒体走主播混音后的单路 Opus（沿用 06 D3）
场内     抢麦：radio/mic-request → 主播仲裁 → 读秒；被踢：roster 删除 + epoch+1 + cap revoke
T+115    预告下播；host 生成归档事件流（文字记录/最热话题）上报（沿用 02 的 OSS 事件流）
T+120    场次结束：room/close → epoch+1；batch revoke → revEpoch+1；未用票全部作废；名册归档
```

- **不记名但可追责**：听众不需要账号，票绑定设备公钥；名册只有 `ticketId 短码 + 设备名 + 入场时间`，不存真实身份（与 06 的隐私表一致：不写手机号、不写 IP）。
- **防转卖**：一票一设备、并发 1、一次性核销；异常（同票跨网络并发）→ 挂起 + 告警，场控手机一键踢。
- **与 06 的关系**：06 提供"发现 + 中继 + SFU/HLS 兜底"；本文提供"授权 + 名册 + 撤销"。两条通道都成立：
  - P2P 通道（局域网/同 tailnet）：`ticket/redeem` 走 mesh RPC，媒体走 WebRTC 直连；
  - 中继通道（跨网）：布告板发布 host 的**签名批次描述**（公开可验），听众在 hub 页面兑换后由 hub 转发到 host（hub 只是搬运工，不代替 host 做授权）。
- **公开场次**允许无票收听（`public-listener`），但只能听公开流，不能进 mesh 房间、不能拿组密钥、不能读回放缓存。

#### 5.1.3 回放与缓存（保险柜 `kind=radio`）

- 主播可把本场音频分片 / 文字记录作为托管对象（`kind=radio`、`variant=segment:<n>`）托管给持票听众，听众本机缓存 → 下次重听秒开。
- 对象权限随票：`vault/open:radio` 校验 cap 的 `scope.room` 与 `objectHashes`；场次结束 `batch revoke` 时账本级联 `revoked` → 下次打开删除本地容器（复用现有"硬状态 + 删除"语义）。
- 主播不上传明文、A 端不拿 `K_g` 之外的东西（沿用保险柜安全性质）。

### 5.2 小游戏（S1）

#### 5.2.1 测试批次

| 项 | 设计 |
| --- | --- |
| 测试服 host | 主账号下的一台"测试服"桌面实例（可专用机），持有游戏对象与状态 |
| 玩家入场 | 主账号建批次 `kind=game`、`role=tester`、`maxTickets=2000`、`notAfter=构建过期日（参考 TestFlight 90 天）` |
| 玩家终端 | 任意 DSH 实例（兑换后加入）或手机（PWA 直接玩，不需要装游戏） |

#### 5.2.2 玩家旅程

```text

```

- 玩家**看不到**主办方的会话/工作区（角色上限强制），只能拿测试对象。
- 调试面板通过 entitlement 位开放，但 `agent/*`、`files/*` 永不对 tester 开放。

### 5.3 手机远程办公（S3）

- 手机是 `phone-approver` + `owner-delegate` principal：可 `session/list`、`session/read`、`agent/prompt:<sessionScope>`、`agent/stop`、`files/read`、上传附件。
- **为什么能"全编辑"而不是"只能发继续/总结"**：手机持设备绑定密钥 + attestation，且每次操作都由 host 用 `remote-access` 决策；远程调用仍受会话作用域与工具沙箱约束（对齐 liveshare 的 `view`/`write` 层与 `fork` 开关，但手机是 owner 委派，不是外部 viewer）。
- 审批：手机发起的操作如涉及高危（跨会话、改配置、开 session 保险柜）→ 走手机审批（同一设备既是请求方又是审批方时，仍需一次生物识别，防"手机被小孩/恶意 App 拿着"）。
- 与桌面并发：桌面正在跑 turn 时，手机发 `agent/prompt` 进入该会话的 inbox（与 DSH 既有 `user-rpc` principal 机制一致），不打断、不设超时。
- 手机不加载 agent 运行时（§4.8.1）；即使手机被 root，也无法在本机执行工具，只能驱动远端 host。

### 5.4 多主账号与配置同步（S4 的一部分）

- 账号槽：桌面/手机都能同时登录多个主账号；每个槽是独立 `domainId` 命名空间（§4.12）。
- 手机主界面 = 底栏移动版：默认展示"当前账号槽"的底栏项；账号切换器在顶部；每个账号槽各自的配置同步（`kind=config`）。
- 一键同步：手机改主题/底栏 → 写 `config` 对象 → 已配对桌面在下次打开/连接时拉取；离线期间的桌面改动进入"待合并"队列（每键 last-write，UI 标注来源设备）。

## 6. 威胁模型

> 默认攻击者能力：能拿到任意一张口令票、能控制自己的终端、能监听自己所在网络、能重放/篡改自己的流量；**不能**读他人进程内存、不能破 SE/StrongBox、不能改主办方主机。

| 编号 | 威胁 | 攻击路径 | 处理 | 残余风险 |
| --- | --- | --- | --- | --- |
| T1 | 口令被转发/截图 | 私聊转给朋友；群海报被爬 | 首绑设备、一次性核销、并发=1、限流、名册显示设备 | 拿到**未用**票的人仍可自己用（预期：票就是可赠送的） |
| T2 | 口令爆破 | 脚本撞 50/70 bit 空间 | 主机 HMAC 存储 + 四层限流 + 统一错误 + 批次锁定 | 在线大量并发（需 host 侧资源，限流兜底） |
| T3 | 口令离线爆破 | 拿到 host 磁盘（tickets 文件） | 只存 HMAC；`batchKey` 与 `root.key` 分离且 0600；没有 key 无法离线验证 | 拿到 `batchKey` 的本地攻击者（等同 host 被控） |
| T4 | 票据复制到另一设备 | 复制 cap 文件/配置 | cap 绑设备公钥（`sub`）+ 请求由设备私钥签名；复制品无法签 | 设备私钥被导出（PWA 降级场景，见 §11） |
| T5 | 重放审批/票据 | 录下 `approve/submit` 或 `vault/open` 回包 | challenge/nonce/单调计数/短 TTL；host 单次使用缓存；回包 sig 绑代次 | 时钟回拨（用单调计数兜底） |
| T6 | 撤销延迟（离线设备） | 被踢设备断网继续听/看缓存 | 短 TTL + 续期；`revEpoch` + 撤销列表；敏感操作 fail closed | 离线期间最多撑到 TTL 结束；缓存内容在删除前仍可读（除非 C 档 2-of-2） |
| T7 | SIM swap / 手机号接管 | 补卡收验证码 | 手机号不进认证/恢复公式；审批要设备私钥签名 | 通知渠道被换号 → 只影响提示，不影响权限 |
| T8 | 手机丢失 | 捡到手机 | 设备清单 + 一键注销 + `revEpoch+1` + 恢复码/第二设备；高危操作生物识别 | 锁屏被破（4/6 位 PIN 被偷看）→ 需 attestation + 短 TTL 降低窗口 |
| T9 | 恶意 guest 反向读 | 用 cap 调 `sessions/*`/`files/*` | 角色动作上限（表 §4.6）+ RPC 白名单按角色过滤 + 默认拒绝 | 逻辑漏洞（需攻击矩阵测试） |
| T10 | 保险柜神谕 | 让 host 解任意密文 | 沿用现有设计（无解密接口、只按账本派生） | — |
| T11 | 审批钓鱼/疲劳 | 伪造请求、轰炸手机 | 号码匹配、摘要哈希、来源设备指纹、速率限制、无 passcode 回退、高危延迟 | 用户自己被骗（社会工程） |
| T12 | "手机号一致→提权"被滥用 | 子账号口令泄露 + SIM swap | **否决该路径**；提权只能由主账号手机签名、作用域化、记审计 | — |
| T13 | prompt injection 发码/提权 | agent 被诱导调用工具 | 发码/审批/改权限**不进模型面**；只人类 UI + 签名通道 | agent 可以正常读数据（设计如此） |
| T14 | 单端偷建跨账号链接 | 被控桌面偷偷 link | 2-of-2 双方手机签名；`acts` 白名单；TTL；审计 | 双方手机同时被控（超出威胁模型） |
| T15 | 降级到旧客户端绕过 | 用 rc.15 客户端连接 | 门票能力是新的 `caps`；旧对端行为不变但不获得新权限；host 侧按 `caps` 决定是否启用 | 旧客户端仍可做"受信设备只读"（已有能力） |
| T16 | 日志/工具泄漏凭证 | 口令、cap、K_g 进日志/工具返回值 | 日志只记 `capId/ticketId` 哈希前缀、字节数；无模型工具暴露；UI 不显示密钥 | 同 OS 用户读进程内存（沿用保险柜非目标） |

## 10. 与 20261127 原稿的逐条对照

| # | 原稿表述 | 判断 | 理由 | 本文落点 |
| --- | --- | --- | --- | --- |
| 1 | 手机端不作为 Agent，而是信任节点 + 消费节点 | **保留** | 手机不跑 agent 运行时，只作 Connection/审批/消费/远程驱动 | §4.8.1 |
| 2 | 手机作通知和授权中心，所有强通知走手机 | **保留 + 修正** | 通知必须带签名与摘要；离线时补投且过期即拒；不存在"默认接受" | §4.8.5 |
| 3 | 主界面 = 底栏移动端布局；可远程管理多端全局配置、一键同步主题 | **保留** | 配置是可序列化对象，用 `kind=config` 托管对象同步；手机是配置权威 | §4.11 / §5.4 |
| 4 | 主账号共享受信体系，子账号提权受信体系；**手机号与主账号一致 → 共同受信** | **否决"手机号"这一条** | NIST 800-63B-4 把 PSTN 列为 restricted authenticator；SIM swap 是现实攻击（B §5） | 改为"设备密钥 + 作用域化提升"（§4.3 I7 / §4.9.3） |
| 5 | a/b/phone 同域，a→b 消息 phone 也收到，phone 点确定被视为 b 的动作 | **修正表述** | 身份不可借用："视为 b 的动作"会让审计失去主体；应为 `approvedBy=phone`、`executedBy=b` | §4.8.6 审批字段 + 审计 |
| 6 | 子账号在手机登录（有口令）→ 其权限等级视为主账号 | **否决** | 子账号口令本就面向不特定测试者；若口令泄露 + 手机号伪造 = 主账号被接管 | 子账号登录仍是子账号角色；owner 级只属于"主账号已配对手机"（§4.4.2 第 3 条） |
| 7 | 第一次连接默认受信，后面可撤销 | **否决作为默认** | 与零信任冲突；现实现已是"首次阻塞确认"；默认受信只可用于无数据面的公开消费通道 | §3.1 / §4.3 I9 |
| 8 | 手机远程可全编辑发送消息、发文件，对比其他 dsh 只能发固定文本 | **保留 + 约束** | 高保证来自设备绑定密钥 + attestation + 审批，不是"手机"这个形态本身；仍受 session 作用域与 remote-access | §5.3 |
| 9 | 消费终端 = 文档服务 + 网页服务（电台 + 小游戏）的入口 | **保留** | 用门票 principal 进入；公开内容可匿名 | §5.1 / §5.2 |
| 10 | 可同时登录多个主账号；跨 tailnet 交叉受信；**交叉受信必须让登陆手机作为密钥保险柜** | **保留** | 2-of-2 双方手机签名 + 作用域白名单 + epoch；这是"手机=保险柜"的最强用法 | §4.12.3 |

## 11. 开放问题与诚实的边界

1. **手机钥匙的保证等级取决于形态**：原生壳（SE/StrongBox + attestation）> PWA（不可导出 WebCrypto 密钥，但浏览器/OS 的安全属性弱于专用安全芯片）。产品必须**显示等级**（`deviceAssurance`），并在 UI 上标注"此设备为降级钥匙"；C 档门限不应允许 PWA 参与。
2. **无云推送意味着"强通知"有延迟**：不在线时只能等下次连接；原稿"所有强通知都走手机"在工程上是"所有强通知**优先**走手机，离线时补投"。若未来做推送，推送内容也不应包含可批准的材料（只做提醒）。
3. **浏览器/手机不能直接进 UDP mesh**：PWA 走 WebSocket/HTTPS 网关（本文的 `phone-gateway`）；原生壳才可选用 WebRTC/UDP。不要把"手机能 ping 通 tailnet"当成"手机能进 mesh"。
4. **匿名与追责的张力**：公开听众允许完全匿名；持票听众是"不记名但可追"（票 + 设备 + 批次），不收集手机号（与 06 的隐私表一致）。若主办方要求实名，属于产品策略，不在协议层强制。
5. **2-of-2 会制造"双丢即死"**：C 档必须配恢复码/第三 shard，否则不如 A 档。默认不开 C。
6. **同 OS 用户的恶意程序**：与保险柜一致，超出威胁模型；本文只承诺"不主动把凭证写盘/写日志/交给模型"。
7. **旧实现缺陷需要一并修**（否则设计建立在错误前提上）：`vaultMaxBytes` 未在 HostedVault 生效、`challenge` 未比对、`vaultRelease=confirm` 无 UI、`releases.json` 未实现、`bottom-settings.mjs` 缺 `vault` 组、`README.zh.md` 状态过期。建议作为 P1/P5 的"顺手修复"并回写文档。
8. **团队/组织账号**不在本期：主账号是自然人；多人共管同一账号仍靠"多台手机审批器"实现，不做管理员层级。
9. **电台 500+ 听众**不在 P2P 直连能力内（主播出口限制，见 06 §2）；门票层不解决带宽，容量问题交给 06 的中继/SFU/HLS。
